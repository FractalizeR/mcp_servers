# Этап 3.1 (PARALLEL) — find_issues: потерянные ключи и курсор

## Проблемы
- №3: `keys: ["TEST-15","TEST-999999"]` возвращает одну задачу без единого сигнала.
  Единственный намёк — расхождение `summary.searchCriteria.keysCount` и `itemsOnPage`.
  По серверу нет единой стратегии: batch-инструменты жёстко валят весь вызов (это чинит
  пакет 1.1/2.1), а `find_issues` молча теряет.
- №4: вызов только с `cursor` отбивается рефайном «Должен быть указан хотя бы один способ
  поиска». Поведение защитное и остаётся, но описание `cursor` о нём умалчивает — узнать
  можно только из текста рантайм-ошибки.

## Решение
- Стратегия по всему серверу: **частичный результат + явный перечень непопавшего**.
  В `summary` добавляется перечень запрошенных, но не найденных ключей (только когда
  поиск шёл по `keys`). Существующие поля не переименовываются — совместимость.
- Описание параметра `cursor` дополняется требованием повторять исходные критерии поиска.

## Кейсы
- поиск по `keys`, все найдены → перечень пустой
- часть не найдена → перечислены именно отсутствующие
- поиск не по `keys` (query/filter/queue/filterId) → поля нет либо оно пустое, семантика
  «не применимо» описана в схеме
- сравнение регистра ключей: `test-15` vs `TEST-15` — решение зафиксировать в тесте

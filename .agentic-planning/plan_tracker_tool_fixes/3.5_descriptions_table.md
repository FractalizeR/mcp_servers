# Таблица описаний инструментов — до/после правки discoverability (пакет 3.5)

Сгенерировано скриптами `extract_metadata.py` / `extract_after.py` (regex-парсинг `*.metadata.ts`), 153 инструментов по трём серверам (yandex-tracker, yandex-wiki, ticktick).

## Чем получено и чего этот способ не видит

Данные собраны regex-разбором поля `description` в файлах `*.metadata.ts` (одиночные/составные строки вида `'...' + '...'`) и грубым подсчётом ключей верхнего уровня в соответствующей `*ParamsSchema = z.object({...})` из парного `*.schema.ts` (эвристика по отступу — не настоящий AST-парсинг; столбец с числом параметров убран из финальной таблицы как ненадёжный после первого прохода). Чего способ не видит:
1. Описания, собранные из template literals с интерполяцией переменных (`` `...${VAR}...` ``) — такие строки regex не матчит целиком. Единственный случай в проекте — `upload-attachment.metadata.ts` в yandex-wiki: описание там фактически богатое (300+ символов), длина проставлена вручную, текст не редактировался.
2. Длина считается в символах (JS code units) после конкатенации частей — не в токенах эмбеддинга MCP-клиента; соответствие «символы → релевантность поиска» неизвестно и остаётся гипотезой пользователя, проверяемой только вживую после перезапуска сервера.
3. Не учитывает `.describe(...)` на отдельных полях Zod-схемы параметров и поле `title` в METADATA — оба тоже уходят в `tools/list` (см. `packages/framework/core/src/tool-registry/tools-list-projection.ts`), но лежат в файлах вне набора этого пакета (`*.schema.ts`) или не были частью брифа (`title`), поэтому не тронуты и не посчитаны.
4. `estimatedTokens` в разделе ниже — это ceil(sum(desc_len)/4), как считает `packages/framework/core/src/mcp-server-adapter/tools-metrics.ts:calculateToolsMetrics` для ВСЕГО `tools/list` сервера разом (не на инструмент) — единственная метрика 'бюджета токенов', реально используемая в проекте.

## Порог правки: < 45 символов (явно, по числам)

Выбран чуть выше 25-го перцентиля исходного распределения (p25≈41, медиана≈49, среднее≈69 по 153 инструментам) — это описания вида `[Category/Sub] Глагол Существительное` без единого слова контекста, отбора среди похожих инструментов или английских синонимов. Именно в эту группу попадает эталонный случай задания — `get_issues` (`[Issues/Read] Получить задачи`, 29 символов). Инструменты ≥45 символов не трогались вообще: они уже не самые бедные, а раздувать весь корпус не требовалось для решения диагностированной проблемы и прямо противоречило бы правке координатора.

Порогу удовлетворяли 64 инструмента; отредактировано **63** — `upload_attachment` (yandex-wiki) исключён, т.к. его короткая длина в первом проходе — артефакт слепого пятна парсера (template literal), а не реальная бедность описания. **90 инструментов остались нетронутыми** — их описания уже были достаточно информативными по выбранному порогу.

## Лимит длины description: поднят с 80 до 120 символов (тест обновлён)

`packages/servers/yandex-tracker/tests/mcp/tool-metadata.test.ts` жёстко проверял `description.length ≤ 80` для всех инструментов yandex-tracker (аналогов в yandex-wiki и yandex-ticktick не найдено — проверено грепом `80 символов`/`toBeLessThanOrEqual(80)` по `tests/` всех трёх серверов). Это и есть, по всей видимости, задокументированная причина бага: короткое чисто-русское «[Category] Глагол Существительное» — не недосмотр, а следствие лимита.

80 символов физически не вмещают префикс категории (`[Issues/Read] ` — 15 симв.) + суть действия + 2-4 английских ключевых слова в скобках + короткую дизамбигуацию вида «быстрее find_issues, если ключи уже известны» — такая связка занимает 95-155 символов до сжатия. Прежде чем поднимать лимит, самые длинные формулировки (`find_issues`, `transition_issue`, `get_issues`, `bulk_transition_issues`, `get_bulk_change_status`, `bulk_update_issues`, а также `get_page`/`get_page_by_id` в wiki и `get_task`/`get_project` в ticktick) были сжаты вручную ещё раз. Итоговый максимум по всем 63 отредактированным описаниям — **114 символов** (`yandex-tracker/get_issues`).

**Новый лимит — 120 символов** (тест `tests/mcp/tool-metadata.test.ts` обновлён вместе с этой таблицей, комментарий в тесте объясняет решение): даёт ~5% запас над зафиксированным максимумом, не открывает дверь абзацам — 120 символов всё ещё умещается в одну строку без переноса контекста. До правки лимит 80 не нарушал ни один инструмент tracker (0 > 80 исходно); после правки — 10 из 92, все входят в список отредактированных выше. Медиана по серверу осталась короткой (см. таблицу сумм ниже) — расширены точечно только исходные аутсайдеры.

## Известный конфликт с package-level CLAUDE.md — не мой файл, флаг для оркестратора

`packages/servers/yandex-tracker/CLAUDE.md` фиксирует правило «не смешивать русский и английский в описаниях инструментов одного сервера». Новые описания содержат английские ключевые слова в скобках рядом с русским текстом — это предписанный координатором приём против англоязычного эмбеддинга клиента и прямое нарушение этой конвенции. Строка про лимит `≤ 80 символов` в том же файле теперь тоже разошлась с фактом (тест обновлён на 120). Файл `CLAUDE.md` вне набора файлов этого пакета, поэтому сам не правил — но конвенцию нужно обновить осознанно, иначе следующий агент, читающий CLAUDE.md, повторит короткие описания.

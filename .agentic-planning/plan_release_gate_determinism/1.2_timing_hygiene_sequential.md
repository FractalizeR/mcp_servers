# Пакет 1.2 — Гигиена ожиданий в харнессах (sequential)

**Зависит от:** 1.1 (тот же набор файлов)
**Модель исполнителя:** средняя (правка по готовому решению).

**Это гигиена, а не устранение причины релизных падений.** По логам прогонов ожидания по времени
дают 0 из 6 последних падений. Пакет ценен тем, что убирает ~15 с холостого сна на сервер
(17 вызовов `withServer` × 900 мс), делает отказ при битом env мгновенным и внятным и снимает
целый класс будущих гонок. Засчитывать его как «флак устранён» нельзя.

## Что реально осталось из ожиданий (таблица B в [0_enumeration.md](0_enumeration.md))

- `raw-wire-test.ts`: `STARTUP_DELAY_MS = 900` — **единственное оставшееся ожидание старта**.
- `raw-wire-test.ts`: `sleep(300)` в `close()` — ожидание останова.
- `smoke-test-server.ts`: `sleep(2000)` и `sleep(1000)` — **оба ожидания останова**, в `finally`.
  Ожидание старта в этом файле убрал коммит `39ef0db3`, там уже стоит комментарий
  «Фиксированной паузы перед первым запросом больше нет».

## Набор файлов

Тот же, что у пакета 1.1 (шесть файлов `packages/servers/*/scripts/`). Согласовано с веткой
`claude/mcp-dev-interface-plan-ef5087`: до её пакета 3.1 эти файлы за ней не числятся.

## Что делаем

1. Удалить `STARTUP_DELAY_MS` и его вызов в `withServer` — первый запрос уходит сразу.
   Константу именно удалить, а не занулить.
2. `request()` в `raw-wire-test.ts` привести к поведению `waitForJSONRPCResponse()` из
   `smoke-test-server.ts`: отказ по событию `close`/`error` ребёнка, в тексте — код выхода,
   сигнал и накопленный stderr.
3. Обработчик `error` на `child.stdin` — иначе смерть ребёнка даёт `EPIPE` и необработанное
   исключение вместо отказа.
4. Ожидание останова **в обоих скриптах**: SIGTERM → событие `exit` → SIGKILL по пределу.
   Три места на сервер: `raw-wire close()`, `smoke` shutdown основного процесса, `smoke` `finally`
   второго процесса.
5. Арифметика таймаутов — **внутри каждого скрипта отдельно**:
   - `raw-wire-test.ts`: `RESPONSE_TIMEOUT_MS` 8 000 → 20 000 (в окно теперь входит старт).
     Глобального таймаута у скрипта нет; решить, нужен ли он при 17 вызовах `withServer`,
     и если да — назвать значение в отчёте.
   - `smoke-test-server.ts`: `TIMEOUT_MS = 40000` при четырёх окнах по 10 000 не имеет запаса —
     худший случай ровно 40 000 плюс два `spawn` и разбор трёхмегабайтного бандла. Глобальный
     таймаут сработает раньше конкретного и подменит диагностируемое сообщение. Поднять
     `TIMEOUT_MS` с запасом либо снизить окна; выбор обосновать в отчёте.
6. Подставной `http.Server` (сценарии 10–13) **не трогать** — он уже событийный
   (`server.listen(0, '127.0.0.1', resolve)`), проверено во всех трёх серверах.

**Чего НЕ делаем:** не выносим общий код, не трогаем сценарии и диагностику пакета 1.1,
`scripts/test-tool-not-found*.ts` уже удалены отдельным коммитом.

## Definition of Done

1. `grep -n "sleep(" packages/servers/*/scripts/{smoke-test-server,raw-wire-test}.ts` не показывает
   ни одного ожидания старта или останова процесса.
2. Негативная проверка: запуск с заведомо битым env отказывает **сразу**, в тексте видна ошибка
   сервера из stderr. В отчёте — вывод.
3. Новая арифметика таймаутов выписана в отчёте по каждому скрипту: сумма худших окон против
   глобального предела, с запасом.
4. Список сценариев до и после совпадает поимённо.
5. `npm run validate` в корне проходит.

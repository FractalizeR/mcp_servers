# Пакет 2.1 — Единый набор проверок для PR и релиза (parallel)

**Зависит от:** — (файлы не пересекаются с 1.1/1.2 и 3.1)
**Модель исполнителя:** средняя.

## Мотивация

`scripts/validate.sh` объявляет себя единственным источником истины о наборе проверок, и
`release.yml` зовёт его через `npm run validate`. А `ci.yml` держит собственный рукописный
список — и он разъехался: восемь шагов релизного набора на PR не запускаются вообще, два
расходятся по смыслу, один шаг не исполняет ничего. Полная таблица — A в
[0_enumeration.md](0_enumeration.md).

Практическое следствие: `test:smoke:server` и `test:raw-wire` — единственные проверки,
поднимающие реальный бандл, — впервые в жизни коммита запускаются на main. Именно на них
приходятся четыре из шести последних падений релиза, и обнаруживаются они там, где это
максимально дорого.

## Что делаем

1. `ci.yml`: заменить шаги `build` … `cpd && knip` **одним** вызовом `npm run validate`.
   `checkout`, `setup-node`, `npm ci` и кеш Turborepo остаются.
2. Сверить результат с таблицей A построчно. Расхождения, которые сверка обнажает:
   - `test` → `test:coverage`: на PR начнут проверяться пороги покрытия (80/80/75/80 из
     `vitest.shared.ts`). **Если покраснеет — пороги не понижать молча:** вынести фактические
     цифры пользователю.
   - `knip` (`turbo run knip`) → `knip:root`: первый **не исполняет ничего** — ни один workspace
     не объявляет скрипт `knip`, turbo даёт «0 successful, 0 total» и код 0. Замена на `knip:root`
     не расширяет проверку, а впервые её включает.
   - добавляются `validate:docs`, `validate:docs:root`, `validate:tools`, `format:check`
     (три из них прогнаны локально — зелёные; `test:coverage` не прогонялся).
3. `typecheck:tests` — осиротевший шаг: есть в `package.json` tracker и ticktick, нет в wiki,
   нет в `turbo.json`, не запускается нигде. **Решение пользователя.** Пакет его не подключает,
   а выносит двумя вариантами: завести задачу в `turbo.json` и дописать скрипт в wiki, либо
   удалить из двух `package.json`.
4. **Двойной прогон на main.** `ci.yml` триггерится в том числе на `push: branches: [main]`,
   поэтому после унификации каждый пуш в main выполнит полный `validate` дважды — в `ci.yml`
   и в `release.yml`. Пакет это фиксирует и выносит пользователю: оставить (страховка, turbo-кеш
   делает второй прогон дешевле) либо снять `validate` из `release.yml` после включения required
   status checks. Молча не решать.
5. `test:integration` пакета `dev-client` (появится из соседней ветки) в `validate.sh`
   **не добавлять**: требует `claude` CLI и запись MCP-клиента.

## Definition of Done

1. `ci.yml` не содержит собственного списка шагов проверки — только вызов `scripts/validate.sh`.
2. К отчёту приложена построчная сверка с таблицей A: для каждого шага показано, что он
   исполняется, либо названо, почему его нет.
3. `npm run validate` в корне проходит локально целиком.
4. Время job-а названо до и после **одним способом** — по длительности job в GitHub Actions
   (не смешивая с локальным замером).
5. Судьба `typecheck:tests` и решение по двойному прогону на main вынесены пользователю
   с вариантами, а не выбраны молча.

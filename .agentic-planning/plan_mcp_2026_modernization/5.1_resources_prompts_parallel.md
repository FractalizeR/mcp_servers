# Этап 5. Resources и Prompts (parallel)

Зависит от этапов 3 и 4: Resources требуют `structuredContent` и владельца cache-полей в adapter.

Рабочее дерево: пакеты по серверам — **основной чекаут** при strict file isolation; framework-часть
(5.1.A) делается первой и последовательно.

## Пакет 5.1.A — Resources в framework (sequential)

Новые методы у adapter: `resources/list`, `resources/read`, `resources/templates/list`. Все три обязаны
возвращать `ttlMs` и `cacheScope` — это требование спеки, владелец тот же adapter.

```
ResourceProvider
  listResources(cursor?): { resources[], nextCursor? }
  readResource(uri): { contents[] }
  listTemplates(): ResourceTemplate[]
```

- Пагинация `resources/list` — тем же opaque-cursor, что уже используется в list-эндпоинтах Трекера.
- Ошибка «ресурс не найден» — код **`-32602`**, а не `-32002`: код сменился в этой ревизии.
- Регистрация провайдеров — как у инструментов, через composition root.

## Пакет 5.1.B — ResourceLink в результатах инструментов (главный выигрыш)

**Проблема, которую решаем.** `find_issues` на 200 задач сейчас вываливает 200 объектов в контекст
модели. Это дорого и вытесняет всё остальное.

**Решение.** Инструменты, возвращающие коллекции, отдают компактную сводку плюс массив
`resource_link` вместо полных тел. Агент подтягивает тела выборочно через `resources/read`, который
к тому же кешируется по `ttlMs`.

Схемы URI (проектируются здесь, множество порождается планом):
- `tracker://issue/{key}`, `tracker://queue/{key}`, `tracker://project/{id}`
- `wiki://page/{slug}`
- `ticktick://task/{id}`, `ticktick://project/{id}`

**Граничные условия.**
- Инструмент должен уметь оба режима: ссылки и полные тела. Управление — параметром, а не глобальной
  настройкой: агент сам знает, нужны ли ему тела.
- Режим по умолчанию — решение с последствиями. Ссылки экономят контекст, но добавляют круг
  «список → чтение»; для маленьких результатов это чистый проигрыш. Разумный дефолт — порог по
  количеству элементов, и он должен быть виден в описании инструмента.
- `resource_link`, возвращённый инструментом, **не обязан** появляться в `resources/list` — спека это
  прямо разрешает. Значит `readResource` должен уметь отдать то, чего нет в списке.

## Пакеты 5.1.C.{tracker,wiki,ticktick} — провайдеры и prompts (parallel)

Наборы файлов не пересекаются.

**Resources** каждого сервера: сущности из схем URI выше.

**Prompts** — самый дешёвый способ вовлечь команду: в клиенте они выглядят как слэш-команды и не
требуют нового API, это обёртки над существующими инструментами.

- Трекер: triage очереди, дейли-сводка, сводка по спринту/проекту, разбор связей эпика.
- Вики: сводка раздела, подготовка обновления документа.
- TickTick: дневной и недельный обзор, GTD-разбор входящих.

Prompts тоже возвращают `ttlMs`/`cacheScope` в `prompts/list` — владелец adapter.

**Границы для исполнителя.** Формулировки самих промптов — на усмотрение исполнителя, но каждый
обязан быть проверен вручную хотя бы один раз на реальных данных: промпт, который не проверяли,
почти всегда даёт не тот результат, который задумывался.

## DoD этапа

- `resources/list`, `resources/read`, `resources/templates/list`, `prompts/list`, `prompts/get`
  работают на трёх серверах и возвращают cache-поля.
- Инструменты-коллекции умеют возвращать `resource_link`; тест сравнивает объём ответа в двух режимах
  и подтверждает экономию.
- `resources/read` по ссылке, отсутствующей в `resources/list`, работает.
- Несуществующий ресурс → `-32602`.
- Промпты видны как слэш-команды хотя бы в одном реальном клиенте (проверка руками).
- `npm run validate:quiet` зелёный.

## Риски

- Соблазн сделать ресурсом всё подряд. Ресурс оправдан там, где содержимое адресуемо и переиспользуемо;
  для одноразовых вычисляемых ответов это лишний слой.
- Дефолтный режим `resource_link` может ухудшить UX на маленьких выборках — отсюда требование порога.

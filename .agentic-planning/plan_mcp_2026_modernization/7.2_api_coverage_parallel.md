# Этап 7.2. Пробелы покрытия API (parallel)

Зависит от этапа 7.1 (сначала чиним имеющееся, потом добавляем новое) и от этапа 3 (новые
инструменты рождаются сразу с `outputSchema` и annotations).

Источники: `inventory/table4-tracker-api-coverage.md` (~40 областей API, ~35 непокрытых пунктов),
`inventory/table5-wiki-api-coverage.md` (11 областей).

Рабочее дерево: **основной чекаут**, пакеты по серверам не пересекаются по файлам.

## Принцип отбора

> **Пересмотрен 2026-08-14 владельцем.** Исходная посылка была фактически неверной, и вместе с ней
> отпадает главный аргумент за узкий отбор.
>
> Было: «список инструментов теперь виден агенту целиком, поэтому каждый лишний инструмент
> удорожает выбор для модели». На деле **все актуальные харнессы ищут по инструментам и не грузят
> полный список в контекст**. Значит цена лишнего инструмента для модели близка к нулю, и сжимать
> набор ради неё не нужно.
>
> Стало: **реализуем почти всё, чего не хватает, кроме опасного и совсем редко используемого.**
> Пакеты «средней ценности» 7.2.B и 7.2.D переходят из «по мере необходимости» в план работ.
>
> Что это НЕ отменяет: решение этапа 2 об удалении lazy discovery остаётся верным — оно стояло на
> втором доводе, что клиент и так реализует поиск сам, и сервер дублировал чужую работу. Таблица
> «что сознательно не реализуем» ниже тоже остаётся: там отбор идёт по опасности и по редкости, а
> не по стоимости выбора.

Реализуем то, что меняет сценарии работы **с группами задач** — это наше отличие, — и всё остальное,
что не попадает под «опасно» или «почти не используется».

## Пакет 7.2.A — Tracker, высокая ценность

**Entity API: Goals, Projects, Portfolios — включая Key Results.** Крупнейший структурный пробел.
Команда, работающая группами задач, группирует их вокруг цели или портфельного проекта; сейчас
через MCP не создать цель, не прочитать её и не получить список связанных задач — верхний уровень
иерархии работы агенту не виден вовсе.

Key Results (`keyResultItems`) — отдельная подобласть: получение, добавление, полная замена и
очистка. В референсном клиенте они появились между октябрём 2025 и августом 2026, то есть это не
застарелый пробел, а недавно появившаяся в самом Трекере возможность. Для команды, отчитывающейся
по OKR, это прямое попадание в сценарий «прогресс по цели через привязанные задачи».

Внимание: у Трекера есть **две разные** сущности «проект» — legacy `/v2/projects`, который мы уже
покрываем, и Project внутри Entity API. Это разные вещи с разными идентификаторами; смешать их в
одном инструменте нельзя, а имена инструментов должны различать их явно.

**Users: получение и поиск.** Без резолва «Иван Иванов» → login/uid агент не может заполнить
`assignee`, `summonees`, права очереди. Это нужно почти в каждом сценарии записи по группе задач и
блокирует часть исправлений из этапа 7.1 (упоминания в комментариях).

## Пакет 7.2.B — Tracker, средняя ценность

Порядок — по отношению «польза к стоимости», реализовывать по мере необходимости, а не списком:

- **Справочники Administration** — типы задач, статусы, резолюции, приоритеты. Сейчас агент
  угадывает ключи при создании и переходах, получая ошибки валидации на пустом месте. Частично
  закрывается `raw_api_request`, но требует знания точного пути.
- **Сохранённые фильтры** — команда держит общий фильтр вроде «открытые баги спринта», агент же
  каждый раз реконструирует критерии вручную. Избранное — надстройка, вторична.
- **Локальные поля очереди** — команды с доменными полями не могут узнать их схему через MCP.
  Нюанс из референсного клиента: локальное поле адресуется PATCH по короткому ключу, а не по
  глобальной ссылке — легко сделать неправильно.
- **Колонки доски и жизненный цикл спринта** (старт, архивация, удаление). Сейчас MCP покрывает
  чтение сущностей, но не планирование итерации.
- **Поиск по worklog в масштабе организации.** Отчёт по трудозатратам за период сейчас требует
  перебрать все задачи и опросить каждую — вместо одного запроса с фильтром по автору и датам.

## Пакет 7.2.C — Wiki, высокая ценность

**Контекст, меняющий приоритеты.** Проверка на живом API показала: таблицы, которые команда реально
ведёт, — это YFM-разметка внутри `content`, а не динамические таблицы. Grid-область заморожена
(см. этап 7.1). Значит ценность смещается к операциям с содержимым и к навигации по структуре.

- **Полнотекстовый поиск.** Недостижим никаким путём: не реализован, а `raw_api_request` только
  GET, тогда как поиск — POST. Без него агент не найдёт страницу, не зная заранее её точный slug
  или идентификатор. Для команды, ведущей документацию вместе с агентом, это ломает самый частый
  вход в сценарий.
- **Обход поддерева раздела.** Единственный документированный способ пройти структуру раздела, с
  пагинацией и фильтром актуальности. Нужен почти в каждой задаче «обнови документацию».

## Пакет 7.2.D — Wiki, средняя ценность

- **Комментарии** — ни чтения, ни записи. Обсуждение решений в комментариях к странице — обычный
  паттерн совместного ведения вики.
- **Права доступа к странице** — добавление читателя или редактора на новый раздел; `raw` не
  закрывает, потому что все методы не GET.
- **Вложения: загрузка и скачивание.** Сейчас вложения видны через список ресурсов, но не
  управляемы — ни положить файл, ни забрать содержимое.

## Что сознательно не реализуем

Решения зафиксированы, чтобы к ним не возвращаться на каждом круге:

| Область | Причина |
|---|---|
| Удаление и восстановление очереди | Необратимо по последствиям, уносит все задачи очереди. Автономный агент не должен иметь такой кнопки |
| Import-эндпоинты Трекера | Предназначены для миграции с сохранением исторического авторства; в руках агента — риск подмены истории |
| Автодействия и триггеры очереди | Ошибка агента здесь срабатывает отложенно, на следующей подходящей задаче, и диагностируется тяжело |
| Upload Sessions Вики (MS365) | Шесть методов с состоянием и дедлайнами ради нишевого сценария облачных документов |
| Дашборды, отсутствия, макросы, категории полей, внешние приложения | Административные и визуальные области, не влияющие на работу с группами задач |
| Восстановление страницы по токену — изолированно | Списка выданных токенов в API нет; инструмент без него бесполезен. Сначала проверить, перечисляются ли токены где-либо |

**Массовое редактирование Entity по фильтру** — если Entity API будет реализован, массовые правки
по фильтру, а не по явному списку идентификаторов, требуют режима предварительного просмотра на
уровне инструмента. Копировать семантику API один в один здесь нельзя: это типичный источник
«задело больше, чем думал».

## DoD этапа

- Каждый новый инструмент имеет `outputSchema`, annotations и тест.
- Инструменты Entity API не смешивают Entity-проект с legacy-проектом: разные имена, разные схемы,
  в описании явно сказано, что есть что.
- Массовые операции с фильтром имеют режим предварительного просмотра.
- `npm run validate:quiet` зелёный.

## Риск

> **Пересмотрен вместе с принципом отбора.** Прежняя формулировка — «реализуем 7.2.A, смотрим на
> практику, потом решаем по средней ценности» — опиралась на неверную посылку о стоимости лишнего
> инструмента для модели. Она снята: делаем A, B, C и D.

Оставшийся риск другой природы и никуда не делся: **объём**. Четыре пакета — это десятки новых
инструментов, каждый со схемой, `outputSchema`, annotations, тестом и проверкой достижимости
параметров. Опасность не в том, что модели станет труднее выбирать, а в том, что широкий заход
делается наспех: новый инструмент, рождённый без теста или с непроверенной формой запроса, — это
будущий дефект того же класса, что мы чинили в этапе 7.1.

Отсюда порядок: сначала пакеты высокой ценности (7.2.A и 7.2.C), затем средней (7.2.B и 7.2.D),
и каждый — с полным DoD, а не «добавили инструмент, потом допишем тесты».

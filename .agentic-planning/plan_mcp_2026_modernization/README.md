## Грабля исполнения: устаревший `dist` ломает прямой прогон vitest

Стоила двух возвратов пакета и долгой диагностики, поэтому записана здесь, а не в этапе.

`packages/servers/*/vitest.config.ts` резолвит `@fractalizer/mcp-core` алиасом на **исходники**
framework, но часть импортов доезжает до того же пакета через `node_modules`, то есть на **`dist`**.
Пока `dist` свежий, обе дороги дают одно и то же. Как только в `src` framework что-то добавили и не
пересобрали, в процесс загружаются два разных экземпляра одного модуля, и поле схемы оказывается
`undefined` на этапе инициализации. Симптом — `TypeError: Cannot read properties of undefined
(reading '_zod')` на **импорте**, «0 test», Failed Suites; падает почти всё, что тянет реестр
инструментов.

Почему это не видно штатным путём: `npx turbo run test` собирает зависимости первым шагом, поэтому
`dist` всегда свежий. Красным становится только голый `npx vitest run` из каталога пакета — ровно то,
что мы велим агентам делать ради экономии времени.

Почему это дважды увело диагностику не туда:
- в отдельном worktree `dist` отсутствует вовсе, поэтому всё идёт из `src` согласованно и тесты
  зелёные. Выглядит как «дерево проклято», хотя на деле «в дереве есть протухший артефакт»;
- сравнение «worktree на базовом коммите против основного дерева» меняет **две** переменные разом —
  и содержимое, и наличие `dist`. Вывод «дело в содержимом» из такого сравнения не следует.

Решающая проба, которая различает: перенести файлы подозреваемого в чистый worktree. Если там зелено —
дело не в файлах.

**Что делать:** перед прямым `npx vitest run` в пакете сервера — `npx turbo run build --filter=<пакет>`
(он подтянет и сборку framework). Это надо писать в задание агенту явно.

## Отдельная работа: типизация тестов

Вскрыто при разборе находки L11 внешнего ревью. `tests/` и `scripts/` были исключены из проверки
типов, и там накопились настоящие ошибки, которых никто не измерял.

Скрипты вычищены полностью. С тестами иначе: включение их в проверку показало **порядка 900
предсуществующих ошибок примерно в 120 файлах** — почти все от `noUncheckedIndexedAccess` (доступ по
индексу массива) и устаревших моков, где у фикстуры не хватает полей. К миграции на SDK это
отношения не имеет.

Правку этих 900 сознательно **не делали**, и `typecheck:tests` не подключён к валидации у Трекера и
Вики (у TickTick подключён — там ошибок не было). Причина: массовая правка тестов ради компилятора
меняет их смысл молча, а разбирать нужно поштучно. Отдельный план, не довесок к ревью.

Побочное следствие, которое надо помнить: пока это не сделано, проверка типов у трёх серверов
неоднородна — тесты TickTick типизируются, тесты Трекера и Вики нет.

## Найденное по ходу, не входящее ни в один этап

- **Документация сервера Вики отстала от кода.** Её `README.md` перечисляет 7 инструментов страниц и
  `ping`, тогда как 12 инструментов таблиц, ресурсов и raw API существовали ещё до этого плана;
  `CLAUDE.md` сервера утверждает, что «Фаза 2: Grids & Resources (не начата)», хотя она давно
  закончена. Найдено пакетом 3.1.C.wiki, им же не исправлено намеренно: обновление документации
  сервера — отдельная работа, а не довесок к простановке annotations. Заводится отдельной задачей
  после плана.

**Инвентарь протухает.** Перед стартом каждого этапа перечисление пересобирается заново по актуальному
коду — унаследованная таблица выглядит как выполненная работа, но собиралась под другой вопрос.

## Общие правила исполнения

- Рабочее дерево для каждого пакета указывается явно в его разделе. По умолчанию — основной чекаут при
  strict file isolation; worktree там, где пакеты пишут параллельно в пересекающиеся области.
- Агентам запрещены `git stash`, `git checkout -- <file>`, `git restore`, `git clean` в общем дереве.
- После каждого этапа: `npm run validate:quiet`, отметка прогресса здесь, коммит на русском.
- Ветка `main` защищена — перед коммитом в неё спрашивать.

## Открытые пункты, которые агентами не закрываются

1. **Ручная проверка в клиентах.** Подключить серверы к Claude Code и к Codex CLI, второй — и по
   умолчанию, и с `CODEX_MCP_PROTOCOL_VERSION=2026-07-28`. Это DoD этапа 4, единственный его пункт,
   который агент выполнить не мог.
2. **Ручная проверка девяти промптов** на реальных данных. План требует хотя бы один живой прогон
   каждого: промпт, который не проверяли, почти всегда даёт не тот результат, а тестом это не ловится.
3. **Пилот Apps вживую** — в Claude Desktop с виджетом и в Codex CLI без него.
4. **Версия Entity API — непроверенная догадка.** Принято `v3` по аналогии; если неверно, пять
   инструментов ответят 404. Проверяется только живым вызовом, правка — одна строка на операцию.
5. **Флаг `requiresExplicitUserConsent` для создающих инструментов** — решение владельца не принято.
   JSDoc предписывает выставлять его для create и delete, по факту у создающих инструментов он
   `false`, а эвристика `validate:tools` ищет только `update|delete|append|bulk|batch` и не ловит
   `create`, `clone`, `remove`.

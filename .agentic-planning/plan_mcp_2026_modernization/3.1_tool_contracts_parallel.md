# Этап 3. Контракты tools (parallel)

Зависит от этапа 2. С этапом 4 не пересекается по файлам — можно вести одновременно.

Рабочее дерево: пакеты 3.1.A и 3.1.B — **основной чекаут**, последовательно (общий framework).
Пакеты 3.1.C.* — **worktree на каждого исполнителя**: они правят по ~150-200 файлов каждый, и в общем
дереве параллельный прогон тестов трёх серверов будет мешать сам себе.

**Перечисление.** 97 инструментов, `inventory/table2-tools-matrix.tsv` (сервер × имя × категория).

**Способ сбора, описанный в артефакте, больше не существует.** Таблица собиралась парсингом
`generated-index.ts`, а этап 2 удалил эти файлы вместе с пакетом `search`. Новый источник истины —
живой реестр: `scripts/smoke-test-server.ts` каждого сервера поднимает процесс и спрашивает
`tools/list`. На момент закрытия этапа 2 он даёт 50 инструментов у Трекера, 22 у Вики, 25 у TickTick —
ровно 97, то есть число сходится с артефактом, и `SearchToolsTool` в нём уже нет.

Перечисление пересобирается этим способом перед стартом, а DoD этапа проверяется тестом, обходящим
реестр, — не сверкой с файлом-артефактом, который протухает после каждого добавления инструмента.

Структура одного инструмента: три файла — `*.metadata.ts`, `*.schema.ts`, `*.tool.ts`. Значит массовые
пакеты трогают порядка 200 файлов на Трекер и по 90-100 на Вики и TickTick.

## Пакет 3.1.A — JSON Schema 2020-12 (framework, sequential)

- `zod-json-schema-adapter.ts:83` и `:175`: `target: 'draft-7'` → `'draft-2020-12'`. Zod `4.3.6` это
  поддерживает.
- Убрать вырезание `$ref` и `$schema` (`zod-json-schema-adapter.ts:13`, `schema-to-definition.ts:65`)
  вместе с комментариями «MCP не поддерживает» — оба утверждения теперь неверны.
- Zod остаётся единственным источником истины и валидатором входа. JSON Schema — только описание
  контракта наружу; это не замена валидации и не ослабление строгости.

**Обязательный тест** — на каждый инструмент:
- схема валидна как JSON Schema 2020-12;
- **в схеме нет рекурсивных `$ref`** (цикла). Рекурсия ломает programmatic tool calling на стороне
  клиента с ошибкой `Circular $ref detected`, причём тот же самый инструмент при обычном вызове
  работает — то есть без теста дефект вскроется только у пользователя.

**Граничное условие.** Спека требует, чтобы `inputSchema` был валидным объектом JSON Schema, а для
инструментов без параметров рекомендует `{ "type": "object", "additionalProperties": false }`.
Проверить, что генератор для пустой схемы выдаёт именно это, а не `{}`.

**Факт исполнения (пакет 3.1.A, принят).**

- Настоящий вред старого кода был не в `$schema`, а в `$defs`: адаптер пересобирал результат из
  четырёх полей и молча отбрасывал `$defs`, из-за чего `$ref` на `#/$defs/...` оставался битой
  ссылкой. Теперь `$defs` проходит насквозь, `ToolInputSchema` расширен соответствующим полем.
- **`$schema` в выход всё же не добавлен** — отклонение от буквы плана. Обоснование исполнителя:
  единственный валидатор входа в проекте — Zod, диалект по URI никто не выбирает, а добавление поля
  ломало десяток тестов на точное равенство. Принято: без `$schema` клиент считает диалект по
  умолчанию, что для 2020-12 корректно. Риск остаточный и низкий — клиент, желающий узнать диалект
  явно, этого сделать не сможет.
- Граничное условие про пустую схему оказалось **уже выполненным** до пакета: генератор и раньше
  давал `{ type: 'object', properties: {}, additionalProperties: false }`. Добавлен тест, кода не
  потребовалось.
- Детектор циклов — отдельный модуль `definition/detect-circular-refs.ts` (DFS с резолвом по JSON
  Pointer). Его способность ловить цикл доказана живой пробой: в схему `ping` временно внедрена
  самоссылка, тест упал, правка возвращена.

## Пакет 3.1.B — расширение `ToolDefinition` (framework, sequential)

Зависит от 3.1.A.

Расширить `packages/framework/core/src/tools/base/base.types.ts`:

```
ToolDefinition
  name, description            // как сейчас
  title?                       // человекочитаемое имя для UI
  inputSchema                  // 2020-12
  outputSchema?                // 2020-12, описывает structuredContent
  annotations?: {
    readOnlyHint?, destructiveHint?, idempotentHint?, openWorldHint?
  }
```

`icons` — **не** на уровне инструмента, а один раз на сервер, см. пакет 3.1.D.

Изменить формирование результата в `base-tool.ts:255-258`: возвращать `structuredContent` **и**
сериализованный JSON в `content[].text` — спека прямо требует текстовый дубль для обратной
совместимости. Единый success/error envelope фиксируется здесь же.

Изменить проекцию в `tools/list` (`server.ts:88-92` каждого сервера) — сейчас она отбрасывает все поля,
кроме трёх. Это единственное место этапа 3, пересекающееся с этапом 4; чтобы избежать конфликта,
**проекция переезжает в framework** и `server.ts` вызывает её, а не строит объект сам.

Удалить неиспользуемый `buildDefinition()` (`base-tool.ts:143`) — не переопределён ни одним инструментом.

**Контракт, зафиксированный пакетом 3.1.B — на него опираются пакеты 3.1.C.\*, 3.1.E и этап 4:**

- Проекция: `projectToolDefinitionsForList(definitions: readonly ToolDefinition[]): McpToolListEntry[]`
  в `packages/framework/core/src/tool-registry/tools-list-projection.ts`, экспортируется из
  `@fractalizer/mcp-core`. `server.ts` трёх серверов её вызывает и объект больше не собирает.
- Envelope: `formatSuccess(data)` → `{ success: true, data }`, `formatError(message, error?)` →
  `{ success: false, message, error? }`. Оба возвращают один и тот же payload дважды — как
  `structuredContent` и как `JSON.stringify` в `content[0].text`.
- `title?`, `outputSchema?`, `annotations?` на `ToolDefinition` — **опциональные**. На момент
  фиксации контракта ни один из 97 инструментов их не заполняет; проверок, падающих на их
  отсутствие, вводить нельзя, пока волна 3.1.C не пройдёт.
- `buildDefinition()` удалён; `getParamsSchema` остался опциональным на уровне типа (иначе не
  компилируются mock-классы тестов, переопределяющие `getDefinition()` целиком), но его отсутствие
  теперь даёт явную ошибку вместо вызова несуществующего legacy-метода. Попутно вскрылась и заменена
  тавтологическая проверка в `tool-metadata.test.ts`: она искала метод в прототипе базового класса и
  была всегда истинной.

## Пакеты 3.1.C.{tracker,wiki,ticktick} — классификация и outputSchema (parallel)

По одному пакету на сервер, наборы файлов не пересекаются. Зависят от 3.1.B.

Для каждого инструмента своего сервера:

1. **Проставить annotations.** Выводить их из существующего `requiresExplicitUserConsent` **нельзя**:
   поле заполнено в 3 файлах из 97. Классификация делается заново по смыслу операции:
   - `readOnlyHint` — операция не меняет состояние в системе;
   - `destructiveHint` — операция разрушающая (удаление, необратимая перезапись);
   - `idempotentHint` — повтор с теми же аргументами не меняет результат;
   - `openWorldHint` — операция обращается во внешний мир (для наших API-инструментов — да).

   Создание, изменение, удаление и raw API требуют **раздельной** классификации: «не read-only» не
   означает «destructive», а «update» не означает «идемпотентно».

2. **Добавить `outputSchema`** и возврат `structuredContent`. Схема описывается на Zod рядом с
   входной, в том же `*.schema.ts`.

**Границы для исполнителя.** Спорные классификации (например, идемпотентен ли `add_comment`) решаются
самостоятельно и называются в отчёте одной строкой каждая. Возврат к оркестратору — только если
выяснится, что для целой категории инструментов классификация неоднозначна системно.

**Порядок работы.** Сначала одна категория целиком как образец, потом остальные. Тесты по ходу гонять
фильтром по своему серверу (`turbo run test --filter=<пакет>`), полный `npm run validate:quiet` —
один раз перед сдачей.

## Пакет 3.1.D — иконка сервера

> **Перенесён в очередь после этапа 4** (решение оркестратора при раскладке по волнам). Пакет требует
> отдавать иконку в ответе `server/discover` и не отдавать её в per-response `serverInfo`. Ни того,
> ни другого до этапа 4 не существует: `server/discover` появляется в пакете 4.1.C, а владельцем
> `serverInfo` в `_meta` становится adapter из 4.1.B. Сделанный раньше, пакет пришлось бы переделывать
> сразу после переезда протокольных полей в adapter. Содержание пакета ниже не меняется.

Одна иконка на сервер, в `Implementation.icons` (идентичность сервера), не на инструментах.

- `src` — **`data:` URI с base64**. Внешний хост не нужен, что важно для stdio.
- **PNG обязателен**: клиенты, умеющие рисовать иконки, MUST поддерживать `image/png` и `image/jpeg`;
  `image/svg+xml` — только SHOULD, часть клиентов отклонит SVG из-за риска встроенного JavaScript.
  Массив допускает несколько записей: PNG как гарантия, SVG рядом.
- Текст в SVG — **в кривых**. Шрифт не встраивается: без него надпись отрисуется чем попало.
- **Иконка не едет в каждом ответе.** `serverInfo` сервер SHOULD слать в `_meta` каждого
  результата, но `icons` внутри него опционально. Отдаём иконку один раз в `server/discover`, в
  per-response `serverInfo` оставляем имя и версию. Причина не в производительности: в контекст
  модели `_meta` не попадает (туда идут определения инструментов и результаты вызовов), а пара
  килобайт на локальном stdio незаметна. Причина в логах — клиентский `mcp.log` и наш Pino иначе
  накапливают одну и ту же картинку по разу на каждый ответ.
- **Ассеты готовы**, брать из `assets/icon/`: рабочий вариант — `fr-metric` (расстановка по
  метрикам шрифта), `fr-metric.svg` плюс `fr-metric-48/96/256.png`. В массив `icons` кладём обе
  записи: PNG 48 (1159 байт, обязательная поддержка у клиентов) и SVG (2082 байта в data URI,
  `sizes: ["any"]`). Обоснование выбора, лицензия и скрипты пересборки — в `assets/icon/README.md`.
- **Шрифт — Marck Script** (SIL OFL 1.1, Denis Masharov, `fsType = 0`), лицензия записана в самом
  файле шрифта. Рассматривался Roscherk SHA — отклонён: лицензионных полей в файле нет вовсе,
  `fsType = 4` («Preview & Print») ограничителен, контур втрое тяжелее.
- Опционально `theme: light|dark`, `sizes: ["any"]` для SVG.

## Пакет 3.1.E — diff страницы Вики перед сохранением

Вынесен сюда из Apps-трека: **построчный diff не требует MCP Apps**. Обычный инструмент, возвращающий
разницу между текущим и предлагаемым содержимым страницы, работает во всех клиентах, включая Codex, и
закрывает тот же риск — незаметную порчу страницы агентом.

Контракт: инструмент принимает идентификатор страницы и новое содержимое, возвращает структурированный
diff, **ничего не записывая**. `readOnlyHint: true`.

## DoD этапа

- Все 97 инструментов имеют `annotations` и `outputSchema`; проверяется тестом, обходящим реестр, а не
  ручным просмотром.
- Тест схем: каждая валидна как 2020-12, ни одна не содержит цикла `$ref`.
- `tools/list` отдаёт `title`, `outputSchema`, `annotations`.
- Ответ инструмента содержит и `structuredContent`, и текстовый дубль.
- `icons` присутствует в ответе `server/discover` и отсутствует в `_meta` обычных результатов.
- `npm run validate:quiet` зелёный.

## Риски

- Объём. Классификация 97 инструментов — механическая, но не автоматическая: эвристика по имени
  (`create|update|delete|...` даёт ~49 совпадений) годится как черновик, но не как результат.
- Соблазн сгенерировать `outputSchema` из типов автоматически. Проверить осуществимость до того, как
  делать вручную: если существующие DTO уже описаны на Zod, работа сокращается на порядок.

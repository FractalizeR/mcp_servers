# Таблица 5. Покрытие API Яндекс.Вики нашим MCP-сервером

Дата: 2026-08-14. Сервер: `packages/servers/yandex-wiki/` (22 зарегистрированных tools).

---

## Чем получено

**Способ 1 — официальная документация.** Прочитаны через WebFetch (HTML→markdown конвертация + суммаризация моделью, не verbatim-цитаты) страницы `yandex.ru/support/wiki/en/api-ref/{about,access,index}` и index-страницы всех 11 разделов, на которые ссылается общий индекс: `pages`, `attachments`, `pages_access`, `pagesresources`, `comments`, `grids`, `users`, `upload_sessions`, `operations`, `recovery_tokens`, `search`. Для страниц, которые реализованы у нас (`pages`, `grids`), дополнительно прочитаны detail-страницы конкретных методов (`pages__page_grids.md`, `pages__descendants_by_id.md`, `pages__create_page.md`, `pages__delete_page.md`, `pages__get_page_details.md`, `grids__update_grid.md`, `grids__update_cells.md`, `grids__remove_rows.md`, `grids__add_rows.md`, `grids__delete_grid.md`) — их содержимое процитировано в разделе «Дефекты» дословно там, где это указано.

**Способ 2 — код сервера.** `find`/`Read` по `src/wiki_api/{entities,dto,api_operations,facade}/`, `src/tools/api/**/*.{schema,tool,operation}.ts`, `src/tools/generated-index.ts`, `src/common/schemas/*`. Также прочитан `IHttpClient` (`packages/framework/infrastructure/src/http/client/i-http-client.interface.ts`) и его `AxiosHttpClient` реализация — чтобы отличать баги нашего кода от ограничений транспорта.

**Способ 3 — YFM.** `yandex.cloud/docs/wiki/static-markup` (редирект на `yandex.ru/support/wiki/ru/static-markup`, помечена как документация **старого редактора**) и `github.com/yandex-cloud/yfm-documentation` (общий синтаксис YFM/Diplodoc, не специфичный для Wiki).

### Чего этот способ не видит

- **WebFetch — не прямой доступ к тексту, а суммаризация моделью.** В нескольких попытках сама модель явно писала «HTTP-глаголы не указаны в документе, показаны по догадке» (attachments, comments, pages_access, `grids/index.md` без пометки — но проверка через detail-страницы `grids__update_grid.md`/`grids__update_cells.md` показала, что оба метода на самом деле **POST**, а не `PUT`, как «угадала» первая суммаризация индекса). Это значит: **HTTP-методы и точные названия query-параметров в разделах, которые я НЕ перепроверял detail-страницей, не гарантированы** — они помечены как «по названию раздела», а не как факт.
- Недокументированные/неофициальные эндпоинты (если есть) — не видны в принципе.
- Различия между Yandex 360 for Business и Yandex Cloud Organization версиями Wiki (разные заголовки `X-Org-Id`/`X-Cloud-Org-Id`) в API-референсе не разведены по методам — не проверялось, различается ли состав методов между инсталляциями.
- Возможности, доступные только через веб-интерфейс (drag-n-drop медиа, real-time совместное редактирование, история изменений в UI, экспорт в PDF/DOCX через кнопку) — не имеют отражения в API-референсе и не проверялись.
- Rate limits — в прочитанных страницах не упомянуты вообще (не значит, что их нет).
- `yw_raw_api_request` — **только GET** (см. `src/tools/api/raw/raw-api-request.schema.ts:24`, паттерн пути `^\/v1\/[\w.~\/-]*$`, без query-строки в самом пути). Это значит: там, где ниже стоит «покрыто через raw_api_request», это верно только для **чтения**; ни один из недостающих write-методов (access, comments-write, upload_sessions, recovery) через raw закрыть нельзя.

## Заметные пробелы

- **Search (высокая).** Команда ведёт документацию вместе с ИИ-агентом — полнотекстовый поиск по базе (`POST /search`, поддерживает `query`, `filters.type`, `filters.authors`, `cluster`, диапазоны дат, `highlight`) прямо сейчас недостижим никаким путём: раздел не реализован, а `raw_api_request` — GET-only и метод в любом случае POST. Без него агент не может найти страницу иначе как знать точный slug/id заранее.
- **Page Descendants / структура раздела (высокая).** `GET /pages/{id}/descendants` и `GET /pages/descendants` — единственный документированный способ обойти поддерево вики-раздела (с пагинацией `cursor`/`page_size`, фильтром `actuality`). Не реализовано и не покрывается `raw_api_request` практически (путь можно вызвать вручную, но это ровно тот случай, для которого стоило бы дать типизированный tool — навигация по разделу нужна почти в каждой задаче «обнови документацию»).
- **Comments (средняя).** Постановка задач и обсуждение решений в комментариях к странице — обычный паттерн совместного ведения wiki. У нас нет ни чтения, ни записи; чтение потенциально закрывается raw (если GET), запись — нет.
- **Page Access / права (средняя).** Управление доступом (`pages_access`, 4 метода) не реализовано вообще, и raw это не закрывает (все методы — не GET). Для команды, ведущей вики с ИИ-агентом, добавление читателя/редактора на новый раздел — частая операция.
- **Attached Files: upload/download (средняя).** `yw_get_resources` перечисляет вложения (метаданные), но нет ни загрузки нового файла на страницу, ни скачивания содержимого существующего — то есть вложения только «видны», но не управляемы.
- **allow_recursive/recursive у delete_page (низкая-средняя).** См. «Дефекты» №4 — узкий, но реальный кейс: удаление раздела с дочерними страницами.
- **Recover Page By Token (низкая).** Есть выдача `recovery_token` при удалении страницы, но нет tool для собственно восстановления — цепочка «удалили → передумали» не закрывается нашим сервером целиком.

## Проверка на живом API (2026-08-14, дополнение к отчёту)

Выполнена оркестратором через подключённый MCP-сервер Вики на реальной странице
`homepage/proekt-dvizh/razrabotka/priemka-zadach-na-texnicheskuju-prorabotku/sprint-20.07-2.08`
(id `50112654`, `page_type: "wysiwyg"`).

**Главное: в Вики два разных вида таблиц, и наши grid-инструменты работают только с одним.**

- **Разметочная таблица** — синтаксис YFM `#| ... ||  ... ||  ... |#` прямо внутри `content`
  страницы. Именно так устроена проверенная страница спринта: вся таблица приёмки задач лежит
  в теле страницы как текст.
- **Динамическая таблица (grid)** — отдельный объект с UUID, собственным API
  (`/v1/grids/...`) и строками/колонками.

На проверенной странице `yw_get_resources` вернул **0 ресурсов** (и с фильтром `types=['grid']`,
и без фильтра), `GET /v1/pages/{id}/descendants` — пустой список. То есть ни одного grid-объекта,
хотя визуально на странице большая таблица.

**Следствие для плана.** Все 12 grid-инструментов (больше половины из 22 инструментов сервера)
неприменимы к таблицам, которые команда реально ведёт в контенте страниц. Работа с такой таблицей
возможна только через операции с `content` целиком: чтение, `update_page`, `append_content`.
Это поднимает ценность инструмента diff перед сохранением (пакет 3.1.E) и понижает приоритет
доработок grid-области, включая дефект `row_id` (№2) — он реален, но затрагивает сценарий,
который у команды может вообще не использоваться.

**Проверить перед решением:** используются ли динамические таблицы где-либо в их вики. Если нет —
grid-инструменты кандидаты не на доработку, а на вывод из эксплуатации.

**Побочно уточнено:** страница с `page_type: "wysiwyg"` возвращает `content` в YFM-разметке
(`#|`, `||`, `**жирный**`, `&nbsp;`), а не во внутреннем представлении. Это ослабляет гипотезу
из раздела YFM ниже о том, что wysiwyg ожидает другой формат — по крайней мере **на чтение**
формат тот же. Поведение на запись не проверялось.

**Ещё одна поправка к отчёту:** `GET /v1/me` через `yw_raw_api_request` отвечает **404**, то есть
строка «Users → покрыто через raw_api_request» в таблице покрытия неверна. Метод либо имеет другой
путь, либо недоступен.

### Результаты проверки гипотез

Проверено на динамической таблице `7cd0e409-75d9-4c0a-bbd0-505aab22a042` (страница `.../test`,
id `50149981`).

**Дефект №2 (`row_id`) — подтверждён, но серьёзность НИЖЕ заявленной.**
API отдаёт идентификатор строки как **строку**: `{"rows":[{"id":"1"},{"id":"2"}]}`. Схема
`yw_update_cells` требует `number`. Однако запись с `row_id: 1` (числом) **проходит успешно** —
API принимает число и возвращает в ответе `"row_id": "1"` строкой. То есть базовая операция не
заблокирована, как предполагал аудитор.

Реальный дефект — несогласованность чтение→запись: агент получает строку и обязан сам догадаться
сконвертировать её в число, иначе схема отклонит вызов. Пока идентификаторы числовые, это лишний
шаг; **на нечисловом идентификаторе запись станет недостижимой вовсе**. Правка та же —
`z.string()`, как в `remove-rows` и `move-rows`: API строку отдаёт сам, значит и примет.
Серьёзность: средняя, не высокая.

**Дефект №3 (`recovery_token`) — подтверждён полностью.**
Создана временная таблица, затем удалена через `yw_delete_grid`. Ответ содержит только `message`,
поля `recovery_token` нет. Тип `DeleteGridResult { recovery_token: string }`
(`delete-grid.operation.ts:3-5`) утверждает обязательное строковое поле, которого не существует;
`delete-grid.tool.ts:29` подставляет `undefined`, и оно молча выпадает при сериализации.
Пользователю ложный токен не показывается — но контракт лжёт разработчику, и любая логика,
полагающаяся на тип, сломается. Смягчающее обстоятельство: в отличие от `delete_page`, описание
инструмента `delete_grid` про восстановление ничего не обещает.

**Побочно: диагностика ошибок никуда не годится.** Попытка создать таблицу с `page_slug`,
указывающим на несуществующую страницу, вернула `Ошибка при создании таблицы: … Request failed
with status code 400` — без единого слова о причине. Это ровно то, что чинит пакет 1.1.D
(`errorsData` и разбор тела ошибки): сейчас агент при 400 не может понять, что именно не так.

**Не проверено:** примет ли API `row_id` строкой (наш инструмент не даёт передать строку, а
`raw_api_request` только GET). Проверяется одним curl с методом POST.

## Специфика Yandex Flavored Markdown (YFM)

**Наблюдение по коду (не по доке):** ни в одном файле `src/wiki_api/**` или `src/tools/**` нет логики парсинга/трансформации Markdown — весь `content` идёт как непрозрачная строка `z.string()` от tool-параметра через DTO прямо в тело HTTP-запроса (`create-page.operation.ts:17`, `update-page.operation.ts:26-29`, `append-content.operation.ts:23-26`) и обратно как `unknown`/строка в `PageWithUnknownFields.content` при чтении. Это значит: **наш код не может испортить YFM-разметку сам по себе** — риск потери/порчи целиком на стороне того, что именно передаёт вызывающий агент, и на стороне того, как Wiki API интерпретирует эту строку.

Отсюда вытекают конкретные риски, не про наш парсинг, а про контракт:

1. **Тип страницы vs формат содержимого.** `page_type` у нас — `'page' | 'grid' | 'cloud_page' | 'wysiwyg' | 'template'` (`page.entity.ts:6`), но `content` в схеме `yw_create_page` — один и тот же `string` независимо от `page_type`. Документация явно указывает, что старый редактор и текущий YFM — разные форматы разметки одной и той же вики; официальная страница про markup («static-markup») сама помечена как описание **старого редактора**, актуальная страница про синтаксис не найдена в проверенных источниках. **Гипотеза (не факт):** для `page_type: 'wysiwyg'` контент, скорее всего, ожидается не как YFM-markdown, а в другом внутреннем представлении — наш tool не предупреждает и не валидирует это, просто отправит любую строку. Проверить можно только созданием реальной wysiwyg-страницы через `yw_create_page` и сверкой с тем, что показывает веб-интерфейс.
2. **`grid_format`/`rich_text_format` (`'yfm' | 'wom' | 'plain'`)** — у таблиц (grids) явно есть параметр формата текста ячеек (`grid.entity.ts:19`, `TextFormat`). У страниц (`page.entity.ts`) аналогичного явного поля формата нет — то есть для grids Wiki API признаёт минимум 3 диалекта разметки текста, а для обычных страниц формат в наших типах никак не специфицируется. Не проверено, что произойдёт при записи YFM-специфичных конструкций (каты, табы, `{% note %}`) в `wom`/`plain`-таблицу — вероятно, будут либо экранированы, либо интерпретированы буквально.
3. **Общий YFM-синтаксис (по generic-документации Diplodoc/YFM, не Wiki-специфичной):** блоки типа `{% note %}`, каты/табы, многострочные таблицы, вставки медиа, блоки кода, переменные (`{{var}}`) — всё это символьные последовательности внутри той же строки `content`. Наш код не экранирует и не проверяет их синтаксическую валидность перед отправкой — если агент сформирует битую конструкцию (незакрытый `{% note %}` или таб), мы отправим её как есть, и на стороне Wiki она либо будет показана как есть (сломанный блок), либо просто не отрендерится корректно. Это риск для пользователя данных, а не баг нашего кода — но стоит писать в промпт агента как предупреждение.
4. **Обратное чтение.** `GET /pages` по документации **не возвращает `content` без явного `fields=content`** (см. цитату в «Дефекты», п. про `pages__get_page_details.md`). Наш `yw_get_page`/`yw_get_page_by_id` корректно прокидывают этот параметр (`fields: WikiFieldsSchema`) — то есть YFM-текст не портится при чтении, но по умолчанию его просто не будет в ответе, и агент должен явно об этом знать.

Итог: сама транспортировка контента у нас «прозрачная» (плюс), но нет ни одной проверки/подсказки про совместимость `page_type`/`grid_format` с реальным форматом строки — риск полностью смещён на вызывающего агента и на недокументированное поведение Wiki API для «неправильных» комбинаций.

## Дефекты и неполнота существующих реализаций

Найдено кодовым ревью существующих (уже помеченных «реализовано»/«частично») инструментов. Каждая строка — либо подтверждённый факт (код + прямая цитата доки), либо явно помеченная ГИПОТЕЗА.

## Сомнительные и рискованные

- **Upload Sessions (MS365 cloud_page).** Реализовывать не стоит без явного запроса: это протокол multipart-загрузки под `cloud_page` (docx/pptx/xlsx через MS365-интеграцию), нишевая функциональность, не связанная с обычным ведением текстовой/табличной документации. Высокая цена реализации (6 методов, сессии с состоянием, дедлайны загрузки) при низкой вероятности использования командой, которая пишет обычные wiki-страницы и таблицы.
- **Comments — автоматическая запись от имени ИИ-агента.** Даже если реализовать, стоит явно решить (не в коде, а в процессе), должен ли агент оставлять комментарии от имени пользователя без подтверждения — это менее обратимое действие, чем правка страницы (у страницы есть `recovery_token`, у комментария — не факт).
- **Recover Page By Token без сопутствующего listing.** Добавлять `recover_page_by_token` изолированно, не имея способа посмотреть, что вообще было удалено (нет endpoint'а «список recovery-токенов» в документации), даёт tool, которым нельзя пользоваться без внешнего журнала токенов — сначала стоит проверить, действительно ли токен нигде не перечисляется.
- **`filter`/`sort`/`only_cols`/`only_rows` у `yw_get_grid`** (`src/wiki_api/api_operations/grid/get-grid.operation.ts:9-16`) принимаются как произвольные строки без валидации синтаксиса — если это DSL Wiki API (не проверено доком), стоит перед доработкой убедиться, что синтаксис вообще стабилен и документирован, а не reverse-engineered.

## Принятые решения и допущения

- Документация читалась через WebFetch (модель-суммаризатор), а не как сырой markdown — там, где это меняло вывод (HTTP-глагол update_grid/update_cells), результат перепроверен detail-страницей конкретного метода, а не взят из суммаризации индекса.
- Категории API взяты из структуры официального индекса (`pages`, `attachments`, `pages_access`, `pagesresources`, `comments`, `grids`, `users`, `upload_sessions`, `operations`, `recovery_tokens`, `search`), а не придуманы заново — так проще сверять с будущими обновлениями доки.
- «Покрыто через raw_api_request» проставлено только там, где: (а) tool для этого не реализован, и (б) метод в документации — GET. Там, где метод — не GET, статус оставлен «не реализовано» без пометки про raw, чтобы не создавать ложное впечатление обходного пути.
- Раздел «Дефекты» ограничен методами, которые у нас уже реализованы (`реализовано`/`частично` в таблице покрытия) — по прямому запросу задачи, а не по всей поверхности API.
- Глубина проверки YFM — на уровне «что происходит с контентом в нашем коде» (транспортная прозрачность подтверждена чтением всех operation-файлов) плюс справочный обзор общего синтаксиса YFM; специфичный для текущего (не старого) редактора Wiki эталонный список макросов найти не удалось — официальная страница по markup явно помечена как документация старого редактора.

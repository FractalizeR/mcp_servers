# Этап 1. Дефекты текущей версии (sequential)

Не зависит ни от новой спеки, ни от SDK v2. Делается первым, потому что этап 2 правит те же точки.

Рабочее дерево: **основной чекаут**. Пакеты последовательные, один исполнитель.

## Пакет 1.1.A — фильтрация как граница доступа

**Проблема.** `tools/list` фильтрует набор, а `ToolRegistry.execute()`
(`packages/framework/core/src/tool-registry/tool-registry.ts:238-290`) достаёт инструмент из полной
карты `this.tools` без единой проверки. Скрытый или отключённый tool вызывается напрямую.

**Решение.** Один источник истины о доступности инструмента, применяемый в обеих точках.

Контракт (без реализации):

```
ToolAccessPolicy
  isVisible(toolName): boolean     // попадает ли в tools/list
  isCallable(toolName): boolean    // разрешён ли к исполнению
  denialReason(toolName): string   // текст для ответа клиенту
```

- `getDefinitionsByMode(...)` и `execute(...)` спрашивают **один и тот же** объект policy.
- Policy конструируется в composition root из конфигурации и передаётся в `ToolRegistry`.
- Отказ на исполнении возвращается как tool execution error (`isError: true`), а не как протокольная
  ошибка: модель должна суметь себя поправить.

**Граничные условия.**
- Инструмент отсутствует вовсе → текущее поведение с fuzzy-подсказкой сохраняется.
- Инструмент существует, но не разрешён → **не** раскрывать в тексте ошибки список доступных
  инструментов и не подсказывать похожие: это утечка карты сервера.
- Нормализация имени (снятие префикса сервера) выполняется **до** проверки policy, иначе
  `fr_yandex_tracker_x` и `x` разойдутся в решениях.

**Файлы:** `tool-registry.ts`, `tool-filter.service.ts`, новый файл policy, composition root каждого
из трёх серверов, тесты.

**DoD.**
- Тест: инструмент, отсутствующий в `tools/list`, при прямом `tools/call` получает отказ. Падает до фикса.
- Тест: имя с префиксом сервера и без него дают одинаковый вердикт policy.
- Тест: текст отказа не содержит имён других инструментов.
- `npm run validate:quiet` зелёный.

**Факт исполнения (пакет 1.1.A, принят).** Единство источника истины реализовано не одним объектом
policy в обеих точках, а одним **предикатом**: `ToolFilterService.matchesCategoryFilter` /
`isDisabledByFilter` — единственная реализация, вызываемая из `filterByCategories`,
`applyDisabledFilter` и `ConfiguredToolAccessPolicy`. `getDefinitionsByMode(...)` сохранил прежнюю
сигнатуру с call-time фильтрами (иначе ломались 3 contract-теста и потребовалась бы правка `server.ts`,
которая по плану принадлежит этапам 3-4). Оба входа в проде выводят фильтры из одного неизменяемого
`ServerConfig`. **Долг:** после того как этап 4.1.B заберёт проекцию `tools/list` в adapter, там
надлежит спрашивать тот же объект `accessPolicy`, а не параметры вызова — иначе расхождение снова
станет возможным. Записано как обязательный пункт пакета 4.1.B.

## Пакет 1.1.B — redaction логирования

**Проблема.** `tool-registry.ts:242` — `logger.debug('Параметры вызова:', params)`. В файловый лог
уезжают тексты комментариев, содержимое страниц Wiki, произвольные пользовательские данные.

**Решение.** Логировать форму вызова, а не его содержимое.

```
redactParams(params): object   // имена ключей + типы + размеры; значения — только по allow-list
```

- По умолчанию значение **не** попадает в лог ни для одного параметра.
- Allow-list задаётся на уровне метаданных инструмента (например, идентификаторы задач и очередей —
  безопасны и полезны для отладки).
- Строки заменяются на маркер с длиной, а не на префикс: префикс секрета — тоже секрет.

**Граничные условия.** Вложенные объекты и массивы; `undefined`/`null`; очень большие payload —
редактор не должен сам стать источником нагрузки.

**Файлы:** новый redaction-модуль в `packages/framework/core/src/tool-registry/`, `tool-registry.ts`,
метаданные инструментов трогаются **только** если решено заводить allow-list сразу (иначе — отдельным
пакетом в этапе 3).

**DoD.**
- Тест: вызов с параметром, содержащим заданную строку-маркер, не оставляет её ни в одном логе. Падает
  до фикса.
- Тест: имена параметров в логе сохранены — отладка не деградировала.

**Факт исполнения (пакет 1.1.B, принят).** Механизм `redactParams(params, { allowedKeys })` готов,
но **allow-list отложен**: поле метаданных инструмента не заводилось (`tools/base/tool-metadata.ts`
лежит вне набора файлов пакета, а заполнять его пришлось бы по всем 97 инструментам). Сейчас вызов
идёт с пустым allow-list — то есть в лог не раскрывается ни одно значение. **Долг этапа 3:** вместе
с проставлением annotations и outputSchema завести в метаданных поле allow-list и заполнить его
идентификаторами задач/очередей/страниц. До этого отладка по логам видит только форму вызова.
Редактор дополнительно режет длину даже разрешённых значений (500 символов) — защита от ошибочно
широкого allow-list в будущем.

## Пакет 1.1.C — повтор неидемпотентных POST

Найдено аудитом покрытия API (`inventory/table4-tracker-api-coverage.md`), верифицировано отдельно.

**Проблема.** `AxiosHttpClient.requestWithResponse` оборачивает в `retryHandler.executeWithRetry`
и GET, и POST (`packages/framework/infrastructure/src/http/client/axios-http-client.ts:105-124`),
а `ExponentialBackoffStrategy.shouldRetry` решает по одному лишь статус-коду и **не смотрит на
метод** (`exponential-backoff.strategy.ts:36-55`): повтор происходит на `NETWORK_ERROR`, 408, 429,
500, 502, 503, 504.

Значит при потере ответа на уже выполненный запрос — типичный `504` от шлюза — повтор создаёт
второй объект. Это касается **всех** неидемпотентных POST обоих серверов: создание задачи,
комментария, worklog, связи, страницы Вики, строки таблицы, и особенно массовых операций, где
повтор `bulk_move_issues` перемещает группу задач дважды.

**Почему это серьёзно.** Молча продублированная задача или дважды применённая массовая операция —
порча данных, которую постфактум трудно обнаружить и дорого разгребать.

**Решение.** Два уровня, оба нужны.

1. **Транспорт перестаёт повторять небезопасные методы вслепую.** Стратегия повтора должна знать
   метод запроса. GET повторяется как сейчас; POST — только когда вызывающий явно объявил запрос
   идемпотентным.

```
RetryPolicy
  isRetryable(method, statusCode, idempotencyDeclared): boolean
```

2. **Ключ идемпотентности там, где его поддерживает API.** У Трекера создание задачи принимает
   `unique`: референсный клиент генерирует его сам (`uuid4().hex`) и при конфликте на повторе
   находит уже созданную задачу вместо создания новой. Наш `create_issue` не отправляет его вовсе.

**Граничные условия.**
- `429` — особый случай: сервер сам просит повторить, и запрос при этом заведомо не выполнялся.
  Его повторять можно и для POST.
- Отключение повторов для POST увеличит число ошибок, доходящих до агента. Это правильно: лучше
  честная ошибка, чем тихий дубль. Текст ошибки должен подсказывать, что операция могла
  выполниться, и что стоит проверить перед повтором.

**Файлы:** `exponential-backoff.strategy.ts`, `axios-http-client.ts`, интерфейс retry-handler,
`create-issue.operation.ts` и его DTO, тесты framework.

**DoD.**
- Тест: POST, отвечающий `504`, не повторяется без явного объявления идемпотентности. Падает до фикса.
- Тест: GET на `504` повторяется как прежде.
- Тест: POST на `429` повторяется.
- Тест: `create_issue` отправляет `unique`; повтор с тем же ключом не создаёт вторую задачу.

## Пакет 1.1.E — добить поверхность повторов (заведён по итогам 1.1.C)

Пакет 1.1.C выполнен и принят, но вскрыл два факта, которых план не предусматривал. Оба означают,
что дефект «повтор неидемпотентного POST» закрыт **не полностью**, а один из них ещё и создал
регрессию отказоустойчивости.

**Факт 1. Read-only POST потеряли повтор.** Трекер использует POST для чтения: `_search` в
`find-issues.operation.ts` и, предположительно, другие поисковые ручки. Побочных эффектов у них нет,
но новая политика перестала повторять их на 5xx/сеть/таймаут — повторяется только `429`. План
принимал рост числа ошибок как правильную цену за отсутствие дублей, но эта цена уместна для
мутирующих запросов, а не для чтения: там повтор безопасен и был полезен.

**Решение.** Перечислить **все** места вызова POST в трёх серверах, разделить на читающие и
мутирующие, читающим проставить `idempotencyDeclared: true`. Перечисление — часть DoD: «поправили
find_issues» без списка остальных не принимается.

**Факт 2. TickTick фикс не получил.** `packages/servers/ticktick/src/ticktick_api/http/authenticated-http-client.ts` —
независимая копия HTTP-клиента, дергающая `RetryHandler` напрямую. Дефолт `{ method: 'get' }`,
введённый в 1.1.C ради совместимости, означает, что её POST повторяются вслепую, как и раньше.

**Решение.** Прокинуть метод и флаг идемпотентности в вызовы `RetryHandler` из клиента TickTick.
Отдельный вопрос — оправдана ли вторая копия HTTP-клиента вообще; сведение её с `AxiosHttpClient`
в этот этап **не входит**, это отдельное решение.

**Файлы:** POST-вызовы операций трёх серверов, `authenticated-http-client.ts` TickTick, их тесты.
Framework (`http/retry/**`, `http/client/**`) трогать не нужно — контракт уже есть.

**DoD.**
- В отчёте — полный список POST-вызовов трёх серверов с пометкой «читающий / мутирующий».
- Тест: читающий POST (`find_issues`) на `504` повторяется.
- Тест: мутирующий POST на `504` не повторяется (регрессионный, стоит после 1.1.C).
- Тест: POST клиента TickTick на `504` не повторяется без объявленной идемпотентности. Падает до фикса.

## Пакет 1.1.D — потеря `errorsData` при разборе ошибок API

`ErrorMapper.mapResponseError` читает только `errorMessages` и `errors`
(`packages/framework/infrastructure/src/http/error/error-mapper.ts:62-68`). Трекер возвращает ещё
`errorsData` — свежий референсный клиент (2026-08-10) специально начал его сохранять.

Содержимое поля не документировано, поэтому *что именно* теряется — гипотеза. Не гипотеза —
асимметрия: поле в ответе есть, до `ApiErrorClass` не доходит. Пробросить его в ошибку и в лог
(с учётом redaction из пакета 1.1.B) дёшево, а без него диагностика опирается на догадки.

**Факт исполнения (пакет 1.1.D, принят).** Проброс сделан в **обеих** ветках `ErrorMapper`, а не
только в названной планом (строки 62-68): `mapRateLimitError` (429) теряла поле по той же причине —
ранний `return` до общего разбора. Тип — рекурсивный `JsonValue`: референсный клиент
(`exceptions.py:76`) хранит поле как есть, схема не документирована, гарантии «это всегда объект»
нет. В лог значение не пишется вовсе: `Logger.error()` по конструкции извлекает из ошибки только
`message/stack/name`, и это закреплено тестом-регрессией, а не оставлено как «и так работает».
Полное значение доступно через объект ошибки и `toJSON()`, то есть доходит до MCP-клиента.

## Риски этапа

- Policy — новая точка в горячем пути каждого вызова. Держать её без I/O и без асинхронности.
- Соблазн заодно ввести read-only профиль. **Не в этом этапе:** профиль — продуктовое решение, а
  инфраструктура для него здесь как раз и создаётся.

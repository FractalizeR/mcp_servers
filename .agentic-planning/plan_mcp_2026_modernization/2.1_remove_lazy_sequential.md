# Этап 2. Удаление lazy discovery (sequential)

Зависит от этапа 1 (правит те же точки в `ToolRegistry`).

Рабочее дерево: **основной чекаут**. Пакеты идут последовательно — они делят `tool-registry.ts`,
конфигурацию и документацию, изолировать их по файлам не получается.

**Обоснование.** Основной потребитель — готовый продукт (Claude Code, Claude Desktop, Codex), в
котором поиск инструментов уже реализован на стороне клиента. Дублировать progressive disclosure на
стороне сервера незачем.

**Перечисление.** Пересобрано оркестратором 2026-08-14 перед стартом этапа: **101 файл поверхности**
(102 хита минус один ложный — слово «essential» в комментарии `.serena/project.yml`), а не 82, как
в исходном артефакте. Старый список — строгое подмножество нового; разбор пропаж и команда пересборки
дописаны в конец `inventory/table1-lazy-surface.md`, снимок списка — `inventory/table1-lazy-surface-files-2026-08-14.txt`.

Расхождение возникло не из-за изменений кода, а из-за способа сбора: исходный grep был
регистрозависимым и полно покрывал только Трекер. У Вики и TickTick пропущены ровно те же по смыслу
файлы, что у Трекера учтены: `package.json`, `vitest.config.ts` (алиасы на исходники пакета),
`generated-index.ts`, `scripts/generate-tool-index.ts`, `tests/smoke/tool-search.smoke.test.ts`.

**Отдельно важное:** пропущен `.github/workflows/release.yml` — `@fractalizer/mcp-search` числится
там в списке публикуемых пакетов. Без правки этого файла релизный пайплайн после удаления пакета
сломается, и вскроется это не на валидации, а на релизе.

Способ по-прежнему не видит пользовательские конфиги вне репозитория и README уже опубликованных
версий на npmjs — эти два канала правятся вручную и в DoD не входят.

## Пакет 2.1.A — выключение режима

- Убрать `toolDiscoveryMode` и `essentialTools` из конфигурации всех трёх серверов и из `ServerConfig`.
- `tools/list` всегда отдаёт полный набор, прошедший policy из этапа 1.
- Убрать переопределение essential-набора в `main()` каждого сервера (`server.ts`, ~строки 190-200).
- Env-переменные `TOOL_DISCOVERY_MODE` / `ESSENTIAL_TOOLS` удалить, а не оставить no-op: молчаливо
  игнорируемая переменная хуже отсутствующей, потому что выглядит работающей.

**Граничное условие.** У пользователей эти переменные уже прописаны в конфигах клиентов. Сервер при
старте должен **явно предупредить** в stderr, что переменная больше не поддерживается, и продолжить
работу, а не падать.

## Пакет 2.1.B — единственный рубильник

- `DISABLED_TOOL_GROUPS` остаётся, значение по умолчанию — пустое, то есть не отключается ничего.
- `ENABLED_TOOL_CATEGORIES` (уже помечен `@deprecated`) удалить вместе с логикой позитивного фильтра
  и разрешением конфликта приоритетов между двумя фильтрами.
- Рубильник обязан проходить через ту же policy этапа 1 — то есть отключённая группа не только
  скрывается, но и не вызывается.

**Граничное условие.** Пустая строка, неизвестное имя группы, опечатка. Неизвестная группа — предупреждение
в stderr с перечнем допустимых значений, не молчание и не падение.

## Пакет 2.1.C — удаление пакета `search`

- Удалить `packages/framework/search/` целиком.
- Удалить `src/tools/generated-index.ts` во всех трёх серверах, `scripts/generate-tool-index.ts`,
  скрипт `generate:index` и шаг валидации, который его проверяет.
- Снять зависимость `@fractalizer/mcp-search` из `package.json` серверов, убрать из `.dependency-cruiser.cjs`,
  `knip.json`, `turbo.json` (если фигурирует), из графа зависимостей в `CLAUDE.md` и `ARCHITECTURE.md`.
- Удалить `SearchToolsTool` из composition root каждого сервера (`bindSearchToolsTool`, ветка lazy,
  `registerToolFromContainer('SearchToolsTool')`) и вернуть регистрацию инструментов к единому пути.
- Тесты, перечисленные в таблице 1 (smoke `tool-search`, интеграционные и unit по search) — удалить,
  а не оставлять пропущенными.

**Важно.** Пакет опубликован в npm. После мержа — `npm deprecate` с указанием причины и версии, начиная
с которой он не нужен. Тихое исчезновение пакета ломает тех, кто на него сослался напрямую.

**Открытый вопрос к исполнению:** `ToolCategory` живёт в `mcp-core`, а не в `search` — проверить, что
удаление пакета не утащило за собой типы, которые используются в метаданных инструментов. Если утащило,
типы переезжают в core, и это отдельное решение, а не побочный эффект удаления.

## Пакет 2.1.D — детерминированный порядок

Спека 2026-07-28 требует (SHOULD) стабильный порядок `tools/list` — под кеш на стороне клиента и
prompt-cache модели. Сортировка `sortByPriority` уже есть, но контрактом не является.

- Зафиксировать порядок как контракт: при неизменном наборе инструментов два последовательных
  `tools/list` возвращают побайтово одинаковый список.
- Сортировка должна быть **полной**: приоритет как первый ключ, имя как обязательный tie-breaker.
  Иначе порядок внутри одного приоритета зависит от порядка регистрации в DI.

## Пакет 2.1.F — проверка размера корневой документации не работает

Найдено пакетом 2.1.E при попытке доказать зелёный `validate:docs`.

**Проблема.** `scripts/validate-docs-size.ts` проверяет корневые документы (`CLAUDE.md`,
`ARCHITECTURE.md`, `README.md` Трекера, `tests/README.md`) только при условии
`cwd === monorepoRoot`. В пайплайне (`scripts/validate.sh` → `turbo run validate:docs`) turbo
запускает задачу с `cwd`, равным директории каждого пакета, — то есть условие не выполняется
никогда. Отдельный скрипт `validate:docs:root` делает настоящую проверку, но не подключён ни к
`validate.sh`, ни к `turbo.json`.

**Почему это стоит чинить.** Лимиты размера документации объявлены в `CLAUDE.md` как жёсткие (MUST)
и опираются на машинную проверку. Проверка, которая всегда возвращает успех, — худший вид отказа:
правило выглядит соблюдаемым, потому что никто его не измеряет. На момент находки фактические
размеры под лимитами (`CLAUDE.md` 392/400, `ARCHITECTURE.md` 678/700, README Трекера 598/600), то
есть запас практически исчерпан и первое же нарушение пройдёт молча.

**Решение.** Подключить корневую проверку к пайплайну — либо шагом в `validate.sh` рядом с
`turbo run validate:docs`, либо задачей turbo, запускаемой из корня. Дефект существовал до этого
плана; чинится здесь, потому что здесь он найден и здесь же документация правится массово.

**Файлы:** `scripts/validate-docs-size.ts`, `scripts/validate.sh`, `turbo.json`, корневой
`package.json`.

**DoD.** Искусственное превышение лимита в корневом `CLAUDE.md` роняет `npm run validate:quiet`.
Проверяется временной правкой с последующим возвратом, а не рассуждением.

## DoD этапа

- `grep -rn "toolDiscoveryMode\|essentialTools\|search_tools\|mcp-search" --exclude-dir=node_modules --exclude-dir=dist`
  по репозиторию не находит ничего, кроме исторических упоминаний в этом плане, в аналитическом
  документе `MCP_2026_07_28_ANALYSIS.md` и в каталоге `results/` (снимок метрик от 2025-11-21,
  зафиксированный в истории; это отчёт о прошлом состоянии, править его — переписывать замер).
- `npm run validate:quiet` зелёный, включая `depcruise` и `knip`.
- `tools/list` каждого сервера возвращает полный набор инструментов; smoke-тест это проверяет.
- Два последовательных `tools/list` дают идентичный результат.
- Отключённая через `DISABLED_TOOL_GROUPS` группа не вызывается напрямую (тест из этапа 1 расширен).

## Риски

- Самый большой пакет плана по числу файлов. Соблазн делать «заодно» правки в соседнем коде — не делать:
  любой не относящийся к удалению рефакторинг уедет в отдельный коммит.
- `knip` после удаления пакета может вскрыть цепочку теперь-неиспользуемых экспортов в `core`. Это
  ожидаемо; чистить в этом же этапе, но отдельным коммитом.

# Этап 4. Dual-era транспорт (sequential)

Зависит от этапа 2. С этапом 3 по файлам не пересекается (кроме проекции `tools/list`, которая по
решению этапа 3 переезжает в framework — см. пакет 3.1.B).

Рабочее дерево: **основной чекаут**, пакеты последовательные.

**Перечисление.** `inventory/table3-protocol-surface.md` — все точки, где формируется MCP-ответ.
Пересобрать перед стартом. Способ не покрывает поведение, реализованное внутри самого SDK.

Асимметрия, которую надо учесть: `server/handlers.ts` есть у Трекера и TickTick, у **Вики его нет** —
её `server.ts` содержит логику хендлеров внутри себя.

## Почему это не «просто version bump»

`Server` + `StdioServerTransport` из SDK v1 говорят только на 2025-эпохе. Обновление версии пакета
не меняет ничего на wire. Modern-протокол включается явным входом `serveStdio(factory)`.

## Почему legacy остаётся навсегда

Codex CLI с `v0.147.0` поддерживает 2026-07-28 **опционально**: по умолчанию открывает соединение
через `initialize`, а для stdio требует `CODEX_MCP_PROTOCOL_VERSION=2026-07-28`. Пока это так,
`legacy: 'reject'` не используем.

## Пакет 4.1.A — миграция на SDK v2

- Перевести `@modelcontextprotocol/sdk` на v2 (модульные пакеты) в `core` и трёх серверах.
- На этом шаге поведение на wire не меняется — только компиляция и тесты зелёные.
- Отдельный коммит: смешивать миграцию SDK с изменением протокола нельзя, иначе при регрессии
  непонятно, что её вызвало.

Ссылки: [upgrade-to-v2](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/migration/upgrade-to-v2.md),
[support-2026-07-28](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/migration/support-2026-07-28.md).

## Пакет 4.1.B — общий adapter

Вынести lifecycle и transport из трёх почти одинаковых `server.ts` в framework.

```
createMcpServerAdapter({
  serverName, version, icons,      // идентичность
  toolRegistry, accessPolicy,      // из этапов 1-3
  logger
}): { start(): Promise<void> }
```

Владельцем протокольных полей становится adapter, а не инструменты:

- `resultType` на каждом результате;
- `io.modelcontextprotocol/serverInfo` в `_meta` каждого результата;
- `ttlMs` и `cacheScope` на `tools/list`;
- детерминированный порядок списка (контракт из пакета 2.1.D).

**Кеш — консервативно:** `cacheScope: "private"` и короткий TTL. `public` означает, что ответ может
кешировать общий посредник; для нас это неверно, потому что набор инструментов зависит от
конфигурации конкретной установки.

Три `server.ts` после этого содержат только сборку контейнера и вызов adapter. Логика хендлеров Вики
переезжает в adapter вместе с остальными — асимметрия исчезает.

## Пакет 4.1.C — обе эпохи

- Вход `serveStdio(() => buildServer())`. Одна фабрика пинится на соединение, эпоха выбирается
  рукопожатием.
- Legacy `initialize` — как сейчас, но версия больше не хардкодится строкой в трёх местах.
- Modern: `server/discover` (**MUST** по спеке), `_meta` на каждом запросе, идентичность читается из
  `ctx.mcpReq.envelope`, а не из `initialize`.
- Неподдерживаемая версия → `-32022 UnsupportedProtocolVersion` со списком поддерживаемых.
- Уровень логирования — per-request из `io.modelcontextprotocol/logLevel`. Сервер **MUST NOT** слать
  `notifications/message` для запросов без этого поля. Наше логирование в Pino/stderr это не затрагивает
  и остаётся как есть — спека прямо рекомендует stderr взамен deprecated MCP Logging.

**Не реализуем:** `subscriptions/listen`, MRTR, Tasks, resumability. Первое и последнее относятся к
HTTP-транспорту, которого у нас нет; MRTR и Tasks — предмет более поздних этапов, если понадобятся.

## Пакет 4.1.D — raw-wire тесты

Тесты, разговаривающие с сервером байтами по stdio, а не через внутренние API. По одному набору на
каждый из трёх серверов:

1. Legacy: `initialize` → `tools/list` → `tools/call` работает как сейчас.
2. Modern: `server/discover` возвращает версии, capabilities и идентичность.
3. Modern: запрос без обязательных полей `_meta` → `-32602`.
4. Неподдерживаемая версия → `-32022` со списком поддерживаемых.
5. Каждый успешный результат содержит `resultType` и `serverInfo` в `_meta`.
6. `tools/list` содержит `ttlMs` и `cacheScope`.
7. Два последовательных `tools/list` побайтово идентичны.
8. **Один и тот же `tools/call` в обеих эпохах даёт одинаковый результат** — главный тест этапа.
9. Отказ policy (этап 1) одинаков в обеих эпохах.

## Риски

- SDK v2 — новая для нас поверхность; часть API может отличаться от документации. Пакет 4.1.A
  специально отделён, чтобы это вскрылось до изменений протокола.
- Ручная проверка в реальных клиентах обязательна: raw-wire тесты проверяют соответствие нашему
  пониманию спеки, а не совместимость с конкретной реализацией клиента.

# Этап 7.1. Дефекты существующих инструментов (parallel)

Зависит от этапа 3: исправленные инструменты должны сразу получать `outputSchema` и annotations,
иначе их придётся переделывать дважды.

Источники: `inventory/table4-tracker-api-coverage.md`, `inventory/table5-wiki-api-coverage.md`.
Сквозные инфраструктурные дефекты (повтор POST, `errorsData`) вынесены в этап 1 — здесь только
то, что чинится внутри конкретного сервера.

Рабочее дерево: **основной чекаут**, два пакета по серверам, наборы файлов не пересекаются.

## Что проверить до начала

Часть находок помечена аудиторами как гипотезы: они выведены из кода и документации, но не
наблюдались на живом API. Их надо подтвердить **до** правки — иначе есть риск чинить то, что
работает, и не починить то, что сломано.

| Гипотеза | Статус |
|---|---|
| `update_issue` с `status` возвращает ошибку либо молча игнорирует параметр | **проверено 2026-08-14: подтверждено — API отвергает** |
| `yw_update_cells` не принимает `row_id` из ответа `yw_get_grid` | **проверено 2026-08-14: подтверждено частично, серьёзность понижена** |
| `yw_delete_grid` не получает `recovery_token` | **проверено 2026-08-14: подтверждено** |

Подробности проверки — в `inventory/table5-wiki-api-coverage.md`, раздел «Результаты проверки
гипотез». Кратко: API отдаёт `row_id` строкой, но принимает и число, поэтому запись не заблокирована
— дефект в несогласованности чтение→запись, а не в невозможности вызова; `recovery_token` при
удалении таблицы действительно не возвращается, тип операции лжёт.

**Результат проверки `update_issue.status`** (живой запрос к API, тестовая задача):

```
HTTP 422
{"errorMessages":["Поля [status] только для чтения."],"errors":{},"errorsData":{}}
статус до: cancelled   статус после: cancelled
```

Параметр отвергается сервером с внятным сообщением. Данные не портятся, молчаливого игнорирования
нет — то есть **серьёзность ниже заявленной аудитором «высокой»**: это не ложное впечатление успеха,
а мёртвый параметр, который гарантированно тратит вызов впустую и вводит модель в заблуждение самим
фактом присутствия в схеме. Итоговая оценка — средняя. Правка прежняя: убрать `status` из схемы,
DTO и операции, а в описании инструмента направить на `transition_issue`.

**Побочно подтверждено для пакета 1.1.D:** поле `errorsData` действительно присутствует в теле
ошибки Трекера (здесь пустым объектом). Значит `ErrorMapper`, читающий только `errorMessages` и
`errors`, игнорирует существующее поле, а не гипотетическое. Насколько содержательным оно бывает —
по-прежнему неизвестно; на этом классе ошибок оно пустое.

**Побочное наблюдение по retry:** код ответа `422` не входит в список повторяемых
(`exponential-backoff.strategy.ts`), поэтому такой запрос не ретраится. Это верное поведение —
менять при работе над пакетом 1.1.C не нужно.

## Пакет 7.1.A — Yandex Tracker

| Дефект | Где | Суть |
|---|---|---|
| `status` в `update_issue` | `update-issue.schema.ts:43-45`, `update-issue.dto.ts:23-24`, `update-issue.tool.ts:74` | Параметр объявлен и уходит в `PATCH /v3/issues/{key}`. **Проверено живым запросом: API отвечает `422` — «Поля [status] только для чтения».** Правильный путь уже реализован — `transition_issue` |
| `add_comment` без упоминаний | `add-comment.schema.ts:21-38` | Нет `summonees`, `maillistSummonees`, `markupType`, `isAddToFollowers`. Агент физически не может упомянуть коллегу — это не неудобство, а отсутствующий сценарий |
| `bulk_move_issues` без `initialStatus` | `bulk-move-input.dto.ts:23-60`, `bulk-move-issues.schema.ts:22-53`, `bulk-move-issues.operation.ts:57-72` | При переносе в очередь с другим workflow задача остаётся в статусе, которого там нет |
| `update_issue` без оптимистической блокировки | `update-issue.operation.ts:39-42` | Нет `version`; параллельные правки молча затирают друг друга. Референсный клиент шлёт версию в `If-Match` |

**Решения, требующие выбора.** Для `status` в `update_issue` вариантов два: убрать параметр совсем
или перенаправлять его внутрь на `transition_issue`. Первое честнее и проще; второе удобнее для
агента, но прячет разницу между изменением поля и переходом по workflow, и на неоднозначном
переходе всё равно потребует уточнения. Рекомендация — убрать, а в описании инструмента назвать
правильный путь. Исполнитель вправе решить иначе, назвав причину.

Проверка дала аргумент в пользу «убрать»: сервер отвечает не общей ошибкой валидации, а точным
сообщением про поле только для чтения. Значит достаточно, чтобы описание инструмента направляло
на `transition_issue` — модель разберётся без внутренней магии перенаправления.

**Факты исполнения (пакет 7.1.A, принят).**

- `status` **убран**, как рекомендовал план. Описание инструмента упирается в лимит 80 символов,
  поэтому подробное объяснение («API отклоняет статус как read-only при PATCH, используй
  `transition_issue`») вынесено в `.describe()` схемы — оно попадает в JSON Schema без лимита.
- `add_comment`: `summonees`, `maillistSummonees`, `markupType` уходят в тело, как в референсном
  клиенте. `isAddToFollowers` реализован query-параметром — в референсе его нет вовсе, подтверждение
  нашлось только в текстовом описании документации. Заодно введён единый тип элемента batch: именно
  рассинхрон его формы на трёх слоях и убивал поля раньше.
- **Оптимистическая блокировка сделана query-параметром `?version=N`, а не заголовком `If-Match`** —
  отклонение от буквы плана. Две причины, обе весомые: `IHttpClient.patch()` не умеет заголовки, а
  сам интерфейс лежит вне набора файлов пакета; и референсный клиент помечает заголовочный путь
  комментарием «XXX: API does not always respect If-Match header :(». Query-параметр задокументирован
  в актуальном `api-ref` и имеет ту же семантику. Принято.
- **Общая машинная проверка сделана и работает.** Тест обходит реестр, генерирует по Zod-схеме
  полностью заполненный набор параметров с уникальными маркерами и шпионит на всех методах HTTP-клиента,
  проверяя, что каждый маркер долетел до пути, тела или query. 28 пишущих инструментов покрыты; три
  вложенческих исключены с названной причиной — они обходят `IHttpClient` через прямой multipart.
  Новых находок сверх четырёх известных тест не дал, но все четыре подтверждает при откате.
  Отдельно доработан случай булевых полей: подстрочный поиск голого `true` не отличает «поле дошло»
  от «где-то в JSON есть true», поэтому проверяется конкретная пара ключ-значение.

## Решение по grid-инструментам: заморозка

Установлено проверкой на живом API и подтверждено заказчиком: **динамические таблицы у команды
почти не используются**, а то, что выглядит таблицей на страницах, — YFM-разметка `#| … |#` внутри
`content`. Двенадцать grid-инструментов обслуживают сценарий, которого в работе почти нет.

Удалять их не нужно — «почти не используются» не равно «не используются». Но и развивать не нужно.
Режим — заморозка:

- **Чиним только корректность**, и только дёшево: `recovery_token` (убрать несуществующее поле из
  типа и из ответа), `row_id` (сменить на строку). Оба — правки в одну строку.
- **Не добавляем** новых grid-возможностей, не тратим на них классификацию annotations сверх
  минимальной, не делаем для них Resources и ResourceLink.
- **Пересмотреть** после того, как заработают контентные сценарии: если спрос не появится, следующий
  шаг — не доработка, а вывод из эксплуатации с предупреждением в описании инструментов.

## Пакет 7.1.D — защита разметки при правке контента

Это то, что «не ломать» означает на практике. Настоящий риск не в grid-инструментах, а в
контентных: `update_page` и `append_content` переписывают `content` целиком, а внутри него живут
таблицы приёмки задач, ссылки на тикеты и остальная YFM-разметка. Агент, переписывающий страницу
«по смыслу», ломает её молча и необратимо — `recovery_token` есть только у удаления страницы, а не
у перезаписи.

Три меры, по возрастанию цены:

1. **Diff перед сохранением обязателен.** Инструмент из пакета 3.1.E перестаёт быть удобством и
   становится обязательным шагом флоу: сначала показать разницу, потом писать. В описании
   `update_page` это должно быть сказано прямо, чтобы модель шла этим путём сама.
2. **Предупреждение о структурной разметке.** Если в текущем содержимом есть конструкции YFM
   (`#| … |#`, `{% … %}`, вставки), а новое содержимое их теряет или изменяет их число — инструмент
   обязан сказать об этом в ответе, а не молча записать. Считаем конструкции до и после;
   расхождение — сигнал.
3. **Полная перезапись требует явного намерения.** Обсуждаемо: сделать так, чтобы замена всего
   содержимого страницы отличалась от точечной правки отдельным параметром. Решение отложено до
   реализации — сначала надо посмотреть, как часто мера 2 срабатывает на практике.

**Граничные условия.** Проверка структурной разметки не должна превратиться в парсер YFM — это
подсчёт маркеров, а не разбор синтаксиса. Ложное срабатывание дешевле пропуска: лучше лишний раз
предупредить, чем потерять таблицу спринта.

**DoD пакета.** Тест: правка страницы, содержащей таблицу `#| … |#`, при которой таблица исчезает
из нового содержимого, возвращает предупреждение. Тест: правка, не затрагивающая разметку,
предупреждения не даёт.

## Пакет 7.1.C — контракт формата содержимого Вики

Не дефект кода, а отсутствующая проверка. `content` идёт непрозрачной строкой от параметра
инструмента до тела запроса — наш код разметку не портит, но и не проверяет, что формат строки
соответствует `page_type`. Для `page_type: 'wysiwyg'` содержимое, предположительно, ожидается не в
YFM — гипотеза, проверяется созданием такой страницы и сверкой с веб-интерфейсом.

Минимум, который стоит сделать независимо от результата проверки: назвать в описании инструмента,
какой формат ожидается для каждого `page_type` и `grid_format`, чтобы агент не выбирал наугад.
Здесь же — инструмент diff перед сохранением из пакета 3.1.E.

## Пакет 7.1.E — свести проверку достижимости параметров во framework

Заведён по факту: пакеты 7.1.A и 7.1.B независимо друг от друга написали по своему тесту,
проверяющему одно и то же — что параметр, объявленный во входной схеме инструмента, реально доезжает
до HTTP-запроса. У Трекера это `tests/smoke/tool-params-reach-api.smoke.test.ts` плюс генератор
образцов по Zod-схеме, у Вики — `tests/smoke/schema-operation-reachability.smoke.test.ts`.

**Это третий случай за план,** когда изолированные исполнители изобретают одну вещь: до этого были
проекция полей определения инструмента (пакет 3.1.G) и хелпер envelope. Причина каждый раз одна —
общее место лежит во framework, а framework исполнителям запрещён, чтобы они не подрались за файл.
Вывод для будущих планов: если пакет по своей природе порождает общий механизм, его надо выносить
отдельным предваряющим пакетом, как это сделано с 3.1.F.

- Сравнить оба подхода, взять лучший (у Трекера генератор образцов умеет булевы поля — это тонкость,
  на которой первая версия его же теста ошибалась).
- Вынести генератор и сам обход во framework, оставив в серверах только список исключений с причиной.
- TickTick аудитом не покрывался и своего теста не имеет — после выноса он получает проверку даром,
  и это главный аргумент за вынос.

**DoD.** Генератор существует в одном экземпляре во framework; все три сервера проверяются им;
исключения перечислены явно и с причиной, а не молчаливым пропуском.

**Результат: вынос окупился сразу.** TickTick аудитом не покрывался и своего теста не имел —
подключение общей проверки нашло у него дефект, которого никто не искал.

## Пакет 7.1.F — `complete_task` у TickTick теряет `projectId`

Найдено пакетом 7.1.E, не исправлено: это предметный дефект сервера, а не тестовой оснастки.

`CompleteTaskOperation` шлёт `POST /task/{taskId}/complete` — `projectId` не доезжает ни в путь, ни
в тело. Соседние `GetTaskOperation` и `UpdateTaskOperation` при этом обе используют
`/project/{projectId}/task/{taskId}`, то есть форма пути у API именно такая, и `complete_task`
выбивается из неё в одиночку. Параметр объявлен в схеме инструмента и молча пропадает — ровно тот
класс дефектов, ради которого проверка и делалась.

Сейчас записан в тесте исключением с причиной «дефект, не чинится», чтобы прогон оставался зелёным
и при этом честным. Исключение снимается вместе с починкой.

**Отдельно проверено и дефектами НЕ является:** `status`, `query`, `priority`, `days` у
соответствующих инструментов TickTick фильтруются на нашей стороне после `getAllTasks()`, потому что
в TickTick Open API v1 серверной фильтрации по ним нет. Каждый случай подписан причиной в списке
исключений.

**DoD.** `complete_task` отправляет `projectId`; регрессионный тест падает до правки; исключение из
списка снято, а не оставлено «на всякий случай».

## DoD этапа

- Каждый дефект закрыт регрессионным тестом, падающим до правки.
- Гипотезы либо подтверждены и исправлены, либо опровергнуты — с записью результата проверки в
  соответствующей таблице инвентаря.
- Ни один инструмент не принимает параметр, который не доезжает до API: тест обходит реестр и
  сверяет поля схемы с тем, что реально отправляет операция.
- `npm run validate:quiet` зелёный.

## Риск

Последний пункт DoD — самый ценный и самый дорогой. Именно он превращает разовую починку в защиту
от повторения: оба сервера уже наступили на «параметр объявлен, но не отправляется» независимо друг
от друга. Если сделать проверку общей и машинной, класс дефектов закрывается целиком.

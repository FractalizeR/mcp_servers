# 3.1 — Живая приёмка, валидация, ревью (последовательно, последним)

Пять инструментов годами числились рабочими, потому что моки отвечали предписанным.
Поэтому закрытием пакета считается **вызов по боевому API**, а не зелёный тест.

## Почему один прогон, а не по прогону на пакет

Токен один и бьёт в боевой Трекер. Два процесса `mcp-dev --dangerously-allow-write`
мешают друг другу (`CLAUDE.md`, раздел mcp-dev), а журнал прогона подписан одной меткой
и чужой не принимает. Прогон ведёт оркестратор после сборки всех пакетов.

## Порядок

1. **Перегенерировать** `tests/live_scope/known-mutating-requests.ts` —
   `npm run enumerate:requests`. Таблица снимается с Zod-схем инструментов, а волна 2.x
   их и меняла: без этого шага рубеж тестируется на предположении о теле, а не на теле,
   которое инструмент шлёт. Расхождения перегенерации с ожиданиями этапа 1.1 разбираются
   поимённо, а не принимаются оптом.
2. `npm run validate` целиком (не `:quiet`) — CI не должен узнать о поломке первым.
3. Пересобрать бандл: `mcp-dev` отказывает на устаревшем относительно `src/**` бандле.
4. Прогон под рубежом. **Первым вызовом** — создание доски и чтение её по
   `GET /v3/boards/{id}`: на адресуемости `liveBoards` стоят пакеты 2.5 и 2.6, правило
   колонок в рубеже и сценарий со спринтом. Не подтвердилось — прогон останавливается. Переменные: `YANDEX_TRACKER_LIVE_SCOPE_QUEUE=TEST`,
   `..._JOURNAL`, `..._RUN_ID=live-2026-08-26`, `..._RUN_PREFIX=[live-2026-08-26]`,
   `..._DISPOSABLE_QUEUE=TESTTEST`, `..._RUN_OWNER=vr`.
5. Матрица прогона — по одному сценарию на дефект:

| Дефект | Что вызвать | Чем подтверждается |
|---|---|---|
| D1 | `create_component` в `TEST` | `get_components` показывает созданный компонент |
| D7 | `create_queue` (`TESTTEST`) | `get_queue` отдаёт очередь; следом `bulk_move_issues` `TEST → TESTTEST`, не закрытый прошлым прогоном |
| D8 | `create_project` | `get_project` по возвращённому id |
| D8-доп | `create_project` со `status` | форма статуса: пакет 2.3 оставил строчный enum (`draft`, `in_progress`, …) по типизации, снятой с боевых ответов, а документация называет `DRAFT|IN_PROGRESS|…`. Спор решается вызовом: строчная форма принята — схема верна; отвергнута — статус переводится в верхний регистр |
| D10 | `create_global_field` | `get_global_field` по возвращённому `id` |
| D10-доп | `update_global_field` на созданном поле | подозрение на шестой дефект того же рода: документация правки поля называет `name: {en, ru}`, а наша схема правки шлёт строку. Поле для проверки появляется впервые — до этого прогона правку было не на чем испытать |
| D9 | `create_board` с `queue` и `sprintsAvailable` | `get_board` показывает переданное имя и фильтр; `create_sprint` на этой доске проходит |
| D11 | две колонки с одинаковым `id` | `update_board_column` и `delete_board_column` **отказывают** |

6. Отдельно проверить, что `POST /v3/boards` отклоняется рубежом, а не выполняется.
7. Каждый эффект подтверждается **независимым чтением**, а не сообщением инструмента:
   именно рапорт об успехе с переданным именем скрыл D9.
8. **Уборки нет.** Созданное прогоном не удаляется: удаление боевых сущностей
   организации оставлено пользователю (решение 2026-08-26) — риск снести нужное выше
   пользы от автоматической уборки. Прогон вместо уборки перечисляет созданное поимённо,
   с идентификаторами и именами, чтобы пользователь убрал сам.

   Следствие, названное явно: инструменты удаления сущностей организации
   (`delete_global_field`, `delete_project`, `delete_board`) этим прогоном **не
   проверяются**. Правило «сначала проверь удаление» здесь неприменимо, и в отчёте это
   стоит отдельной строкой, а не молчанием.

## Definition of Done

- отчёт `3.2_LIVE_RUN_REPORT_<дата>.md` рядом с планом: по каждому дефекту — вызов,
  ответ, подтверждающее чтение; отдельными разделами — **всё созданное прогоном с
  идентификаторами** (убирает пользователь), непроверенные инструменты удаления и
  найденные новые дефекты;
- инструмент, не прошедший живьём, возвращается в свой пакет 2.x с уточнённым заданием;
  «доделать мелочь» оркестратором вместо возврата не делается;
- ревью изменений (`dvizh-vr-workflow:review`) после валидации — контрактов сломано
  пять, это не тот объём, который принимается без ревью;
- документация: `packages/servers/yandex-tracker/CLAUDE.md`,
  `src/tracker_api/api_operations/README.md`, `src/live_scope/README.md`,
  `tests/TESTING_STRATEGY.md` — там, где названы старые маршруты;
- коммиты по пакетам, на русском, по Conventional Commits со scope домена.

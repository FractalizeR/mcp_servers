# 1.1 — Рубеж под новые маршруты (последовательно, первым)

Без этого этапа живой прогон встанет: новые маршруты (`POST /v3/components`,
`POST /v3/liveBoards`) не описаны ни одним правилом, а рубеж fail-closed по построению.
Этап идёт один и первым, потому что трогает файлы, общие для всех пакетов 2.x.

## Набор файлов

`src/live_scope/`: `sandbox-queue-rules.ts`, `organization-rules.ts`, `rule-matching.ts`,
`live-scope.guard.ts`, `README.md`.
Тесты: `tests/live_scope/*`.

## Решения

### Компонент переезжает из очереди в организацию? — нет

`POST /v3/components` остаётся правилом песочной очереди: компонент по-прежнему
локализован в очереди, изменился только адрес. Очередь теперь читается **из тела**
(`body.queue`), а не из пути, и проверяется тем же `queueWithinScope`. Тело без
распознанной очереди — отказ (родитель не распознан), как у создания задачи.

Правило `/v[23]/queues/{q}/components` **удаляется**, а не остаётся «на всякий случай»:
маршрута нет в API, и живое правило на несуществующий путь маскирует регресс.
Состав тела компонента ограничивается перечнем `name, queue, description, lead, assignAuto`.

`createdEntityOf` в `live-scope.guard.ts`: детектор `/v[23]/queues/{q}/components`
заменяется на `/v3/components`. Иначе созданный компонент не попадёт в журнал и
собственная же правка отклонится.

### Доска: создание и правка разъезжаются по разным маршрутам

- создание — `POST /v3/liveBoards`;
- правка и удаление — `PATCH|DELETE /v3/boards/{id}` (не менялись).

Семейство `orgFamilyRules` для доски перестаёт быть симметричным: `createPattern`
указывает на `liveBoards`, `editPattern` — на `boards/{id}`, и **перечни допустимых
ключей у них разные**. Отсюда контракт `OrgFamily` дополняется **двумя** парами полей, а не одной:

- `createAllowedKeys` / `allowedKeys` — перечни ключей тела отдельно для создания и правки;
- `createViolation` (уже есть) / **`editViolation`** (добавляется) — проверки ссылок
  отдельно для создания и правки.

Второй пары не миновать: у доски ссылка на очередь при создании лежит в
`autoFilters...fieldValues.queue`, а при правке — в верхнеуровневом `queue`; у проекта
при создании это `queues`, при правке — `queueIds`. Общий `bodyViolation`, переписанный
под создание, молча снял бы проверку очереди с правки — это дыра, а не неудобство.

`POST /v3/boards` после этого не покрыт ни одним правилом и попадает в fail-closed —
это желаемое: устаревший маршрут молча игнорирует тело, и отказ рубежа честнее.

Очередь доски больше не поле верхнего уровня. `boardBodyViolation` при создании
достаёт ссылку из `autoFilters.addFilter.liveFilter.fieldValues.queue` — массива
элементов вида `{fixed: "TEST"}` — и требует, чтобы **каждый** элемент был очередью
области прогона. Форма, из которой очередь не распознана, при непустом `autoFilters` —
отказ. `autoFilters` нет вовсе — доска создаётся без привязки к очереди, это законно.

Ключи создания доски: `name, owner, boardPermissionsTemplate, backlogAvailable,
sprintsAvailable, columns, backlogColumns, nonParametrizedColumns, autoFilters`.
Ключи правки — прежний `BOARD_KEYS`.

`createdEntityOf`: детектор создания доски переводится с `/v3/boards` на `/v3/liveBoards`.

### Проект

Ключи **создания**: `name, queues, description, lead, status, startDate, endDate`.
Ключей `key`, `queueIds`, `teamUserIds` у `POST /v3/projects` нет — из перечня создания
они уходят.

Ключи **правки** остаются прежними, включая `queueIds` и `teamUserIds`: `update_project`
их реально шлёт (`update-project.tool.ts`), и снятие их из общего перечня отклонило бы
законную правку. Это ровно та ошибка, которую предотвращает раздельная пара перечней.

Проверка ссылок тоже раздельная: на создании — `queues` (одна ссылка, не массив) через
`queueRefWithinScope`, на правке — прежний `queueIds` через `queueRefsWithinScope` плюс
запрет непустого `teamUserIds`.

### Очередь

`QUEUE_KEYS` пополняется ключом `issueTypesConfig`. Внутрь него рубеж не смотрит:
ссылок на людей и на чужие сущности там нет (`issueType`, `workflow`, `resolutions` —
справочники организации), а общая проверка людей по всему телу и так рекурсивна.

### Глобальное поле

Ключи **создания**: `id, name, description, category, type, order, readonly, visible,
hidden, container, optionsProvider`. Ключа `schema` в запросе не существует.
Ключи **правки** — по факту `UpdateFieldDto` (пакет 2.4); перечни задаются раздельно
через `createAllowedKeys`/`allowedKeys`.

Префикс прогона проверяется у локализованного имени — `hasRunPrefix` уже требует
префикс в каждом непустом языке, менять его не нужно.

## Таблица известных мутирующих запросов

`tests/live_scope/known-mutating-requests.ts` **генерируется** скриптом
`npm run enumerate:requests` из Zod-схем инструментов. На этом этапе схемы ещё старые,
поэтому этап правит таблицу вручную только настолько, чтобы его собственные тесты были
осмысленны, а **перегенерация целиком — шаг этапа 3.1, после волны 2.x**. Иначе таблица
зафиксирует предположение о теле, а не то тело, которое инструмент шлёт, — и тесты
останутся зелёными при разъехавшемся контракте.

## Definition of Done

- `npm run test:quiet` в пакете сервера зелёный; тесты рубежа покрывают по каждому
  из пяти маршрутов: допуск законного тела, отказ по чужой очереди/чужому человеку,
  отказ по неизвестному ключу тела с его именем в тексте;
- `tests/live_scope/known-mutating-requests.ts` перечисляет новые маршруты, а старые
  (`POST /v3/queues/{q}/components`, `POST /v3/boards`) из него убраны — с пометкой, что
  таблица перегенерируется на 3.1;
- правка проекта (`PATCH /v3/projects/{id}` с `queueIds`) и правка доски
  (`PATCH /v3/boards/{id}` с `queue`) остаются разрешёнными — отдельными тестами, иначе
  раздельные перечни разъедутся незамеченными;
- `POST /v3/boards` отклоняется с причиной fail-closed — отдельным тестом;
- журнал пополняется по `POST /v3/components` и `POST /v3/liveBoards` — тест на
  `observeResponse`;
- `src/live_scope/README.md` описывает новую адресацию компонента и доски.

## Чего этап НЕ делает

Не трогает `src/tools/**`, `src/tracker_api/**` — это пакеты 2.x. Рубеж пишется под
контракты из `0_CONTRACTS.md`, а не под текущий код операций.

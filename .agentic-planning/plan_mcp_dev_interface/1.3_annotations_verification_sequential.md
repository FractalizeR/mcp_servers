# Пакет 1.3 — Семантическая верификация аннотаций (sequential)

**Зависит от:** 1.2
**Модель исполнителя:** средняя (нужна сверка семантики, а не только наличия полей).

## Цель

Инвентарь `inventory_tools_annotations.md` получен regex-парсом `*.metadata.ts` и проверяет
**наличие** хинтов. Механизму защиты записи этого мало: инструмент с `readOnlyHint: true`,
который на деле пишет, пройдёт такую проверку и обойдёт защиту. Пакет закрывает оба пробела —
слепые пятна способа получения и семантическую верность разметки.

## Набор файлов

- `packages/servers/{yandex-tracker,yandex-wiki,ticktick}/tests/**` — регрессионные тесты (по одному на сервер, рядом с проверяемыми метаданными)
- Постоянное место для инвентаря: `packages/framework/dev-client/README.md` или `docs`-раздел пакета
- `.agentic-planning/plan_mcp_dev_interface/inventory_tools_annotations.md` — обновление до переноса

**Почему тесты в серверах, а не во framework.** Тест, живущий в `dev-client`, но проверяющий три
сервера, не имеет импортов на них — depcruise промолчит, а turbo не выстроит порядок «сначала
собрать серверы, потом тестировать framework», и тест будет то зелёным, то красным по кэшу.

**Почему инвентарь переезжает.** Правила проекта требуют удалить папку плана после финальной
валидации. Верификационный артефакт, на который опирается защита записи, не должен умирать
вместе с планом.

## Что делаем

1. Снять фактический `tools/list` через `mcp-dev list --json` по каждому серверу — то есть через реальный протокол, а не по исходникам. Это закрывает слепые пятна статического парса: дефолты генератора definition, метаданные вне `*.metadata.ts`, расхождение «файл есть — регистрации нет».
2. Сверить состав имён и хинты с таблицей.
3. **Семантическая сверка:** для каждого инструмента с `readOnlyHint: true` проверить по коду, что он не пишет ни в удалённое окружение, ни на локальную ФС. Известная отправная точка — расхождение wiki (`download_attachment`, `readOnlyHint: true`, делает `writeFile`) против tracker (те же по смыслу инструменты помечены `false` после осознанной правки «пакет 3.1.G»).
4. Расхождения выписать поимённо с указанием канала, который их породил.

## Definition of Done

1. Состав из реального `tools/list` сверен с таблицей (ожидаемо 92 / 36 / 25), расхождения объяснены.
2. Каждый инструмент с `readOnlyHint: true` проверен по коду на отсутствие записи; список проверенных и найденных расхождений — в отчёте пакета.
3. Регрессионный тест заведён **безусловно** (а не «если расхождения найдены»): новый инструмент без явных `readOnlyHint`/`destructiveHint` роняет сборку своего сервера.
4. Строка «чем получено и чего этот способ не видит» обновлена: способов теперь три — статический парс, реальный `tools/list`, сверка по коду.
5. Инвентарь перенесён в постоянное место, ссылки поправлены.

## Уточнение набора файлов (зафиксировано оркестратором перед исполнением)

Постоянным местом инвентаря назначается **`packages/framework/dev-client/docs/tools-annotations-inventory.md`**,
а не `README.md` пакета. Причина механическая: `README.md` пакета входит в набор файлов пакета 2.4,
который идёт параллельно, — два агента писали бы в один файл и затёрли бы работу друг друга.
В README пакета инвентарь только упоминается ссылкой, и эту ссылку ставит 2.4, а не 1.3.

Итоговый набор файлов пакета 1.3:
- `packages/servers/{yandex-tracker,yandex-wiki,ticktick}/tests/**` — регрессионные тесты
- `packages/framework/dev-client/docs/tools-annotations-inventory.md` — новый, постоянное место инвентаря
- `.agentic-planning/plan_mcp_dev_interface/inventory_tools_annotations.md` — обновление до переноса

Файлы `package.json` и `CLAUDE.md` серверов — **вне** набора 1.3: они принадлежат пакетам 2.1–2.3.
Значит, `npm run tools:list` на момент 1.3 ещё не существует, и снимать реальный `tools/list` нужно
прямым вызовом бинарника `mcp-dev` с явными `--server-name` и `--package-dir`.

## Факт исполнения (пакет 1.3, зафиксировано оркестратором)

Пакет **сделан**, DoD 1–5 закрыты. Главный результат — **семантических расхождений между
`readOnlyHint` и фактическим поведением не найдено ни одного**.

Проверены все 69 инструментов с `readOnlyHint: true` (tracker 40, wiki 12, ticktick 17): ни один
не зовёт `httpClient.post/postWithResponse/patch/put/delete`, ни один файл в `tools/` не делает
`writeFile`/`createWriteStream`/`writeFileSync`, все `raw_api_request` заперты на GET дважды —
схемой (`z.literal('GET')`) и операцией (switch с default-throw).

**Предпосылка плана оказалась устаревшей.** План опирался на расхождение
`yandex-wiki / download_attachment` (`readOnlyHint: true` при фактическом `writeFile`) как на
живой пример. К моменту исполнения оно уже устранено коммитом `6a19b7ad`
(«fix(wiki): download_attachment помечен readOnlyHint: false»), лежавшим в истории ветки ещё до
старта работ. Подтверждено реальным `tools/list`: `yw_download_attachment → readOnly: false,
class: write`. На конструкцию плана это не влияет: правило `!== true` и третий класс
`local-side-effect` заведены не ради одного этого случая, а чтобы не опираться на аннотацию как на
единственный признак. Класс `local-side-effect` при этом не мёртв — реальный `tools/list` трекера
даёт 39 read / 52 write / **1 local-side-effect**.

**Состав сверен по реальному протоколу:** tracker 92/92, wiki 36/36. ticktick — `notConnected`
(на машине не подключён), для него сверка сделана статически по коду, и это честно названо и в
инвентаре, и в тексте теста, а не замаскировано.

**Регресс-тест доказан красным/зелёным циклом:** временное удаление `annotations` из
`get-issues.metadata.ts` роняет тест, после отката — зелёный. Тест итерирует `TOOL_CLASSES`
composition root, а не список имён, поэтому не устареет на первом же новом инструменте.

Инвентарь переехал в `packages/framework/dev-client/docs/tools-annotations-inventory.md`; файл в
папке плана превращён в редирект-стаб, чтобы ссылка из `README.md` плана не сгнила до удаления
папки.

## Открытый вопрос, вскрытый этим пакетом (не относится к предмету 1.3)

`npm run validate:quiet` зелёный для tracker и ticktick, но **красный для yandex-wiki**: шаг
`test:raw-wire` (`packages/servers/yandex-wiki/scripts/raw-wire-test.ts`, вне набора файлов 1.3)
падает на 3 из 13 сценариев с «Таймаут ожидания ответа / Network error / Ошибка подключения к
Yandex Wiki API». Файл не модифицирован ни одним пакетом этого плана. У ticktick аналогичный
скрипт ходит в мок-сервер и проходит 12/12, у wiki — судя по симптомам, реальная сеть.
Гипотеза (не факт): сетевое окружение, а не регрессия кода. Подлежит изолированной проверке
оркестратором до финального DoD плана.

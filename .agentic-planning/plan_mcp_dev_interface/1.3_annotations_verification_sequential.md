# Пакет 1.3 — Семантическая верификация аннотаций (sequential)

**Зависит от:** 1.2
**Модель исполнителя:** средняя (нужна сверка семантики, а не только наличия полей).

## Цель

Инвентарь `inventory_tools_annotations.md` получен regex-парсом `*.metadata.ts` и проверяет
**наличие** хинтов. Механизму защиты записи этого мало: инструмент с `readOnlyHint: true`,
который на деле пишет, пройдёт такую проверку и обойдёт защиту. Пакет закрывает оба пробела —
слепые пятна способа получения и семантическую верность разметки.

## Набор файлов

- `packages/servers/{yandex-tracker,yandex-wiki,ticktick}/tests/**` — регрессионные тесты (по одному на сервер, рядом с проверяемыми метаданными)
- Постоянное место для инвентаря: `packages/framework/dev-client/README.md` или `docs`-раздел пакета
- `.agentic-planning/plan_mcp_dev_interface/inventory_tools_annotations.md` — обновление до переноса

**Почему тесты в серверах, а не во framework.** Тест, живущий в `dev-client`, но проверяющий три
сервера, не имеет импортов на них — depcruise промолчит, а turbo не выстроит порядок «сначала
собрать серверы, потом тестировать framework», и тест будет то зелёным, то красным по кэшу.

**Почему инвентарь переезжает.** Правила проекта требуют удалить папку плана после финальной
валидации. Верификационный артефакт, на который опирается защита записи, не должен умирать
вместе с планом.

## Что делаем

1. Снять фактический `tools/list` через `mcp-dev list --json` по каждому серверу — то есть через реальный протокол, а не по исходникам. Это закрывает слепые пятна статического парса: дефолты генератора definition, метаданные вне `*.metadata.ts`, расхождение «файл есть — регистрации нет».
2. Сверить состав имён и хинты с таблицей.
3. **Семантическая сверка:** для каждого инструмента с `readOnlyHint: true` проверить по коду, что он не пишет ни в удалённое окружение, ни на локальную ФС. Известная отправная точка — расхождение wiki (`download_attachment`, `readOnlyHint: true`, делает `writeFile`) против tracker (те же по смыслу инструменты помечены `false` после осознанной правки «пакет 3.1.G»).
4. Расхождения выписать поимённо с указанием канала, который их породил.

## Definition of Done

1. Состав из реального `tools/list` сверен с таблицей (ожидаемо 92 / 36 / 25), расхождения объяснены.
2. Каждый инструмент с `readOnlyHint: true` проверен по коду на отсутствие записи; список проверенных и найденных расхождений — в отчёте пакета.
3. Регрессионный тест заведён **безусловно** (а не «если расхождения найдены»): новый инструмент без явных `readOnlyHint`/`destructiveHint` роняет сборку своего сервера.
4. Строка «чем получено и чего этот способ не видит» обновлена: способов теперь три — статический парс, реальный `tools/list`, сверка по коду.
5. Инвентарь перенесён в постоянное место, ссылки поправлены.

# Пакет 3.1 — Дедупликация smoke-харнесса (sequential)

**Зависит от:** 2.1–2.4
**Модель исполнителя:** старшая (рефакторинг живого тестового контура).

## Мотивация

`scripts/smoke-test-server.ts` (504 + 534 + 520 строк) и `scripts/raw-wire-test.ts`
(717 + 817 + 751 строк) — шесть файлов, ~3.8k строк, в которых один и тот же
transport-харнесс скопирован трижды в двух вариантах.

## Критическое ограничение

**`raw-wire-test.ts` на официальный `Client` переводить нельзя.** Эти тесты специально говорят
сырыми байтами JSON-RPC, потому что проверяют поведение самого SDK (negotiation эпох, коды
ошибок, реакцию на неполный `_meta`). Прогон их через клиент того же SDK превратил бы проверку
в тавтологию. Общим выносится только транспортный низ (спавн процесса, буферизация stdout,
ожидание ответа по id, таймауты, локальный HTTP-стенд для сценариев сбоев) — сценарии остаются
на месте и продолжают говорить байтами.

`smoke-test-server.ts` переводить на клиента можно и нужно: там проверяется наш сервер, а не SDK.

## Набор файлов

- `packages/framework/dev-client/src/**` (транспортный харнесс — куда именно, решается в пакете: возможно, отдельный подпредмет, а не внутрь `session/`)
- `packages/servers/*/scripts/smoke-test-server.ts`
- `packages/servers/*/scripts/raw-wire-test.ts`

Пакет трогает все три сервера сразу — поэтому sequential и после 2.x.

## Definition of Done

1. `npm run test:smoke:server` и `npm run test:raw-wire` для всех трёх серверов проходят с тем же набором сценариев, что до рефакторинга (сценарии сверяются поимённо, а не по числу).
2. Суммарный объём шести файлов сокращён, `npm run cpd` не показывает роста дублирования.
3. Ни один raw-wire-сценарий не переведён на официальный клиент — проверяется чтением диффа.
4. `npm run validate` в корне проходит.

## Замечание редакции 2

Перенос транспортного низа в `dev-client` формально противоречит доводу «слово dev в имени
удерживает пакет от расползания»: тестовый харнесс — не dev-вызов инструментов. Решение:
транспортный низ живёт отдельным подпредметом с собственным именем, а не внутри `session/`,
и если он начнёт обрастать тестовой спецификой — выносится в самостоятельный пакет. Условие
пересмотра названо здесь, чтобы не решать это в спешке во время рефакторинга.

## Ограничение, пришедшее из соседней ветки (зафиксировано оркестратором)

В ветке `claude/tools-list-worktree-deps-9b8d73` идёт работа по тем же шести файлам
`packages/servers/*/scripts/{smoke-test-server,raw-wire-test}.ts` — они там правятся **раньше**
этого пакета. Пакет 3.1 работает поверх их результата, а не поверх текущего состояния `main`.

**Требование к выносимому транспортному низу — гигиена ожиданий.** Готовность сервера
определяется по ответу на `initialize`, завершение процесса — по событию `exit`. Ожидание по
таймеру не восстанавливать ни в каком виде, в том числе по инерции при переносе старого кода.
Таймер остаётся только предельным таймаутом с внятной ошибкой, а не способом дождаться старта.

Точный расклад ожиданий на момент планирования (перепроверено соседней веткой по коду):

- Единственное настоящее ожидание **старта** во всём контуре — `STARTUP_DELAY_MS = 900` в
  `raw-wire-test.ts`.
- В `smoke-test-server.ts` ожидания старта уже **нет**: его снял коммит `39ef0db3`, и там на этом
  месте лежит готовый образец правильного механизма («фиксированной паузы перед первым запросом
  больше нет: запись в stdin буферизуется ОС-пайпом»). Оставшиеся там `sleep(2000)` и `sleep(1000)`
  — это shutdown в `finally` (SIGTERM → пауза → SIGKILL); их тоже перевести на событие `exit`.
- Маркера готовности в логах не существует: при `LOG_LEVEL=error` успешно стартовавший сервер
  молчит и в stdout, и в stderr. «Ждать строку старта» — не вариант. Правильный механизм: слать
  первый запрос сразу (запись в stdin до чтения ребёнком безопасна, данные лежат в буфере пайпа),
  считать готовностью сам ответ, отказываться по событию `exit` с накопленным stderr в тексте ошибки.

**Чего этот пакет НЕ чинит.** Первая редакция этой врезки связывала вынос транспортного низа с
флаком, роняющим semantic-release на `main`. Связь не подтвердилась и снята: по логам шести
последних падений `release.yml` четыре — это буквально «два последовательных `tools/list` вернули
разные списки», два — ожидание stderr (класс, закрытый коммитом `39ef0db3`), и **ни одного** с
сигнатурой таймаута. Причина релизных падений отдельная и ищется в соседней ветке. Исполнитель
рефакторинга не должен считать, что вынос транспортного низа её устраняет.

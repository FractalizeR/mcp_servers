# План: тонкий dev-интерфейс вызова MCP-инструментов

**Задача.** Дать агенту, дорабатывающему код серверов, способ вызвать наши MCP-инструменты
ровно так, как их вызовет MCP-клиент, — без переподключения MCP к самому агенту и без
перезапуска сессии.

**Статус:** редакция 2, после ревью (`comprehensive` + DeepSeek; Codex отказался — исчерпан лимит
аккаунта). Изменения редакции 2 перечислены в конце файла.

## Принятые решения

| Развилка | Решение |
|---|---|
| Достоверность | Официальный `@modelcontextprotocol/client@2.0.0` по stdio против **локально собранного бандла текущего рабочего дерева** |
| Источник секретов | `env` из записи MCP-клиента (через коннектор `@fractalizer/mcp-cli`) — **только env**, не команда и не путь |
| Токен в выводе | Не утекает по неосторожности: env не печатается, значения маскируются, есть тест-канарейка. **Это не граница доверия** — см. ниже |
| Запись | Блокируется по умолчанию, разблокируется только флагом `--dangerously-allow-write` в командной строке |
| Производительность | Батч по умолчанию: одна stdio-сессия на файл вызовов |
| Формат батча | JSONL — одна строка = один вызов |
| HTTP-транспорт | Не делаем (обоснование ниже) |
| Аудитория | Агент, дорабатывающий код. Инструкция — в корневом `CLAUDE.md` и в `CLAUDE.md` серверов |

### Почему бандл берётся локальный, а из конфига клиента — только env

Первая редакция плана резолвила запуск целиком через `getLaunchSpec()`: команду, аргументы и env.
Ревью показало, что это ломает саму цель. Фактическая запись на машине пользователя:

```
fractalizer_mcp_yandex_tracker: node /Users/.../mcp_servers/packages/servers/yandex-tracker/dist/yandex-tracker.bundle.cjs
```

— это путь в основной checkout, а агент работает в git worktree. Схема запускала бы код из `main`
вместо правок агента, **молча**: файл существует, сессия открывается, инструменты отвечают.

Смена механизма (а не заплатка на каждый симптом) убирает разом пять проблем: чужой код,
неразличимость причин отказа `getLaunchSpec()`, поломку разбора `Args` на путях с пробелами,
неопределённый `cwd` и зависимость от недокументированного формата `claude mcp get` в части
команды. Из клиентской записи остаётся ровно то, что нельзя получить иначе, — секреты.

Достоверность при этом не страдает: команда та же (`node <bundle>`), бандл собран тем же
конфигом, окружение то же. Расхождение остаётся ровно одно и оно осознанное — бандл наш,
свежий, а не тот, что в основном checkout.

### Почему не HTTP

В `@modelcontextprotocol/server@2.0.0` HTTP уже есть (`WebStandardStreamableHTTPServerTransport`,
`PerRequestHTTPServerTransport`, `createMcpHandler`) — сделать дёшево. Но ускоряет не транспорт,
а отсутствие перезапуска процесса между вызовами, что решает батч по stdio. HTTP оправдан только
ради демона, живущего между запусками агента, а демон приносит порты, свой жизненный цикл и
главный риск — застрявший в памяти код предыдущей редакции. Условие пересмотра: если замеры
покажут, что старт бандла доминирует над временем вызовов в типичном батче.

### Что именно гарантирует контур секретов

Гарантия: **токен не попадает в контекст агента по неосторожности через вывод dev-интерфейса.**
Это не защита от намеренного чтения: у агента есть Bash, он может выполнить `claude mcp get` сам
и правит исходники сервера, который токен получает. Формулировать сильнее — значит дать
следующему читателю плана гарантию, которой механизм не выдерживает.

**Как это устроено по факту реализации** (уточнено по итогам двух раундов ревью; исходная
редакция плана механизм не фиксировала, и первые две попытки его выбрать оказались неверны).
Маскирование идёт по **единой шкале чувствительности** (`src/secrets/sensitivity.ts`), одинаковой
для секретов из записи MCP-клиента и из родительского окружения. Порядок признаков:

1. **форма значения** — connection-строка с парой `user:pass@`, PEM-заголовок приватного ключа,
   JWT; побеждает всё остальное. Без этого признака `DATABASE_URL` не поймать никогда: имя ключа
   про пароль внутри значения не говорит;
2. **явный список заведомо несекретных имён** — `LOG_LEVEL`, `*_TIMEOUT`, `*_API_BASE`, `*_ORG_ID`,
   `*_CLIENT_ID`, `*_REDIRECT_URI`. Запись MCP-клиента содержит не только токен, и без этого списка
   семизначный `YANDEX_ORG_ID` затирает совпадающие числа в тексте тикетов;
3. **чувствительное имя ключа по сегментам** — `TOKEN|SECRET|KEY|PWD|PASS|PAT|COOKIE|SESSION|DSN|BEARER`
   и т.п. Сравнение именно по сегментам, а не по подстроке: подстрока ловит `PWD` в рабочем
   каталоге и `KEY` в `MONKEY`.

Источник значения влияет **только** на ответ для неопознанного ключа: для записи клиента это
объявленный в коде консервативный fallback «маскировать» (сторона ошибки для неизвестного сервера
выбрана в пользу безопасности), для родительского окружения — «не маскировать».

**Почему это записано так подробно.** Оба неверных варианта механизма выглядели разумно и оба
провалились по одной причине: правило зависело от того, *откуда* пришло значение, а не от того,
*что это за значение*. Первый вариант («маскировать значения всего окружения») затирал `HOME`,
`USER`, `PWD` и портил ответы сервера. Второй («запись клиента чувствительна целиком, окружение —
по имени ключа») сузил радиус той же ошибки, но одновременно начал пропускать `GITHUB_PAT` и
пароль внутри `DATABASE_URL` — то есть ошибался в обе стороны сразу.

## Архитектурное решение

Новый пакет `packages/framework/dev-client` → `@fractalizer/mcp-dev-client`, `private: true`
(в npm не публикуется, серверы подключают как devDependency).

```
dev-client (Client + StdioClientTransport)
    ↓ зависит от
cli (источник env), core (типы), infrastructure
```

| Каталог | Предмет |
|---|---|
| `src/session/` | Клиентская сессия: открыть, `listTools`, `callTool`, закрыть |
| `src/launch/` | Из чего собирается запуск: локальный бандл + проверка свежести + env |
| `src/secrets/` | Контур секретов: маскирование значений env во всём выводе |
| `src/write-policy/` | Классификация read/write и решение о допуске |
| `src/batch/` | Разбор JSONL, прогон, агрегация |
| `src/cli/` | Адаптер доставки (bin `mcp-dev`) |

Рассмотренная альтернатива — команда внутри `@fractalizer/mcp-cli`; отклонена: тот пакет
публикуется конечным пользователям и занимается подключением серверов, а не их вызовом.

Отклонение от гайда по именованию названо явно: `dev-client` содержит режим («dev»), а не
предмет. Оставлено сознательно — режим здесь и есть различающий признак и он же удерживает
пакет от расползания в runtime-код.

## Контракты (сигнатуры, без реализации)

```
// src/launch/
resolveSecretsEnv(serverName: string): Promise<SecretsEnvOutcome>
//   union: { ok, env } | { notConnected } | { notStdio } | { unparsable }
//   ВАЖНО: сырой вывод клиента наружу не отдаётся — он содержит env
resolveLocalBundle(serverPackageDir: string): Promise<BundleOutcome>
//   { ok, path } | { missing, hint } | { stale, bundleMtime, newestSourceMtime }
composeEnv(spec: Record<string,string>): Record<string,string>   // родительское окружение + spec

// src/session/
openSession(launch: ResolvedLaunch, opts: SessionOptions): Promise<DevSession>
DevSession.listTools(): Promise<ToolSummary[]>        // name, title, readOnly, destructive, hasPathArgs
DevSession.callTool(name: string, args: JSONObject): Promise<CallToolResult>
DevSession.close(): Promise<void>

// src/write-policy/
classify(tool: ToolSummary): 'read' | 'write' | 'local-side-effect'
assertAllowed(tools: ToolSummary[], calls: BatchCall[], allowWrite: boolean): void

// src/secrets/
createMasker(env: Record<string,string>): (text: string) => string

// src/batch/
parseBatch(source: string): BatchCall[]
runBatch(session: DevSession, calls: BatchCall[], policy): Promise<BatchOutcome>
```

**Формат JSONL** (одна строка = один вызов):

```
{"tool": "<имя>", "args": { ... }, "label": "<опционально>", "expect": {"isError": false, "contains": "<подстрока>"}}
```

Вывод — тоже JSONL, по объекту на вызов (`label`, `tool`, `isError`, `content`,
`structuredContent`, `durationMs`, `expectation`), плюс человекочитаемая сводка в stderr.
Exit code: `0` — все ожидания сошлись; `1` — есть провалы; `2` — сессия не открылась.

## Политика записи

Три класса вместо двух:

- **read** — `readOnlyHint === true` и среди аргументов нет пути на локальную ФС;
- **write** — `readOnlyHint !== true` (именно `!== true`: отсутствие аннотации означает «считаем записью»);
- **local-side-effect** — `readOnlyHint === true`, но инструмент пишет файл на диск разработчика.

Третий класс заведён не умозрительно. У wiki `download_attachment` стоит `readOnlyHint: true`, а
`download-attachment.tool.ts:30` делает `writeFile`. В tracker те же по смыслу
`download_attachment` и `get_thumbnail` размечены `readOnlyHint: false` — там классификацию
осознанно исправили (комментарий «пакет 3.1.G» в метаданных), до wiki правка не доехала.
`readOnlyHint` в спецификации MCP означает «не меняет своё окружение» и про локальные эффекты
не говорит ничего, поэтому опираться только на него нельзя.

**Расхождение wiki и tracker — дефект существующего кода, а не плана.** План его не чинит: это
отдельное решение пользователя. План лишь не полагается на аннотацию как на единственный признак
и фиксирует сверку в пакете 1.3.

## Имена команд

Скрипты называются `tools:list`, `tools:call`, `tools:batch`. **Не `mcp:list`** — это имя уже
занято в tracker и wiki и означает другое («список MCP-клиентов и их статус»,
`node dist/cli/bin/mcp-connect.js list`). Переопределение сломало бы существующий сценарий и
создало бы два смысла одного имени.

[inventory_tools_annotations.md](inventory_tools_annotations.md) — таблица всех 153 инструментов

## Риски и их обработка

| Риск | Обработка |
|---|---|
| Тестируется бандл из другого дерева | Механизм сменён: бандл всегда локальный, путь из `package.json` пакета сервера |
| Бандл устарел относительно `src/` | Сверка mtime бандла против свежайшего `src/**`, отказ с подсказкой `npm run build`; проверка в ядре, а не в npm-скрипте, — иначе обходится прямым вызовом `mcp-dev` |
| Бандл не собран | Отказ `BundleMissing` с подсказкой |
| Сервер не подключён в клиенте | Типизированный исход `notConnected`; перечисление найденных записей — только если коннектор научится его давать (сейчас метода нет, см. 1.1) |
| Формат вывода `claude mcp get` изменился | Отдельный исход `unparsable` (не путать с «не подключён»), фикстуры реального вывода в тестах |
| Клиент начнёт маскировать env в выводе | Дочерний процесс получит маскированный токен → тихий отказ аутентификации. Обработка: пустой или явно маскированный `env` → отказ до спавна |
| `spec.env` пуст из-за смены формата | Отказ с диагностикой, а не запуск без токена |
| Секреты в родительском окружении (ticktick читает `TICKTICK_ACCESS_TOKEN`/`REFRESH_TOKEN`/`CLIENT_SECRET` из `process.env`) | Маскер строится из **фактически переданного** окружения, а не только из `spec.env` |
| Расхождение версий `@modelcontextprotocol/client` и `/server` | Обе на одном мажоре, правило в renovate |
| Агент прогонит write-инструменты по боевым данным | Блокировка по умолчанию + флаг только из командной строки |
| Батч упрётся в rate limit боевого сервиса | Таймаут на вызов и пауза между вызовами, настраиваемые; ошибки rate limit различимы в выводе |
| Два агента в двух worktree пишут в один боевой сервис | Предупреждение в документации (2.4) |

## Тестовый план

- **Unit:** классификация трёх классов; разбор JSONL (валидные, битая строка с номером, пустой файл); маскирование (значение в середине строки, JSON-экранированная форма, короткое значение, стек ошибки); сверка `expect`; композиция env; сверка свежести бандла.
- **Integration (вне `validate`, см. DoD):** сессия против реального локального бандла; `list`; успешный `call`; неизвестный инструмент; невалидные аргументы; батч в одной сессии; закрытие сессии; падение сервера в середине батча.
- **Безопасность:** канарейка — значение из env не встречается ни в stdout, ни в stderr ни в одном режиме, включая необработанное исключение и JSON-экранированную форму.
- **Политика записи:** write без флага → отказ до отправки `tools/call`; с флагом → доходит; `--dangerously-allow-write` из переменной окружения не действует.
- **Негативные:** сервер не подключён; вывод клиента не разобран; бандл отсутствует; бандл устарел.

## Definition of Done всего плана

1. `npm run validate` в корне проходит целиком, релизный CI не требует ни `claude` CLI, ни токена, ни сети.
2. Из директории любого из трёх серверов работают `npm run tools:list` и `npm run tools:batch -- <file.jsonl>`.
3. Токен не появляется в выводе ни в одном режиме (доказано канарейкой, включая путь необработанного исключения).
4. Write-инструмент без `--dangerously-allow-write` не выполняется; инструмент класса `local-side-effect` тоже.
5. Устаревший бандл не даёт молча пройти вызову.
6. Инструкция для агента есть в корневом `CLAUDE.md` и в `CLAUDE.md` трёх серверов, `npm run validate:docs` проходит.

## Финальная валидация (зафиксировано оркестратором)

`npm run validate` в корне — **зелёная, 61 из 61 задачи**. Пакеты 1.1, 1.2, 1.3, 2.1–2.4 сданы и
верифицированы машинно. Пакет 3.1 не исполнялся — причина ниже.

### Два флака, пойманных по дороге

Оба вскрылись в шагах релизного гейта и оба **не связаны с изменениями этого плана**:

1. **`@fractalizer/mcp-server-ticktick#test:coverage`** — уронил первый полный прогон
   `npm run validate` (единственный упавший из 61). Изолированный повтор той же команды в пакете —
   зелёный (EXIT 0, покрытие 95.54 / 81.77 / 98.77 / 96.15 при порогах 80 / 80 / 75 / 80,
   все 742 теста проходят). Второй полный прогон — тоже зелёный. То есть падение воспроизводится
   только под параллельной нагрузкой turbo.
2. **`@fractalizer/mcp-server-yandex-wiki#test:raw-wire`** — красный на 3 из 13 сценариев во время
   исполнения пакета 1.3, зелёный в последующем полном прогоне при `cache bypass, force executing`
   (то есть шаг реально отработал, а не был взят из кэша).

Оба относятся к области, которую расследует отдельный план
`.agentic-planning/plan_release_gate_determinism/` в ветке
`claude/tools-list-worktree-deps-9b8d73`, и оба — новые наблюдения для него.

### Yandex Wiki API отдаёт 503

Устойчиво, на всём протяжении работ, включая `yw_ping`. Не влияет на валидацию (все тесты wiki
герметичны и ходят в мок), но делает непроверяемым сквозной прогон
`packages/servers/yandex-wiki/dev-calls.example.jsonl` против живого сервиса. Подробности и
изолированная проверка — во врезке пакета 2.2.

### Почему пакет 3.1 не исполнен

DoD 1 пакета требует, чтобы `test:smoke:server` и `test:raw-wire` проходили для всех трёх серверов
**с тем же набором сценариев**, что до рефакторинга, — то есть требует зелёной базы для сравнения.
База сейчас недостаточно устойчива: тот самый `test:raw-wire` у wiki за одну сессию наблюдался и
красным, и зелёным. Рефакторинг транспортного низа поверх флакующей базы неотличим по симптомам от
рефакторинга, который сам внёс регрессию.

Кроме того, шесть файлов пакета 3.1 закреплены за отдельным планом
`plan_release_gate_determinism`, который правит их раньше и по своей причине. На момент фиксации
та работа **не выполнена**: в ветке `claude/tools-list-worktree-deps-9b8d73` лежит один коммит
`5aa2636e` (про `manifest.json`), в её рабочем дереве — только документ плана, шесть файлов не
тронуты. Решение о порядке — за пользователем.

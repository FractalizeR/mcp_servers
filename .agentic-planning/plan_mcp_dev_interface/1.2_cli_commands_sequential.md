# Пакет 1.2 — CLI `mcp-dev` и подключение к трём серверам (sequential)

**Зависит от:** 1.1
**Модель исполнителя:** средняя.

## Цель

Тонкий адаптер доставки поверх ядра плюс единственная в плане правка манифестов и lock-файла.

## Набор файлов

- `packages/framework/dev-client/src/cli/**`, `bin/**`, `tests/cli/**`
- `packages/framework/dev-client/package.json` (секция `bin`), `README.md`
- `packages/servers/{yandex-tracker,yandex-wiki,ticktick}/package.json` — **только** добавление devDependency
- `package-lock.json`

**Почему devDependency всех трёх серверов здесь, а не в параллельных 2.x.** В npm-workspaces
lock-файл один на монорепозиторий. Три параллельных агента с собственными `npm install` затрут
работу друг друга — ровно тот сценарий, против которого заведено правило непересекающихся
наборов файлов. Одна правка, один `npm install`, дальше 2.x работают со скриптами и документацией.

Зависимость указывается так, чтобы `npm ci` с нуля не искал `private`-пакет в registry
(протокол workspace либо `*`); это проверяется DoD, а не предполагается.

## Команды

```
mcp-dev list   --server-name <n> --package-dir <dir> [--json] [--writable]
mcp-dev call   <tool> <json|@file> --server-name <n> --package-dir <dir> [--dangerously-allow-write]
mcp-dev batch  <file.jsonl>       --server-name <n> --package-dir <dir> [--dangerously-allow-write] [--stop-on-error] [--delay-ms <n>] [--call-timeout-ms <n>]
```

- `--server-name` и `--package-dir` задаются в npm-скриптах серверов. Читать их из констант сервера нельзя: framework-пакет не может зависеть от серверов — это обратное ребро графа.
- `list` печатает `имя | класс (read/write/local-side-effect) | title`; `--json` — машинный вид; `--writable` — только не-read.
- `call` — частный случай батча из одной строки, отдельного пути исполнения нет.
- `--dangerously-allow-write` читается **только** из командной строки: из переменных окружения не подхватывается никогда, чтобы флаг нельзя было «прилепить» к сессии агента.
- `--delay-ms` и `--call-timeout-ms` — против упора в rate limit боевого сервиса и против зависших вызовов.

## Порядок проверок и отказов

1. Резолв бандла и свежести, резолв секретов — до открытия сессии.
2. Открытие сессии, `listTools` — классификация возможна только после этого.
3. Проверка политики записи по всему батчу разом — **до первого `tools/call`**, с перечислением нарушивших строк. (В редакции 1 было сказано «до открытия сессии», что противоречило шагу 2.)
4. Неизвестное имя инструмента — deny-by-default: вызов не отправляется, строка помечается провалом.

## Вывод и коды возврата

- stdout — только JSONL результатов. Это то, что читает агент.
- stderr — человекочитаемая сводка: вызовов, провалов, времени.
- Exit code: `0` — все ожидания сошлись; `1` — есть провалы; `2` — сессия не открылась.

## Кейсы и граничные условия

- Пустой батч-файл → exit `0` и явное сообщение, а не тихий успех, выглядящий как прогон.
- Битая строка JSONL → ошибка с номером строки; остальные строки прогоняются, если не задан `--stop-on-error`.
- `@file` не существует; инлайновый JSON невалиден — ошибка разбора отделена от ошибки валидации схемы на сервере.

## Definition of Done

1. `mcp-dev list` из каждого из трёх серверов печатает список инструментов с классами.
2. `mcp-dev batch` с несколькими read-вызовами открывает **одну** сессию (проверяется числом порождённых процессов).
3. `mcp-dev call` с инлайновым JSON и с `@file` даёт тот же результат, что однострочный батч, — это же подтверждает отсутствие отдельного пути исполнения.
4. Write-инструмент без флага: exit `1`, `tools/call` не отправлен (проверяется на заглушке транспорта).
5. Инструмент класса `local-side-effect` без флага не выполняется.
6. Неизвестное имя инструмента в батче не отправляется на сервер.
7. `--dangerously-allow-write`, заданный переменной окружения, не действует.
8. `npm ci` с нуля в чистом клоне проходит, `npm run validate` в корне проходит.

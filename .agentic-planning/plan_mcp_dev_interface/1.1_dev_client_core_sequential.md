# Пакет 1.1 — Ядро `@fractalizer/mcp-dev-client` (sequential)

**Зависит от:** —
**Модель исполнителя:** средняя, с эскалацией на старшую при провале DoD.

## Цель

Пакет, который умеет собрать запуск (локальный бандл + секреты из записи MCP-клиента), открыть
настоящую MCP-сессию, перечислить инструменты, вызвать инструмент — не печатая секретов и не
запуская чужой или устаревший код.

## Набор файлов

- `packages/framework/dev-client/**` (новый пакет целиком)
- `packages/framework/cli/src/connectors/**` и `packages/framework/cli/src/types/launch.types.ts` — расширение контракта, см. ниже
- `packages/framework/cli/tests/**` — фикстуры реального вывода `claude mcp get`
- `.dependency-cruiser.cjs` — правило для нового пакета
- `package-lock.json`, `tsconfig` references — по существующей схеме

Файлы серверов **не трогаем** — они целиком в пакете 1.2.

## Расширение контракта коннектора (обязательная часть пакета)

Сейчас `MCPConnector.getLaunchSpec(): Promise<ServerLaunchSpec | null>` возвращает `null` на
четыре разные причины: записи нет, транспорт не stdio, вывод не разобран, команда `claude mcp get`
упала или истёк таймаут. Обещанные планом различимые исходы через такой контракт недостижимы,
а дублировать парсер недокументированного формата в dev-client — хуже.

Поэтому 1.1 меняет контракт на discriminated union и адаптирует существующих потребителей
внутри `@fractalizer/mcp-cli`. Это единственная причина, по которой пакет выходит за границы
своего каталога, и она названа заранее.

**Метода перечисления подключённых серверов в интерфейсе нет** (есть `getStatus` на один сервер).
Обещание «ошибка со списком найденных записей» из редакции 1 снято: либо добавляем метод в этом
же пакете, либо ошибка ограничивается именем, которое искали.

## Резолв запуска

- Путь к бандлу — **локальный**: из `package.json` пакета сервера (поле `bin`), относительно переданного каталога пакета. Из записи MCP-клиента путь и команда не берутся никогда.
- Свежесть: mtime бандла против свежайшего mtime в `src/**` пакета сервера. Устарел → отказ с подсказкой `npm run build`. Проверка живёт **в ядре**, а не в npm-скрипте: иначе обходится прямым вызовом `mcp-dev`.
- `cwd` дочернего процесса фиксируется явно (каталог пакета сервера) и документируется.
- Композиция окружения: `composeEnv` = родительское окружение плюс `env` из записи клиента. Полностью подменять окружение нельзя — сервер останется без `PATH`, `HOME`, прокси и `NODE_EXTRA_CA_CERTS`, что на машине с split-tunnel VPN даст ложные падения.
- Пустой `env` из записи → отказ до спавна: это признак того, что формат вывода клиента изменился, а не приглашение запускать сервер без токена.
- `clientInfo` и объявляемые capabilities фиксируются явно и комментируются; режим negotiation эпох (`legacy` / `auto`) выбирается осознанно — от него зависит, какую эпоху протокола мы проверяем.

## Контур секретов

- Секреты передаются дочернему процессу и **никуда больше**: не логируются, не попадают в сообщения ошибок, не сериализуются в результат.
- Маскер строится из значений **фактически переданного** окружения (не только из `env` записи клиента): ticktick читает `TICKTICK_ACCESS_TOKEN`, `TICKTICK_REFRESH_TOKEN`, `TICKTICK_CLIENT_SECRET` из `process.env`, и они обязаны попасть под маску.
- Маскирование применяется **до** сериализации в JSONL, печать — после: иначе JSON-экранированная форма значения (`&`, `\\`) не совпадёт с сырой подстрокой.
- Порог «слишком коротких значений» назван числом в коде и обоснован комментарием. Безымянный порог — это дыра, выглядящая как правило.
- Процессный уровень: `uncaughtException` и `unhandledRejection` проходят через маскер, иначе рантайм Node напечатает стек мимо любого форматтера пакета.
- stderr дочернего процесса по умолчанию не ретранслируется; за флагом — через маскер.
- Правило для реализации: значения секретов не кладутся в `Error` никогда, даже временно.

## Классификация инструментов

- `read` — `readOnlyHint === true` и в схеме аргументов нет пути на локальную ФС.
- `write` — `readOnlyHint !== true`.
- `local-side-effect` — `readOnlyHint === true`, но инструмент принимает путь для записи (обоснование и пример в README плана).
- Признак «принимает путь» определяется по схеме инструмента, а не по списку имён: список имён разъедется с кодом при первом же новом инструменте.

## Тестируемость

Фабрика транспорта инъецируется, чтобы сессия тестировалась на заглушке без спавна процесса.
Это требование пакета, а не деталь реализации: без него пороги покрытия (80/80/75/80, применяются
к каждому workspace) недостижимы для пакета, чья суть — процессы и I/O.

## Кейсы и граничные условия

- Сервер не подключён в клиенте / транспорт не stdio / вывод не разобран / команда упала — четыре различимых исхода.
- Бандл отсутствует; бандл устарел.
- Сервер не отвечает на handshake за таймаут → ошибка с накопленным (маскированным) stderr, а не зависание.
- Сервер упал в середине батча → остаток помечается непроведённым, сессия закрывается.
- Неизвестный инструмент и невалидные аргументы — два разных наблюдаемых исхода, оба доходят нетронутыми.
- Двойное закрытие сессии и закрытие при исключении — процесс не остаётся висеть.

## Definition of Done

1. `npm run validate` в пакете и в `@fractalizer/mcp-cli` проходит (контракт коннектора изменён — потребители адаптированы).
2. Канарейка: заведомое значение в окружении не встречается ни в stdout, ни в stderr в режимах — успех, ошибка, подробный вывод, ретрансляция stderr сервера, **необработанное исключение**, и в **JSON-экранированной** форме.
3. Тест: `env` записи клиента пуст → отказ до спавна.
4. Тест: бандл старше `src/**` → отказ; свежий → проход.
5. Тест на композицию окружения: дочерний процесс видит и родительские переменные, и секреты записи.
6. Unit-тесты на три класса классификации, разбор JSONL и маскирование проходят; покрытие пакета соответствует порогам проекта.
7. Позитивная проверка depcruise: в `.dependency-cruiser.cjs` добавлено правило для `framework/dev-client`, и временно внесённый импорт из `packages/servers/**` роняет `npm run depcruise`. (Без этого DoD выполнялся бы бездействием: существующие правила перечисляют пути пофамильно и нового пакета не знают.)
8. Интеграционные тесты вынесены в отдельную задачу `test:integration`, не входящую в `validate`; при отсутствии `claude` CLI или записи они пропускаются, и пропуск считается выполнением.

## Факт исполнения (пакет 1.1, зафиксировано оркестратором)

Пакет **сделан**, DoD 1–8 проверены машинно. Два отклонения от текста плана приняты:

1. **Скрипт `depcruise` пакета запускается из корня репозитория**
   (`cd ../../.. && depcruise packages/framework/dev-client/src -c .dependency-cruiser.cjs`),
   а не по общей схеме `depcruise src -c ../../../.dependency-cruiser.cjs`. Причина вскрылась
   позитивной проверкой DoD 7: правила в `.dependency-cruiser.cjs` написаны с regex `^packages/...`,
   а depcruise репортит пути относительно cwd. При запуске из каталога пакета путь выглядит как
   `src/index.ts` → `../../servers/...`, regex не матчится, и **правило мёртвое**. С правкой
   `npm run depcruise` в dev-client реально краснеет на импорте из `packages/servers/**` (проверено
   оркестратором: exit 2) и зеленеет после отката.

2. **`test:integration` проверяет ядро напрямую** (`DevSession`, `resolveSecretsEnv`,
   `resolveLocalBundle`, `runBatch`), а не через CLI-адаптер `mcp-dev`: адаптера на момент 1.1
   не существует, он в пакете 1.2. При отсутствии записи MCP-клиента или собранного бандла suite
   пропускается. Отдельный `vitest.integration.config.ts`; обычный `vitest run` исключает
   `tests/integration/**`, поэтому в `validate` они не входят.

**Вскрытый дефект существующего кода, вне границ плана (не чинится здесь).** Та же мёртвая
инвокация depcruise действует во **всех** остальных workspace (`cli`, `core`, `infrastructure`,
три сервера) и, соответственно, в `scripts/validate.sh` и в CI. Проверено оркестратором:
импорт из `packages/servers/**`, временно внесённый в `packages/framework/core/src/index.ts`,
даёт `✔ no dependency violations found`. Архитектурные границы монорепозитория машинно
**не контролируются** — решение о починке за пользователем, отдельной задачей.

**Находка по поведению серверов:** на неизвестный инструмент серверы монорепозитория отвечают
не протокольной ошибкой, а `CallToolResult{isError: true}` со списком доступных инструментов.
Учтено в интеграционном тесте; пакету 1.2 (deny-by-default на неизвестное имя) это не мешает —
там имя отсеивается до отправки `tools/call`.

# Этап 1.1 — план реализации защиты области действия

Детализация [1.1_baseline_harness_sequential.md](1.1_baseline_harness_sequential.md) до контрактов.
Основание всех обобщений — [0_outgoing_requests.md](0_outgoing_requests.md) (перечисление снято
машинно скриптом `scripts/enumerate-outgoing-requests.ts`).

## 1. Факт, на котором построен план

92 инструмента дали 80 запросов, из них **50 не-GET**. Область действия определяется по запросу
**четырьмя разными способами**, а для одного класса — не определяется вовсе:

| Класс | Запросов | Чем определяется область | Решение guard |
|---|--:|---|---|
| A — ключ задачи в пути `/vN/issues/{KEY}/…` | 15 | `{KEY}` | префикс очереди + журнал прогона |
| A' — ключ очереди в пути `/vN/queues/{KEY}/…` | 6 | `{KEY}` | префикс очереди + политика (см. §3) |
| B — очередь в теле (`POST /v3/issues`) | 1 | `body.queue` | сверка с очередью песочницы |
| C — bulk (`POST /v2/bulkchange/_*`) | 3 | `body.issues[]`, `body.queue` | все ключи ∈ журнал прогона |
| D — непрозрачный идентификатор | 19 | **ничем** | только журнал прогона |
| E — организация целиком (projects, global fields) | 6 | ничем | запрет живьём (реестр исключений) |

Классы D и E — 25 из 50 — это ровно те, где «аккуратность ведущего прогон» неотличима от ошибки:
`DELETE /v2/boards/{id}` не несёт в себе ни одного признака принадлежности к песочнице.

**Чего перечисление не видит** (строка обязательна): ветки, требующие правдоподобного ответа
сервера (вторая страница пагинации, второй запрос после чтения списка); `raw_api_request` — генератор
образца не осилил его regex, разбирается отдельно; 14 инструментов не дали запроса на синтетическом
образце.

## 2. Точка перехвата

Перехват ставится на **request-interceptor axios instance**, не на методах `IHttpClient`.

Причина названа фактом: `upload_attachment` (не-GET), `download_attachment`, `get_thumbnail` ходят
через `getAxiosInstance()` в обход `IHttpClient` (задокументировано в шапке
`tests/smoke/tool-params-reach-api.smoke.test.ts`). Декоратор поверх `IHttpClient` пропустил бы
мутирующий `upload_attachment` мимо guard — то есть выглядел бы работающим, имея дыру ровно в
классе, ради которого заводится.

## 3. Два независимых измерения решения

Guard отвечает на два разных вопроса, и их смешение — источник ложной защиты:

1. **Определима ли область действия запроса?** (классы A/A'/B/C — да; D — только через журнал; E — нет)
2. **Разрешена ли эта область политикой прогона?**

Определимость без разрешения ничего не значит: `PATCH /v3/queues/TEST` определим (очередь видна),
но правит саму песочницу и по реестру исключений живьём не проверяется.

**Fail-closed:** в живом режиме запрос, чья область не определена ни одним из способов, отклоняется.
Умолчание «пропустить, раз не поняли» превращает guard в декорацию.

## 4. Контракты (без реализации)

### 4.1 Framework — обобщённый механизм

`HttpConfig` расширяется необязательным полем:

```
requestGuard?: (request: { method, url, data }) => void   // бросает — запрос не уходит
```

Регистрируется в `setupInterceptors()` первым. Домен-агностичен: Wiki получает тот же рубеж,
не зная про очереди Трекера. Отсутствие поля = поведение сегодняшнего дня, продовый путь не меняется.

### 4.2 Сервер — доменные правила

- `LiveScopePolicy` — решение по запросу: `decide(request) → allow | deny(reason)`.
  Реализует таблицу §1. Не знает про HTTP-транспорт.
- `RunJournal` — журнал прогона: `register(kind, id)`, `has(kind, id)`, `entries()`, персист в файл.
  Пополняется из **ответов** на разрешённые POST-создания: созданное этим прогоном становится
  единственным, что впоследствии разрешено править и удалять.
- `LiveScopeGuard` — связывает политику, журнал и `requestGuard`; пишет журнал вызовов
  (`recordCall` из 1.1) для отчёта этапа 3.1.

### 4.3 Активация

Через переменные окружения (`YANDEX_TRACKER_LIVE_SCOPE_QUEUE`, `…_JOURNAL`), подключение — в
`bindHttpLayer` composition-root. Причина размещения в `src/`, а не в `tests/`: прошлый живой прогон
шёл через `mcp-dev` (собранный бандл, отдельный процесс) — защита, живущая только в `tests/live`,
не покрывает тот путь, которым прогон реально ведётся.

## 5. Тестовый план

Негативные кейсы обязательны — без них белый список выглядит работающим до первого нарушения:

- по одному отказу на каждый класс §1 (мутация в чужой очереди; создание задачи с `queue ≠ TEST`;
  bulk со списком, где хоть один ключ вне журнала; правка непрозрачного id вне журнала; любой запрос
  класса E);
- разрешающие кейсы: мутация задачи прогона, создание в очереди песочницы, правка созданного по журналу;
- `upload_attachment` — отдельный кейс: подтверждает, что обходной путь `getAxiosInstance()` перехвачен;
- отказ происходит **до сети** — проверяется тем, что адаптер axios не вызван;
- guard выключен (нет env) ⇒ ни одного отказа: продовый путь не задет.

## 6. Definition of Done

- Каждый из 50 не-GET запросов таблицы §1 отнесён к классу, и на класс есть тест.
- Попытка мутации вне песочницы отклоняется до сети — подтверждено негативным тестом.
- `upload_attachment` перехвачен (обходной путь закрыт) — отдельным тестом.
- `npm run validate:quiet` зелёный.
- Реестр исключений (класс E + всё, что не проверяется живьём) записан файлом с указанием
  замещающей моковой проверки.

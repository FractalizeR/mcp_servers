# Этап 1.1 — База и оснастка (sequential, блокирует всё остальное)

## Цель
Получить (а) актуальный машинный инвентарь, (б) изолированную песочницу в живом Трекере,
(в) оснастку, позволяющую гонять живые сценарии повторяемо и с гарантированной уборкой.

## Шаги

1. **Сверка инвентаря с реальным реестром.** `npm run validate:tools` + выгрузка `tools/list`
   у собранного бандла (как это делает `scripts/raw-wire-test.ts`). Расхождение с
   [0_inventory_tools.md](0_inventory_tools.md) означает, что инвентарь снят неверным способом, —
   чинить инвентарь до начала остальных этапов.
2. **Песочница — очередь `TEST` в боевой организации.** Отдельной тестовой организации нет,
   значит изоляция правами недостижима: токен, которым ходят живые прогоны, имеет доступ ко всей
   организации. Это меняет модель угроз — единственная защита остаётся программной, и потому
   она обязана быть в самой оснастке, а не в дисциплине автора теста:
   - **Белый список области действия.** Harness перехватывает исходящий HTTP и отклоняет любой
     не-GET запрос, чей путь не относится к сущностям очереди `TEST` и не создан текущим прогоном.
     Проверяется собственным тестом оснастки: попытка мутации в чужой очереди должна падать
     на клиенте, до сети. Это ровно та проверка, которую в тестовой организации выполнял бы сервер.
   - **Инвентарь созданного.** Каждая созданная сущность регистрируется в журнале прогона; удаляется
     только то, что в журнале. Удаление «всего, что нашлось в очереди `TEST`» запрещено —
     очередь общая, и в ней могут лежать чужие задачи.
   - **Ограничение bulk.** Для `bulk_*` (P0) область действия задаётся явным списком ключей задач
     этого прогона. Запрос вида «все задачи очереди» в живом прогоне запрещён оснасткой:
     цена ошибки в общей организации необратима, а именно этот класс инструментов не имеет
     сегодня ни unit-, ни интеграционного теста.
   - **Что вообще не проверяем живьём при такой конфигурации** (переносится в реестр исключений,
     шаг 5): удаление и правка очередей, глобальных полей, доступов очереди, проектов и всего,
     что по своей природе выходит за пределы одной очереди. Для них — только моковый уровень.
   - Реквизиты — через `YANDEX_TRACKER_TOKEN`, `YANDEX_ORG_ID`, `YANDEX_TRACKER_API_BASE`;
     в репозиторий не попадают.

   *Риск, названный явно:* белый список в клиенте слабее прав на сервере — он защищает от дефекта
   в тестируемом коде, но не от дефекта в самом белом списке. Если позже появится возможность завести
   отдельную организацию, этот пункт заменяется на изоляцию правами, а реестр исключений сокращается.

3. **Harness живых прогонов.** Контракт (без реализации):
   - `withSandbox(fn)` — создаёт префиксованный набор сущностей, отдаёт их сценарию, в `finally`
     удаляет всё созданное. Уборка идёт **через raw API, а не через тестируемые delete-инструменты**:
     иначе сломанный `delete_*` оставляет мусор и одновременно прячет собственный дефект.
   - `readBack(entityRef)` — независимое чтение сущности через `fr_yandex_tracker_raw_api_request`.
     Используется для проверки С-5 и принципиально не ходит через тот же инструмент, чей эффект проверяет.
   - `recordCall(toolName, params, result, httpTrace)` — журнал прогона в файл на диске, из которого
     собирается отчёт этапа 3.1 (многошаговую диагностику читаем из файла, а не из скроллбека).
4. **Уникальность имён.** Все создаваемые сущности получают префикс с меткой прогона. Иначе повторный
   или параллельный запуск отравляет выборки: `find_issues` по очереди вернёт чужие задачи и ассерты
   станут флакающими — дефект оснастки, неотличимый от дефекта продукта.
5. **Реестр «что нельзя проверять живьём».** Явный список инструментов, для которых живой прогон
   недопустим или бессмысленен (правки глобальных полей, доступов очереди, удаление проектов —
   всё, что затрагивает организацию целиком), с указанием замещающей проверки на моках.

## Definition of Done
- Инвентарь совпадает с `tools/list` бандла, расхождений 0 — проверяется командой, а не глазами.
- Harness прогоняет тривиальный сценарий (создать задачу → прочитать через raw API → удалить)
  и оставляет пустую песочницу; два запуска подряд дают одинаковый результат.
- Попытка мутации вне очереди `TEST` или вне журнала прогона отклоняется оснасткой до сети —
  подтверждено отдельным тестом самой оснастки (негативный кейс обязателен: без него белый список
  выглядит работающим, пока его впервые не нарушат).
- Реестр исключений записан файлом, у каждой строки названа замещающая проверка.

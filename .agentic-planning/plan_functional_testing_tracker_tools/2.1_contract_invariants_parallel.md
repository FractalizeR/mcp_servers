# Этап 2.1 — Контрактные инварианты по всем 92 (parallel)

Свойства С-1..С-3. Проверки строятся **как обход всего инвентаря**, а не как список примеров:
добавление нового инструмента без теста должно ронять сборку само.

## К-1. Достижимость и генерация схемы
- Каждый инструмент из инвентаря присутствует в `tools/list`; префикс имени единый; имя уникально.
- `inputSchema` генерируется из Zod (`generateDefinitionFromSchema`) и не расходится с `getParamsSchema()`.
- `DISABLED_TOOL_GROUPS` реально убирает категорию из `tools/list`, а вызов убранного инструмента
  даёт отказ policy, а не 500 и не «tool not found» с другим текстом.

## К-2. Контракт входа
- Для каждого инструмента: пустой объект параметров → ошибка валидации **до** HTTP-вызова
  (проверяется по отсутствию запроса на моке, а не по тексту ошибки).
- Каждое поле схемы доходит до HTTP-запроса — расширение существующего
  `tests/smoke/tool-params-reach-api.smoke.test.ts` на полный инвентарь. Параметр, который принят
  схемой и молча потерян, — самый дешёвый способ получить «инструмент работает, но не делает».
- Опциональные поля с `undefined` не превращаются в `null` в теле запроса.

## К-3. Правдивость аннотаций
- `readOnlyHint=true` ⇒ инструмент за весь тест не сделал ни одного не-GET запроса.
  Проверяется машинно по HTTP-моку, для всех 40 read-only инструментов.
- `destructiveHint=true` ⇔ `requiresExplicitUserConsent=true` (сейчас совпадает на 14 —
  зафиксировать инвариантом, чтобы не разъехалось).
- `idempotentHint=true` ⇒ повторный вызов с теми же параметрами даёт тот же результат и не плодит
  сущностей (на живом прогоне — этап 3.1; на моках — что повторный вызов идёт тем же методом).

## К-4. Контракт выхода
- Ответ каждого инструмента валидируется против его `outputSchema` — расширение
  `tests/smoke/tool-output-schema-representatives.test.ts` с «представителей» на весь инвентарь.
- Batch-инструменты: форма `{ total, successful[], failed[] }` присутствует всегда, в том числе
  когда всё упало и когда всё прошло; `issueId` есть в каждом элементе обеих групп.
- Ключевые идентификаторы (`key`, `id`, `self`) не теряются при фильтрации полей — регрессия
  на исторический дефект `find_issues`.

## DoD
- Ни одна из проверок К-1..К-4 не содержит захардкоженного списка инструментов: список берётся
  из реестра. Новый инструмент без метаданных/схемы роняет тест.
- Красный тест воспроизведён искусственно (временно сломать одну метадату) — проверки действительно ловят.

## Цель
Единые Zod-поля пагинации для всех list-инструментов и решение по протаскиванию метаданных через batch-результат (DP-3, вариант A).

## Контракты
### Общие Zod-поля (в `#common/schemas`)
- `FetchAllSchema = z.boolean().optional()` (default `false`) — `.describe(...)` про opt-in полный обход и лимит.
- `MaxItemsSchema = z.number().int().positive().max(<потолок>).optional()` — переопределение `maxItems` (дефолт 500).
- Переиспользовать существующие `perPage`/`page` (см. `get-comments.schema.ts`). Свести к общим `PerPageSchema`/`PageSchema`, если ещё не сведены.

### Batch (DP-3 A)
- Операции list-batch меняют тип значения: `BatchResult<string, Entry[]>` → `BatchResult<string, PaginatedResult<Entry>>`.
- `BatchResultProcessor.process` остаётся дженериком (`data` = `PaginatedResult<Entry>`). Изменяется только `filterFn` на стороне tool: фильтрует `data.items`, а `data.pagination` прокидывается без изменений.
- Решение: фильтрацию делает tool, поэтому в processor правок нет (проверить на этапе ревью, не упускаем ли мы при этом единообразие).

## Edge cases
- `fetchAll=true` + явный `page` → `page` игнорируется при полном обходе (или ошибка валидации?) — **зафиксировать поведение**: предлагаю при `fetchAll=true` стартовать с первой страницы и `page` игнорировать с предупреждением в лог.
- `perPage` отсутствует + `fetchAll=true` → берём максимум endpoint'а.
- `maxItems` больше потолка схемы → отсечёт Zod.

## Тест-план

- `BatchResultProcessor` с `PaginatedResult` в `data`: фильтр применяется к `items`, `pagination` сохраняется.

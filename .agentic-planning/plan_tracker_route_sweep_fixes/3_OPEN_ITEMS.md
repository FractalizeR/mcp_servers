# Открытые пункты по Трекеру (снято 2026-08-25)

## 1. `update_global_field` не шлёт обязательную версию

Канонический маршрут документации — `PATCH /v3/fields/{id}?version=<текущая_версия_поля>`
(`api-ref/issues/patch-issue-field-name`, `patch-issue-field-value`). Мы версию не шлём,
как не слали её `update_project` и `update_component`, — а те отвечали `428` и не
работали никогда.

**Почему не починено:** проверить нечем. Рубеж прогона отклоняет правку чужого
глобального поля (проверено — отказ пришёл), а своё поле не создаётся из-за незакрытого
D10 (`500` на любую категорию). Менять контракт по аналогии — это ровно та догадка,
которая породила разбираемую серию дефектов.

**Что закроет:** живая проба после закрытия D10 либо ответ поддержки Трекера.
Заодно проверить форму `name` при правке: документация ждёт `{en, ru}`, схема шлёт строку.

## 3. Удаление компонента и глобального поля: маршрут никем не объявлен

`PATCH /v3/queues/{id}` проверен живьём и работает, хотя страницы у него нет.
С удалением хуже — его не объявляет **ни один** источник.

**Документация.** Сплошная выборка всех `DELETE` из 152 страниц справочника
(2026-08-25) даёт 17 маршрутов: доски, колонки, спринты, сущности, отсутствия,
вложения, чек-листы, комментарии, внешние связи, связи, worklog, проекты, очереди.
`components` и `fields` не встречаются ни каноническим блоком, ни примером, ни
упоминанием в тексте.

**Референсный клиент.** Своего `delete` у коллекций компонентов и полей нет. Есть
базовый `Collection.delete(obj)` (`yandex_tracker_client/collections.py:205`), который
шлёт `DELETE <obj._path>` для любой коллекции, а `path` у них — адрес чтения
(`/{api_version}/components/{id}`, `/{api_version}/fields/{id}`). То есть способность
удалять выведена из общей механики базового класса, а не заявлена для этих сущностей.

Это класс «эндпоинты по аналогии» (`tests/TESTING_STRATEGY.md` §2) — тот же генератор
дефектов, что дал разобранную серию: возможность выведена, а не подтверждена.

**Что закроет:** живая проба на расходной сущности. Прогон ничего не удаляет
(решение пользователя), поэтому нужен отдельный заход с явным согласием: завести
компонент и глобальное поле специально под удаление и посмотреть ответ. Возможные
исходы — работает (документация неполна), 404/405 (инструменты не работали никогда,
как update_project и update_component).

## 4. Мелочи

- `update_board` шлёт `version` в теле; в перечне правки доски его нет, живьём это не
  мешает (доска версии не требует), отдельно не проверялось.
- `teamUserIds` у правки проекта: документация его не знает, живая проба невозможна
  (рубеж не пускает — параметр меняет живых людей). Помечен в схеме как непроверенный.
- `mcp-dev` изредка отдаёт пустой вывод; часть случаев объяснялась вызовом из корня
  монорепо (`--silent` глушит `Missing script`), остаток не выяснен.

## 5. Потери возможностей при удалении легаси-проектов (осознанные)

Вместе с семейством `/v3/projects` сняты:

- **MCP-ресурс `tracker://project/{id}`** — ресурсов стало 2 вместо 3.
- **MCP-промпт `project-summary`** — промптов стало 3 вместо 4.

Оба не перенесены на Entity API намеренно: честный перенос требует знать, какие поля
проект отдаёт на самом деле (`entityStatus`, `lead`, `issueQueues`, `start`/`end`
существуют — проверено чтением одной записи, — но состав и семантика остальных живьём
не проверялись). Перенос на непроверенных полях повторил бы способ, которым заведена
вся разбираемая серия дефектов.

**Что закроет:** живая проба состава полей проекта Entity API, затем перенос ресурса и
промпта. Объём — небольшой, но требует прогона по боевому API.

## 6. Пробелы Entity API как замены легаси-проектов

Из `inventory/projects-vs-entities.md`, живьём не проверено:

- обязательность `version` у `update_entity` — документация её как query-параметр не
  описывает вовсе; риск того же дефекта `428`, что был у проекта и компонента;
- `withBoard` у `delete_entity` документирован API, но в схеме инструмента не
  реализован;
- принимает ли `filter` ключ очереди для `entityType: 'project'`;
- словарь `entityStatus` шире легаси-статусов (`draft2`, `according_to_plan`,
  `blocked`, `cancelled`) — соответствие нигде не описано;
- формат дат сменился с `YYYY-MM-DD` на полный ISO с офсетом.

## 7. Семь кандидатов, вскрытых после заточки сверки (2026-08-25, вечер)

Ревью показало, что поиск ключа тела шёл по ВСЕЙ странице, включая раздел ответа:
имя, встречающееся только в примере ответа, засчитывалось как документированный
параметр запроса. Именно так `version` у правки доски выглядел документированным,
хотя API отвечает на него `400`.

Поиск сужен до раздела запроса — и всплыли семь строк, которых прежняя проверка не
видела. Это **кандидаты**, а не дефекты: справочник Трекера неполон, отсутствие имени
означает «проверь живьём».

| Инструмент | Ключи | Страница |
|---|---|---|
| `update_issue` | `assignee` | `api-ref/issues/patch-issue` |
| `manage_queue_access` | `queue-lead` | `api-ref/queues/manage-access` |
| `update_worklog` | `start` | `api-ref/issues/patch-worklog` |
| `update_board` | `orderBy`, `orderAsc`, `useRanking`, `country` | `api-ref/boards/patch-board` |
| `create_sprint` | `startDateTime`, `endDateTime`, `status` | `api-ref/boards/post-sprint` |
| `update_sprint` | `startDateTime`, `endDateTime` | `api-ref/boards/patch-sprint` |
| `update_global_field` | `options`, `suggest` | `api-ref/issues/patch-issue-field-*` |

Проверено выборочно: `assignee` на странице правки задачи встречается только в примере
ответа — то есть сужение поиска верное, а не ложное срабатывание. Работает ли `assignee`
на самом деле, известно из практики, но живой пробой в этом заходе не подтверждено.

**Что закроет:** живой прогон по каждому кандидату с чтением результата обратно.
Подтверждённое доезжание переносится в `LIVE_VERIFIED_KEYS`, неподтверждённое —
чинится как D9. Отдельно отмечу `update_board.orderBy`/`orderAsc`: живая проба дала
только отказ `422` при отсутствии `filter`; успешного вызова с ними не было, поэтому
из белого списка проверенного они сняты.

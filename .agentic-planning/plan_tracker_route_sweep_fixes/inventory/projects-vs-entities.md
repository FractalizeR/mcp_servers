# Легаси-инструменты проектов vs Entity API (`entityType: 'project'`)

Только чтение: код не менялся, живых вызовов не делалось. Источники —
`src/tools/api/projects/*`, `src/tracker_api/api_operations/project/*`,
`src/tools/api/entities/*`, `src/tracker_api/api_operations/entity-api/*`,
`src/tracker_api/entities/{project,entity-api}.entity.ts`, и страницы
справочника `api-ref/entities/{about-entities,create-entity,get-entity,
update-entity,delete-entity,search-entities}` (скачаны curl'ом 2026-08-25 —
кеш `sweep:doc-routes` был пуст, `SEED_PAGE` дал список маршрутов раздела).

## 1. Легаси-инструменты — параметры и возврат

| Инструмент | Вход | Возврат / особенности |
|---|---|---|
| `create_project` | `queues` (ключ ОДНОЙ очереди, обязательно), `name` (обязательно), `lead`/`status`/`description`/`startDate`/`endDate` (опционально), `fields` (обязательно — проекция ответа) | `POST /v3/projects`. `key` не принимается (сервер назначает сам). Ответ: `{ projectKey, project }` |
| `get_project` | `projectId`, `expand`, `fields` (обязательно) | `GET /v3/projects/{id}`. Ответ: `{ project }` |
| `get_projects` | `perPage`, `cursor`, `fetchAll`, `maxItems`, `expand`, `queueId` (единственный фильтр), `fields` (обязательно) | `GET /v3/projects` — **seekable** (`Link rel="seek"`, `total` из `X-Total-Count`). Курсорная пагинация + opt-in полный обход. Ответ: `{ projects[], total?, count, pagination }` |
| `update_project` | `projectId`, `version` (опционально — без него операция сама читает текущую версию лишним GET), поля из базовой схемы (все опциональны), `queues` (ключ очереди), `teamUserIds` (НЕ ПРОВЕРЕНО живьём, под подозрением как несуществующий), `fields` (обязательно) | `PATCH /v3/projects/{id}?version=`. Без `version` — `428`, проверено живой пробой 2026-08-25. Ответ: `{ projectKey, project }` |
| `delete_project` | `projectId` | `DELETE /v3/projects/{id}`. Ответ: `{ message, projectId }` |

Статусы легаси: `draft | in_progress | launched | postponed | at_risk` (нижний
регистр — расхождение с документацией создания, которая называет их в
верхнем; решает живой прогон, не тронуто).

## 2. Entity API (`entityType: 'project'`) — параметры и возврат

| Инструмент | Вход | Возврат / особенности |
|---|---|---|
| `create_entity` | `entityType='project'`, `extraFields` (объект — обязателен `summary`), `fields` (обязательно, формат `fields.<имя>`) | `POST /v3/entities/project`. Тело `{ fields: {...} }`. Ответ: `{ entity, message }` |
| `get_entity` | `entityType`, `entityId`, `fields` (обязательно, `fields.<имя>`; голый `fields` без имени отклоняется явной ошибкой — Entity API не отдаёт «все поля разом») | `GET /v3/entities/project/{id}`. Ответ: `{ entity }` |
| `find_entities` | `entityType`, `searchString`, `filter` (объект ключ-значение), `orderBy`, `orderAsc`, `rootOnly`, `perPage`, `cursor`, `fetchAll`, `maxItems`, `fields` (обязательно) | `POST /v3/entities/project/_search`. **Не seekable** — конверт `{hits, pages, values}` в теле, курсор кодирует самостоятельно собранный `page=N` (не `Link`). `filter`/`searchString`/`orderBy` — возможности, которых у `get_projects` нет вовсе |
| `update_entity` | `entityType`, `entityId`, `version` (опционально), `extraFields` (опционально), `fields` (обязательно) | `PATCH /v3/entities/project/{id}?version=`. Ответ: `{ entity }` |
| `delete_entity` | `entityType`, `entityId` | `DELETE /v3/entities/project/{id}`. Ответ: `{ success, entityType, entityId, message }` |

Поля тела create/update Entity API (документация, раздел «Проект»): `summary`
(обязательное, заменяет `name`), `teamAccess`, `description`, `markupType`,
`author`, `lead`, `teamUsers` (не `teamUserIds`), `clients`, `followers`,
`start`/`end` (формат `YYYY-MM-DDThh:mm:ss.sss±hhmm`, НЕ `YYYY-MM-DD`),
`tags`, `parentEntity`, `entityStatus`. Значения `entityStatus` для
проекта/портфеля: `draft, draft2, in_progress, according_to_plan, postponed,
at_risk, blocked, launched, cancelled` — набор шире и лексически не совпадает
с легаси (`launched` вместо `launched` ок, но нет `in_progress`→ есть, зато
нет прямого эквивалента у `draft` vs `draft2`, `according_to_plan` без пары).

Поле `issueQueues` — **есть в документации**, но помечено прямым текстом:
«Очереди, задачи которых входят в проект. Параметр доступен только для
чтения» (`about-entities`, раздел «Поля объекта issueQueues»). Ни в теле
`create-entity`, ни в теле `update-entity` параметра для ЗАПИСИ привязки
очереди нет вовсе — `issueQueues` в этих телах не упоминается.

`version` как query-параметр `update-entity` в документации явно НЕ
перечислен (раздел «Параметры запроса» страницы называет только `fields` и
`expand`), хотя `EntityApiRecord.version` в ответе присутствует всегда
(референсный клиент). Код (`entity-query.util.ts`) шлёт `?version=` по
аналогии с легаси-паттерном Трекера — не подтверждено ни документацией, ни
живой пробой.

## 3. Таблица закрытия возможностей

| Возможность легаси | Чем закрывается в Entity API | Статус |
|---|---|---|
| Постраничный обход списка (seekable, `Link`, `total` из `X-Total-Count`) | `find_entities` — курсор по `page=N` из тела `{hits,pages}`, свой независимый курсорный контракт (`fetchAll`/`maxItems` есть) | Закрыто **функционально** (агент не видит разницы: тот же наружный контракт `pagination.nextCursor`), но иначе устроено и не seekable — прыжок на произвольную страницу невозможен |
| Фильтр по очереди (`queueId`) | Нет прямого эквивалента: `filter` Entity API — фильтр по значениям полей задачи/сущности, не по составу `issueQueues`; `issueQueues` только для чтения | **Не закрыто** |
| Полнотекстовый поиск / фильтр / сортировка списка | `searchString`, `filter`, `orderBy`, `orderAsc`, `rootOnly` — возможности, которых у легаси нет вовсе | Закрыто, причём Entity API **богаче** легаси |
| Привязка очередей проекта (`queues` при создании/правке) | Отсутствует. `issueQueues` в ответе — только для чтения, вычисляется из состава задач, а не назначается | **Не закрыто** — существенный пробел |
| Статусы проекта (`draft/in_progress/launched/postponed/at_risk`) | `entityStatus` — другой словарь (`draft, draft2, in_progress, according_to_plan, postponed, at_risk, blocked, launched, cancelled`) | Частично закрыто: значения `draft`, `in_progress`, `postponed`, `at_risk`, `launched` совпадают лексически; перенос данных требует явного маппинга, 1:1 не гарантирован |
| `startDate`/`endDate` (формат `YYYY-MM-DD`) | `start`/`end`, формат `YYYY-MM-DDThh:mm:ss.sss±hhmm` (полный datetime с офсетом) | Частично закрыто: поле есть, но другой формат — клиенту легаси-строки придётся конвертировать |
| `lead` (руководитель) | `lead` — то же имя, тот же смысл (документация подтверждает) | Закрыто полностью |
| Оптимистичная блокировка версией (`version`, `428` без неё) | `update_entity` принимает `version`, `EntityApiRecord.version` есть в ответе всегда — но офиц. документация параметр `version` для `update-entity` НЕ перечисляет | Не подтверждено — вероятно закрыто, но требует живой проверки |
| `name` проекта | `summary` (другое имя поля, тот же смысл, подтверждено документацией: «summary — обязательное поле» вместо `name`) | Закрыто с переименованием |
| `teamUserIds` участники (у легаси НЕ ПРОВЕРЕНО, возможно не существует) | `teamUsers` — задокументирован явно как массив ID пользователей | Возможно закрыто лучше, чем легаси (легаси-параметр сам под подозрением) |
| Удаление проекта одним вызовом | `delete_entity` — тот же смысл; плюс недоступный в легаси `?withBoard=true` (документирован для `delete-entity`, отсутствует в схеме инструмента) | Закрыто, Entity API даже богаче по документации, но `withBoard` в MCP-схеме `delete_entity` не реализован — сам по себе отдельный, не связанный с задачей, пробел |

## 4. Чем получено и чего этот способ не видит

**Проверено чтением кода** (полностью достоверно в границах того, что
реализовано и прокомментировано в кодовой базе):
- Полный состав входных/выходных схем всех 5 легаси- и 5 entity-инструментов.
- Механика пагинации `get_projects` (seekable) и `find_entities` (курсор по
  `page` из тела) — включая известные примечания о починке `Link`
  (`pin-projects-link.util.ts`) и о неполном покрытии `fetchAll` при обрезке
  внутри страницы.
- Отсутствие в `delete_entity`/`update_entity` реализации `withBoard`.

**Проверено чтением официальной документации** (страницы
`api-ref/entities/{about-entities,create-entity,get-entity,update-entity,
delete-entity,search-entities}`, скачаны напрямую 2026-08-25, кеш
`sweep:doc-routes` не использовался — он оказался пуст на момент задачи):
- Полный список полей тела `create-entity`/`update-entity` для
  Проект/Портфель/Цель, включая `entityStatus` со словарём значений и
  формат `start`/`end`.
- Что `issueQueues` документирован явно как **read-only**.
- Что `version` НЕ упомянут в перечне query-параметров `update-entity`.
- Формат `withBoard` у `delete-entity` и конверта `{hits,pages,values}` у
  `search-entities`.

**Важное расхождение с комментарием в коде.** `entity-api.entity.ts`
утверждает: «официальная документация Трекера НЕ описывает тело
create/update Entity API (страниц `api-ref/entities/*` не существует)».
На момент этой задачи (2026-08-25) страницы **существуют и отдают 200** с
подробными таблицами полей — расхождение либо снято между написанием
комментария и сегодня, либо комментарий изначально ошибался. Не
перепроверялось, когда именно страницы появились; фиксирую как факт для
дальнейшей работы (может закрыть часть открытых вопросов в
`3_OPEN_ITEMS.md`, включая точный список полей `update_global_field`, если
там похожая ситуация).

**НЕ проверено живьём вовсе (только код + документация, оба источника
согласны, но ни один не подтверждён боевым вызовом):**
- Действительно ли `version` у `update_entity` работает как оптимистичная
  блокировка (документация его не упоминает вообще — молчание может значить
  как «не документировано, но работает по общему паттерну API», так и «не
  поддерживается для Entity API и тихо игнорируется»).
- Действительно ли `entityStatus` для проекта принимает весь заявленный
  словарь при create/update (не только используется в фильтре, как показано
  в примере `search-entities`).
- Формат `teamAccess`/`clients`/`followers`/`parentEntity`/`tags` на входе —
  документация даёт только тип поля, не пример полного тела create с ними.
- Поведение при попытке передать `issueQueues` явно в `extraFields` — просто
  игнорируется 200-м ответом, отклоняется 422, или создаёт непредсказуемое
  состояние. Документация говорит «только для чтения», но не говорит, что
  произойдёт при попытке записи.
- Совпадение состава `filter`/`orderBy` ключей у Entity API «project» с
  реальными полями (документация говорит «ключи не всегда совпадают с
  ключами задач», не даёт полного списка для проекта).

## 5. Пробелы, требующие доработки

1. **Привязка очереди к проекту (`queues` при создании/правке) — нет
   эквивалента в Entity API.** `issueQueues` — read-only, вычисляемое поле.
   Если очередь у Entity-проекта складывается автоматически (задачи этой
   очереди включены в проект через ссылку на проект в самих задачах, а не
   назначением на проекте), то у Entity API вообще нет операции «привязать
   проект к очереди» — это делается со стороны очереди/задачи, а не проекта.
   Не проверено, есть ли соответствующий параметр на очереди
   (`api-ref/queues/*`) — вне рамок этой задачи, но это единственный
   реалистичный обходной путь. **Объём:** если обходной путь существует —
   доработка тривиальна (задокументировать в description инструмента, что
   привязка делается со стороны очереди). Если обходного пути нет — это
   принципиальная потеря функциональности, закрыть кодом нельзя, только
   зафиксировать в решении об удалении легаси-инструментов.

2. **Оптимистичная блокировка `update_entity` не подтверждена.** Раз
   документация про `version` молчит, а у легаси `update_project` без
   `version` был `428` (критичная ошибка, обнаруженная только живой пробой),
   есть риск такого же скрытого дефекта у `update_entity`. **Объём:** один
   живой прогон (`PATCH .../entities/project/{id}` без и с `version`) —
   минуты, но требует расходной сущности и согласия на запись, как и
   остальные живые пробы в `3_OPEN_ITEMS.md`.

3. **Словарь статусов не совпадает 1:1** (`status` легаси ↔ `entityStatus`
   Entity API). Автоматической миграции значений «в лоб» не будет —
   `according_to_plan`, `blocked`, `cancelled`, `draft2` не имеют пары в
   легаси; обратное (`draft`, `in_progress`, `postponed`, `at_risk`,
   `launched`) совпадает лексически, но не проверено, что означает то же
   самое семантически. **Объём:** нужно явное решение/маппинг в
   description инструмента или в документации миграции, не код-фикс.

4. **Формат дат меняется** (`YYYY-MM-DD` → полный ISO с офсетом). Пользователи
   готового легаси-формата должны будут задавать `start`/`end` в новом
   формате. **Объём:** тривиально — обновить описание параметров в
   `create_entity`/`update_entity` (уже done — `extraFields` без
   отдельной типизации `start`/`end`, значит агент и так должен угадывать
   формат; стоит добавить подсказку в `description` полей, если легаси
   удаляется, чтобы не потерять discoverability формата).

5. **`filter` по очереди у `find_entities` не эквивалентен `queueId`.**
   Раз `issueQueues` — read-only и, по всей видимости, невозможно
   фильтровать список проектов по конкретной очереди через `filter` (не
   подтверждено — не проверено, какие ключи `filter` принимает для
   `entityType='project'`). **Объём:** нужна живая проба с
   `filter: {"queue": "..."}` или аналогичным ключом, чтобы либо закрыть
   пробел, либо явно объявить его неустранимым.

6. **`withBoard` у `delete_entity` не реализован в MCP-схеме**, хотя
   документация Entity API его поддерживает. Не пробел относительно
   легаси (там такого параметра тоже нет), но раз всё равно трогаем эти
   инструменты — дешёвая доработка **заодно**. **Объём:** тривиально,
   один optional-параметр в схеме + пробросить в query.

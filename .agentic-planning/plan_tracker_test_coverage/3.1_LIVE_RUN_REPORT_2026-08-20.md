## Что подтверждено рабочим

Эффект каждой мутации проверялся независимым чтением (инвариант канона), а не ответом самой мутации.

- CRUD задачи: `create_issue`, `update_issue`, `get_issues`, `find_issues`.
- Комментарии, чек-листы, связи, worklog — запись и чтение сходятся.
- `transition_issue` возвращает задачу (не описание перехода) — регрессия прошлого дефекта держится.
- Пагинация: `nextCursor` выдаётся, `hasNextPage` на неполной странице равен `false` —
  регрессия ложного `hasNextPage` держится.
- Частичный отказ `get_issues`: несуществующий ключ уходит в `errors[]` с 404, остальные отдаются.
- `bulk_update_issues` **атомарен**: один несуществующий ключ из трёх → 422, ни одна задача не
  изменена (проверено чтением). Happy path асинхронный, `get_bulk_change_status` доводит до `COMPLETE`.
- Сообщение об ошибке bulk называет виновника: `задачи [TEST-99999] не существуют`.

## Расхождения

### 1. `fieldsReturned` — эхо запроса, а не отчёт о возвращённом (системно, ~все инструменты)

Запрос `fields: ["key","totallyBogusFieldName"]` вернул тело только с `key`, а
`fieldsReturned` отдал **оба** имени. В коде везде `fieldsReturned: fields` — подставляется вход.

Почему это дорого агенту: несуществующее поле и пустое значение неразличимы. Агент не может
отличить свою опечатку от «поля нет в задаче» и уходит в неверную ветку рассуждения.

Ожидаемое: либо возвращать фактически заполненные пути, либо отклонять неизвестные имена полей,
либо переименовать в `fieldsRequested` и добавить `fieldsUnknown[]`.

### 2. Имя идентификатора задачи различается: пять вариантов

| Вариант | Где | Пример |
|---|---|---|
| `issueKey` | issues/* (одиночные) | `update_issue`, `transition_issue` |
| `issueKeys` | issues/* (batch) | `get_issues`, `get_issue_changelog` |
| `issueId` | элементы batch-массивов | `comments[].issueId`, `items[].issueId` |
| `issueIds` | comments/checklists/worklog/links/attachments | `get_comments`, `get_checklist` |
| `issues` | bulk/* | `bulk_update_issues`, `bulk_transition_issues` |

Счётчик по схемам: `issueKey` 8, `issueKeys` 3, `issueId` 20, `issueIds` 6, `issues` — все bulk.

Плюс `transitionId` (`transition_issue`) против `transition` (`bulk_transition_issues`).

Почему это дорого: агент не может обобщить контракт с одного инструмента на соседний, платит
лишним вызовом-ошибкой на каждой новой категории. В этом прогоне так потеряно 9 вызовов из 40.

### 3. `successful` в batch-ответе — то число, то массив

Канон [tests/TESTING_STRATEGY.md](../../packages/servers/yandex-tracker/tests/TESTING_STRATEGY.md) §5
требует единого `{ total, successful[], failed[] }`. Фактически:

- `successful: z.number()` — 10 инструментов (`get_comments`, `add_comment`, `get_worklogs`,
  `add_worklog`, `get_issues`, `create_link`, `add/update/delete_checklist_item`, `get_users`);
- `successful: z.array()` — 7 инструментов (`get_checklist`, `get_issue_links`, `get_attachments`,
  `get_issue_changelog`, `delete_comment`, `edit_comment`, `delete_link`).

Одно имя поля с двумя несовместимыми типами — внутри одной категории по-разному
(`checklists/add` число против `checklists/get` массив). Ошибка в форме ответа, а не в данных.

### 4. Ошибка валидации не называет причину промаха

Лишний параметр `issueIds` при отсутствующем `issueKeys` дал
`Поле 'issueKeys': ожидается array, получено undefined` — про сам `issueIds` ни слова, хотя
`additionalProperties: false`. Агенту не подсказано, что он промахнулся именем.

То же для обязательного `fields`: сообщение `ожидается array, получено undefined` не говорит
ни что поле обязательное, ни какие имена допустимы.

### 5. Пример в CLAUDE.md не соответствует контракту

`CLAUDE.md` показывает `tools:call -- fr_yandex_tracker_get_issues '{"issueIds":["PROJ-1"]}'`,
а инструмент требует `issueKeys`. Скопированный пример не работает.

### 6. `get_bulk_change_status` отдаёт лишнее без возможности сузить

Параметра `fields` у него нет, в ответе приезжает полный `createdBy` c `cloudUid`/`passportUid`.

### 7. Оснастка: `mcp-dev` не был слинкован

`npm run tools:list` падал с `sh: mcp-dev: command not found`; в `node_modules/.bin` висели
бинари удалённого ticktick. Лечится `npm install` после #402, но по документации это не очевидно.

## Яндекс.Вики — не проверена, причина транспортная

`yw_ping` → 503 за 27.5 с. Прямая проверка мимо нашего кода: `CONNECT` через прокси проходит
(`HTTP/1.1 200 Connection established`), дальше `Empty reply from server`, стабильно 3 из 3.
`api.wiki.yandex.net` резолвится в 198.18.0.17 — диапазон VPN со split-tunnelling; трекер идёт
через тот же VPN (198.18.0.18) и отвечает 200.

Вывод: с этой машины Вики недостижима на транспортном уровне. Это **не** доказывает ни падения
API Яндекса, ни дефекта нашего кода — проверку нужно повторить из другой сети.

Отдельно к удобству: 27.5 с на безнадёжный отказ — агент столько ждёт впустую.

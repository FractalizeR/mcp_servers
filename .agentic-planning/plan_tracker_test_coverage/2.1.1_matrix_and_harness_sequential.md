# 2.1.1 Фундамент этапа 2.1: матрица и оснастка (последовательно)

Пакет исполняется один, до запуска любых пакетов 2.1.2: он задаёт и матрицу, и общий способ
писать интеграционный тест. Урок 8.2 канона (`packages/servers/TESTING_STRATEGY.md`) —
механика без готовой точки употребления не считается фундаментом.

Инвентарь, на который опирается пакет: [inventory/tools-coverage-2026-08-20.md](inventory/tools-coverage-2026-08-20.md)
(92 строки, снят заново по коду 2026-08-20 на релизе 3.1.0; строка «чем получено и чего способ
не видит» — в шапке файла).

Редакция 3. История правок и их причины — §0.

## 0. Что и почему менялось

**Редакция 1 → 2 (ревью плана).** Три механизма, каждый породил несколько находок:

1. **Матрица мерила один бит, а рисовала семь колонок.** Ключом было имя файла теста, значит
   С-2, С-3, С-4 и С-6 сводились к «рядом лежит файл», и happy path на 15 строк был неотличим от
   теста обязательного состава. Плюс С-4 объявлялся закрытым на моке — против канона §2
   («уровни выше живого не наблюдают С-4 и С-5 в принципе»), у С-5 не было машинного входа
   вовсе, С-1 истинна по построению.
2. **Общие файлы под параллельной записью.** `coverage-exceptions.ts`, `COVERAGE_MATRIX.md`,
   `tests/TESTING_STRATEGY.md`, `tests/README.md` — все четыре пакеты 2.1.2 обязаны были менять
   при заявленном «общие файлы не правит никто». Лечится нарезкой реестра по категориям и явным
   владельцем остальным трём (§C).
3. **Контракт оснастки не покрывал кейсы, которые сам план объявил обязательными** —
   многошаговость, заголовки ответа, последовательность страниц, тела ошибок, утверждения (§D).

**Редакция 2 → 3 (решение по цене).** Редакция 2 лечила механизм 1 отдельным конвейером
свидетельств: оснастка пишет запись на каждый вызов, скрипт их читает. Это честно, но тащит
граблю ровно того класса, на котором проект уже горел (урок 8.1): свидетельства — производный
артефакт вне git, и `coverage:check` без свежего прогона читает вчерашние записи, давая
ложно-зелёное. Плюс vitest гоняет файлы параллельными воркерами — запись пришлось бы разводить
по воркерам.

Принято дешёвое и не менее честное решение: **обязательный состав принуждается типами**, а не
наблюдается постфактум (§A). Тогда «файл интеграционного теста существует» действительно влечёт
обязательный состав, и матрица по именам файлов перестаёт врать, оставаясь дешёвым отчётом.
Барьеры при этом — `typecheck:tests` и `coverage:check`, а не матрица.

## A. Обязательный состав принуждается фабрикой набора тестов

`tests/integration/helpers/tool-integration-suite.ts` экспортирует
`describeToolIntegration(options)` — фабрику, которая **сама порождает** общие кейсы. Поля
обязательны по типу, поэтому тест, не объявивший версию пути или тип постранички, **не
компилируется**:

| Поле | Тип | Что закрывает |
|---|---|---|
| `tool` | имя инструмента | строка матрицы |
| `expectedRequests` | `[{ method, path, apiVersion }]`, непустой | С-4: версия объявлена явно |
| `happyPath` | вход + фикстура ответа | С-3 через `outputSchema` |
| `invalidInput` | вход, который обязан отвергнуться | С-2: без HTTP-запроса |
| `errors` | коды, минимум 403 и 404 | С-6 |
| `batch` | кейс смешанного исхода либо `'not-applicable'` | С-6 |
| `pagination` | `'cursor' \| 'offset' \| 'link' \| 'none'` (+ кейс страниц) | С-6, требование «тип зафиксирован явно» |

Что это чинит: состав перестаёт быть декларацией в плане (`tests/TESTING_STRATEGY.md`:127 —
«декларация без барьера не значит ничего») и становится сигнатурой. `not-applicable` и `'none'`
— тоже объявление: автор обязан их написать, и они видны в ревью.

Чего это не видит: `describe.skip` оставляет файл на месте, а осмысленность ожиданий типами не
проверяется. Первое закрывается запретом `.skip` в `coverage:check` (§B), второе — только ревью,
и это записано в шапке матрицы, а не подразумевается.

Особенное пишется обычными `it()` рядом с фабрикой: многоступенчатые потоки
(`download_attachment`, `get_thumbnail`, `delete_component`, `transition_issue`) в шаблон не
укладываются и укладываться не обязаны. Фабрика закрывает общее, не превращаясь в прокрустово
ложе.

## B. Скрипт матрицы

`packages/servers/yandex-tracker/scripts/build-coverage-matrix.ts`, команды
`npm run coverage:matrix` и `coverage:check`, вывод — `tests/COVERAGE_MATRIX.md`. Строки —
инструменты из `TOOL_CLASSES` (реестр, а не обход файлов: обход не видит незарегистрированный
инструмент). Источники: наличие файлов тестов по базовому имени инструмента и реестр исключений
(§C).

Клетка называет **уровень наблюдения**, а не факт покрытия:

| Значение | Смысл |
|---|---|
| `unit` / `мок` / `живьём` | свойство наблюдалось на этом уровне, ссылка на тест; для `мок` состав кейсов принуждён типами фабрики |
| `мок (устаревшая оснастка)` | интеграционный тест есть и не пропущен, но написан до фабрики (на `mock-server.ts`): свойство наблюдалось, обязательный состав кейсов **не гарантирован** |
| `мок (гипотеза)` | наблюдалось только на моке там, где канон объявляет мок неспособным свидетельствовать |
| `не наблюдалось` | ни один уровень свойства не проверял |
| `исключение: причина` | сознательно не проверяется, ссылка на реестр §C |

Соответствие «свойство ↔ свидетельство» объявляется в скрипте один раз и печатается в шапке
отчёта вместе с оговорками:

| Свойство | Что считается свидетельством | Оговорка |
|---|---|---|
| С-1 | инструмент в `TOOL_CLASSES`, покрыт общим набором `tests/smoke` | истинна по построению для всех 92; отключение категории через `DISABLED_TOOL_GROUPS` этой колонкой **не** наблюдается |
| С-2 | интеграционный тест на фабрике (поле `invalidInput` обязательно) | — |
| С-3 | фабрика сверяет happy path с `outputSchema` | тест семи представителей общий, за конкретный инструмент не отвечает |
| С-4 | фабрика требует `apiVersion` в каждом ожидаемом запросе | **на моке это гипотеза, а не наблюдение** (канон §2); снимается только этапом 3.1 |
| С-5 | запись живого прогона | на моке не наблюдается никогда |
| С-6 | поля `errors`, `batch`, `pagination` обязательны | — |
| С-7 | тест обнаружимости и размера ответа | этап P2, вне 2.1 |

Ключ сопоставления «инструмент ↔ тест» — базовое имя файла инструмента; тест, покрывающий
инструмент под другим именем, скрипту не виден. Слепое пятно печатается в шапке отчёта.

Режим `coverage:check` требует наличия теста по **С-2, С-3, С-4, С-6** — тем, что уровень мока
способен наблюдать, — и падает на `describe.skip`/`it.skip` в интеграционных тестах инструментов.
С-1 не проверяет (истинна по построению), С-5 и С-7 исключены явно: иначе шаг требует 92
фиктивные записи «исключение, потому что этап другой», и реестр перестаёт значить что-либо.
Клетки `мок (устаревшая оснастка)` дырами не считаются: 33 теста, написанных до фабрики, что-то
проверяют, и объявить их дырой значит потребовать миграции, которой этот этап не занимается.
Приравнять их к `мок` тоже нельзя — состав в них на совести автора, ровно ради чего фабрика и
заведена. Отсюда третья оценка и третье число долга.

Отчёт печатает три числа долга: «С-5 не наблюдалось: N» (объём этапа 3.1), «С-7 не наблюдалось: N»
(объём P2) и «на устаревшей оснастке: N» (объём возможного этапа миграции). Долг обязан быть
видимым числом, иначе он растворяется в зелёном.

Подключение шага: скрипт в `package.json` пакета, задача в `turbo.json`, имя задачи в
`TURBO_TASKS_COMMON` внутри `scripts/validate.sh` — три правки, а не одна. Добавляется **после**
закрытия дыр 2.1.2, иначе шаг красный с первого дня и его отключат.

## C. Реестр сознательных исключений — по одному файлу на категорию

`tests/coverage-exceptions/{категория}.ts`, каждый экспортирует список
`{ tool, property, reason, replacedBy }`; `index.ts` сводит их и пишется в этом пакете. Единый
файл был бы точкой конфликта минимум восьми пакетов из тринадцати.

Не Markdown: реестр читает скрипт, а рассинхрон таблицы и кода — тот самый класс дефекта,
который этап и закрывает. Реестр исключений живых прогонов (`tests/TESTING_STRATEGY.md` §1)
остаётся источником причин для С-5; запись ссылается на его строку, а не переписывает её.

**Владельцы общих артефактов после этого пакета:**

| Артефакт | Кто правит |
|---|---|
| `tests/coverage-exceptions/{категория}.ts` | пакет своей категории |
| `tool-integration-suite.ts`, `api-expectation.ts`, `coverage-exceptions/index.ts`, `mock-server.ts`, `templates/` | никто после 2.1.1 |
| `COVERAGE_MATRIX.md` | оркестратор, регенерацией после каждой волны |
| `tests/TESTING_STRATEGY.md`, `tests/README.md` | оркестратор, по строкам из отчётов пакетов |

## D. Оснастка под фабрикой

Существующий `tests/integration/helpers/mock-server.ts` — 1726 строк рукописных методов вида
`mockCreateComponentSuccess`, по методу на инструмент. Для 59 инструментов это точка конфликта
параллельных пакетов и рост файла втрое.

Уточнение ревью, которое стоит держать в уме: машинного давления против разнобоя в тестах в
проекте **нет** — `cpd` сканирует только `src`, `eslint` в пакете тоже (`lint` = `eslint src
scripts`). Поэтому единственный барьер против тринадцати способов — фабрика и типы: то, что в
них не предусмотрено, будет написано тринадцатью способами.

### D.1 Ожидания запросов

`tests/integration/helpers/api-expectation.ts` — слой, на котором работает фабрика и который
доступен напрямую для особенных кейсов:

- `expectRequest({ method, path, apiVersion, query?, body? })` → `.reply(status, body, headers?)`;
- `apiVersion` сверяется с префиксом пути: v2 вместо v3 отвечает 200 и молча отдаёт другую форму
  — это и есть дефект, ради которого пишется С-4;
- **порядок** ожиданий значим, нарушение роняет тест: `delete_component` (GET → DELETE),
  `transition_issue` (`_execute` → GET), `download_attachment` и `get_thumbnail` (вторая ступень
  по значениям из первого ответа);
- **несколько ответов на один запрос** — страница 1, затем страница 2;
- **заголовки ответа** — без них не зафиксировать `Link rel="next"` и `rel="seek"`, то есть не
  выполнить кейс пагинации вовсе;
- незаявленный запрос роняет тест; заявленный, но не случившийся — роняет на
  `assertAllExpectationsMet()`.

### D.2 Утверждения

Живут внутри фабрики и доступны отдельно для особенных кейсов:
`assertMatchesOutputSchema` (обе проекции ответа), `assertNoWarnings` / `assertWarnings`
(инвариант «только когда непусто» на `content[0].text` **и** `structuredContent`, канон §6),
`assertNoHttp`, `assertBatchShape`, `assertPagination`. Тела ошибок — существующие
`generateError403/404`: форма ошибки в тринадцати пакетах должна быть одна.

### D.3 Совместимость

`mock-server.ts` не переписывается и не удаляется: 33 существующих теста продолжают работать на
нём. Новые тесты пишутся только через фабрику.

### D.4 Фикстуры

Источник — `tests/helpers/*.fixture.ts` (29 файлов, включая `agile.fixture.ts` с досками и
спринтами, `entity-api.fixture.ts`, `worklog.fixture.ts`, `bulk-change.fixture.ts`,
`project.fixture.ts`), **не** `tests/integration/templates/` — там всего пять сущностей
(comment, component, issue, queue, user), и на половину пакетов их не хватает.

Для полей, фильтров и локальных полей очереди фикстур нет нигде. Пакет, которому они нужны,
заводит свой `tests/helpers/{категория}.fixture.ts` — новый файл в своём наборе, не правка чужого.

## E'. Две формы вызова фабрики

`describeToolIntegration` — полный контракт для инструментов, делающих HTTP-запросы.
`describeNoHttpToolIntegration` — урезанный, для инструментов, у которых запросов нет вовсе
(`demo`, `get_issue_urls`): у них `errors`, `batch` и `pagination` не «не проверены», а физически
неприменимы, и требовать их значит вынуждать исполнителя написать фиктивный кейс.

Матрица обязана различать формы: клетки С-4 и С-6, полученные через урезанный контракт, несут
значение «неприменимо: инструмент не делает HTTP-запросов», а не `мок` и не `дыра`. Детектор
скрипта опознаёт обе формы поимённо — ошибка шва, найденная вторым раундом ревью: он знал только
полную форму, и честный тест на второй давал ложное «нет интеграционного теста».

## E. Точка употребления

`create_board` покрывается через фабрику в этом же пакете и служит образцом: мутирующий,
категория живьём не проверяется вовсе, и на нём видно расхождение версий (§F). После сдачи пакета
файл доступен пакету P1 только на чтение.

## F. Расхождения версий API, вскрытые инвентарём

Таблица версий в `packages/servers/yandex-tracker/CLAUDE.md` не упоминает доски, спринты, поля,
фильтры, Entity API и users. Внутри одного предмета версии расходятся:

| Предмет | Наблюдаемые пути | Вопрос |
|---|---|---|
| доски | `/v2/boards`, но `/v3/boards/{id}/columns` | доска и её колонки в разных версиях |
| спринты | `/v2/sprints`, `/v2/boards/{id}/sprints`, но `/v3/sprints/{id}/_start` | жизненный цикл в другой версии |
| поля | `/v2/fields`, но `/v3/queues/{id}/localFields` | глобальные и локальные в разных версиях |
| фильтры | `POST /v3/filters/`, `GET /v3/myself/favorites/filters` | завершающий слэш; путь чтения из механики SDK |
| очереди | `POST /v3/queues/` | завершающий слэш |
| Entity API | `/v3/entities/{type}` | в таблице версий отсутствует |

Пакет **не чинит** эти пути: правка версии без ответа боевого API — замена одной гипотезы другой
(канон §5). Наблюдаемое поведение фиксируется тестами как есть, строки заводятся в
`tests/TESTING_STRATEGY.md` §2 как гипотезы для этапа 3.1. Завершающий слэш — отдельным пунктом:
под рубежом области действия редиректы запрещены, поэтому путь, отвечающий редиректом, живьём
упадёт, и это наблюдение, а не дефект рубежа.

Таблица составлена по прогону `enumerate:requests`; с документацией Трекера и
`yandex_tracker_client/` она не сверена — это работа пакетов 2.1.2 по своим категориям.

## DoD

- фабрика `describeToolIntegration` порождает общие кейсы; **проверено попыткой**: тест без
  `apiVersion` и тест без объявленного `pagination` не проходят `npm run typecheck:tests`;
- `npm run coverage:matrix` строит `tests/COVERAGE_MATRIX.md`: 92 строки, каждая клетка —
  значение из перечисления §B, шапка печатает оговорки и слепое пятно;
- `coverage:check` падает на инструменте без интеграционного теста и на `describe.skip`, зелен на
  реестре исключений — проверено попыткой, а не декларацией;
- оснастка покрыта собственным тестом: незаявленный запрос роняет, неслучившийся заявленный
  роняет, неверная версия роняет, нарушенный порядок роняет;
- **проверено отдельно:** незаявленный запрос роняет тест внятно, а не четырьмя попытками retry.
  Гипотеза ревью: `axios-mock-adapter` бросает обычную ошибку, а `HttpClient` её ретраит — так уже
  было с `ScopeViolationError`, который пришлось исключать из retry специально. Подтвердится —
  оснастка обязана обойти retry, иначе диагностика врёт;
- образцовый интеграционный тест `create_board` зелёный;
- строки про расхождения версий и завершающие слэши записаны в `tests/TESTING_STRATEGY.md` §2;
- корневой `npm run validate:quiet` зелёный (шаг `coverage:check` — после 2.1.2).

## Границы пакетов

Каждый пакет пишет в свой каталог `tests/integration/tools/api/{категория}/` и в свой
`tests/coverage-exceptions/{категория}.ts`. Нужный, но отсутствующий файл фикстур пакет заводит
как `tests/helpers/{категория}.fixture.ts` — новый файл, не правка чужого.

**Общие файлы не правит никто:** `api-expectation.ts`, `coverage-exceptions/index.ts`,
`mock-server.ts`, `templates/`, `COVERAGE_MATRIX.md`, `tests/TESTING_STRATEGY.md`,
`tests/README.md`, образец `create_board`. Матрицу регенерирует оркестратор после каждой волны;
строки в `TESTING_STRATEGY.md` и `README.md` пишет оркестратор по отчётам пакетов. Нужда изменить
общий файл — сигнал вернуть пакет оркестратору, а не править в обход.

## Обязательный состав интеграционного теста

Тест пишется через фабрику `describeToolIntegration` из 2.1.1 — она порождает общие кейсы сама,
а её поля обязательны по типу. Тест, не объявивший версию пути или тип постранички, **не
компилируется**: состав принуждается `typecheck:tests`, а не доверием к отчёту исполнителя.

| Поле фабрики | Что обязан объявить исполнитель |
|---|---|
| `expectedRequests` | метод, путь и **версию** каждого запроса |
| `happyPath` | вход и фикстуру ответа — сверяется с `outputSchema` |
| `invalidInput` | вход, который обязан отвергнуться без HTTP |
| `errors` | минимум 403 и 404 |
| `batch` | кейс смешанного исхода либо `'not-applicable'` |
| `pagination` | `'cursor' \| 'offset' \| 'link' \| 'none'` — тип постранички именно этого эндпоинта; тест с соседнего не переносится (`tests/TESTING_STRATEGY.md` §4) |

Инвариант `warnings` («поля нет, когда предупреждений нет», обе проекции ответа) фабрика
проверяет во всех порождённых кейсах — объявлять его не нужно.

Особенное — многоступенчатые потоки — пишется обычными `it()` рядом с фабрикой, на
`api-expectation.ts` напрямую. Фабрика закрывает общее и прокрустовым ложем быть не должна.

Приоритет внутри пакета: сначала деструктивные, затем прочие мутирующие, затем читающие.

## Пакеты, где мок — единственная проверка

P1, P2, P3, P4, P5, P9 целиком лежат в реестре исключений живых прогонов
(`tests/TESTING_STRATEGY.md` §1): доски, колонки, спринты, проекты, глобальные поля, цели и
Entity API, сохранённые фильтры выходят за пределы очереди `TEST` по природе. Для них С-4 и С-5
живьём не наблюдаются никогда, и в матрице их клетка С-4 получает значение `мок (гипотеза)`.
Отсюда два требования сверх общего состава:

- путь и версия каждой операции сверяются с внешним источником истины (документация Трекера,
  затем `yandex_tracker_client/`), а **не** с нашим же кодом операции: сверка с собственным кодом
  доказывает лишь его самосогласованность. Машинного следа этот акт не оставляет — он живёт в
  отчёте исполнителя и проверяется ревью, что и записано в шапке матрицы;
- расхождение с источником не чинится в пакете: строка уходит оркестратору для
  `tests/TESTING_STRATEGY.md` §2 как гипотеза этапа 3.1.

## Особые случаи, известные заранее

- `download_attachment` и `get_thumbnail` строят второй путь по значениям из ответа на первый
  (перечисление видит только `GET /v2/issues/{key}/attachments`). Обе ступени обязательны, иначе
  С-4 второй ступени не проверен ничем. Порядок ожиданий — из оснастки §D.1.
- `delete_component` делает `GET` перед `DELETE`; `transition_issue` — `GET` задачи после
  `_execute` (регрессия из §3 канона: возвращал описание перехода вместо задачи). Обе фиксируются
  целиком, а не одной мутацией.
- `raw_api_request` (P13): детектор `warnings` там обязан быть **выключен** — проверяется входом с
  заведомо неизвестным именем параметра, поле не появляется.
- `ping`, `demo` и `get_issue_urls` HTTP не делают (у `ping` он есть — `GET /v3/myself`, у двух
  других нет вовсе). Решение изменено после ревью шва: P13 пишет для них тест через вторую форму
  фабрики `describeNoHttpToolIntegration` (урезанный контракт: без `errors`, `batch`,
  `pagination`) и записей в реестр исключений на них **не заводит**. Прежняя редакция предписывала
  обратное — запись вместо теста; это противоречило коду, где вторая форма заведена именно ради
  этих трёх, и при исполнении обоих указаний сразу реальный тест оказывался в матрице невидим.
  Настоящий тест — свидетельство лучшего сорта, чем запись «проверять нечем».
- `download_attachment` и `get_thumbnail` помечены W, но наблюдаемый запрос у них `GET`. В
  приоритете «сначала мутирующие» они не первые — приоритет ведётся по наблюдаемому методу.

## DoD пакета

- каждый инструмент пакета имеет либо интеграционный тест обязательного состава, либо запись в
  `tests/coverage-exceptions/{категория}.ts` с причиной и замещающей проверкой;
- `npm run typecheck:tests` и `npm run coverage:check` зелены по категории пакета;
- корневой `npm run validate:quiet` зелёный (не пакетный: пакетный не содержит `validate:docs`
  для корневых доков, `format:check`, `check:tool-contract-ratchet` и порогов покрытия);
- отчёт исполнителя перечисляет: инструменты пакета, тип постранички каждого пагинируемого
  эндпоинта, расхождения с источником истины (или явное «расхождений нет»), строки, которые
  оркестратор должен внести в `TESTING_STRATEGY.md`.

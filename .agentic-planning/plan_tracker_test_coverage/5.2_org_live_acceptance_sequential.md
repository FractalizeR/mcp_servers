# 5.2 Живая приёмка мутирующих инструментов (последовательно)

Продолжение [3.1](3.1_live_acceptance_sequential.md), закрывшего мутации внутри очереди `TEST` на
API v2. Здесь закрывается остаток: мутирующие маршруты **на v3** и семейства уровня организации,
живьём не вызывавшиеся ни разу. Предусловие — этап [5.1](5.1_org_scope_guard_sequential.md) сдан:
до него рубеж отклонит собственные запросы прогона.

Параллельных прогонов этап не выдерживает: журнал один, одноразовая очередь одна. Ведёт основной
поток, не субагенты — цена ошибки здесь боевые данные компании, а не упавший тест.

## Что именно неизвестно

Мутирующие маршруты v3 не выполнялись ни разу: известно только, что путь обслуживается (по нему
проходил GET). Счёт ведётся **по инструментам** — раздел D/E артефакта перечисления содержит 26
инструментов уровня организации, у части из них маршрутов больше одного
(`manage_sprint_lifecycle` — три). Списка «неподтверждённых маршрутов» отдельной таблицей в
артефакте нет; первым шагом этапа она туда дописывается, иначе DoD не по чему проверять.

Слабее прочих три позиции. У `POST /v3/bulkchange/_move`, `_transition`, `_update` не подтверждён
и сам маршрут: оракул показал только `/v3/bulkchange/{id}`, подпути взяты по аналогии с v2. Форма
записи worklog на v3 **нами не наблюдалась** — во всех проверенных задачах worklog пуст; это факт о
выборке, а не о API. `GET /v3/bulkchange/{operationId}` наблюдался только отказом на заведомо
неверном идентификаторе.

Состав мутирующих инструментов и вердикты рубежа по каждому —
[inventory/mutating-tools-2026-08-25.md](inventory/mutating-tools-2026-08-25.md).

## Правила прогона

1. **Эффект проверяется независимым чтением**, а не ответом самой мутации (инвариант канона).
2. **Две сущности на семейство:** одна остаётся пользователю после `create`/`update`, вторая
   создаётся под проверку удаления и удаляется этим же прогоном. Удаляется только созданное этим
   прогоном и только по идентификатору из журнала.
3. **Глобальные поля проверяются удалением первым.** Порядок обратный обычному: создаётся одно
   поле, немедленно проверяется его удаление, и лишь при успехе создаётся второе — под
   `create`/`update`. Основание процедуры сознательно слабое: `DELETE /v3/fields/{id}` подтверждён
   только нашим собственным кодом, страницы документации найти не удалось (таблица 2 артефакта), а
   наш код источником истины не является. Неудача удаления при обычном порядке дала бы два
   неудаляемых поля в форме задач всей компании вместо одного.
   **К фильтрам это правило не применяется:** инструмента удаления фильтра нет
   (`src/tracker_api/api_operations/filter/` — только create/update/get), а `raw_api_request`
   доступен только на чтение. Проверить удаление изнутри прогона нечем — см. семейство 13.
4. **Имя всякой создаваемой сущности несёт префикс прогона** — этого требует рубеж 5.1, и по нему же
   находится остаток, если журнал потерян.
5. Канал — `mcp-dev` (`tools:call` / `tools:batch`) с `--dangerously-allow-write`, по пересобранному
   бандлу. Устаревший `dist` уже маскировался под флак (канон §8.1).
6. Накопленные ранее задачи очереди `TEST` не трогаются: рубеж их и не пропустит (не в журнале), а
   пользователь просил их сохранить. Задачи под bulk создаются прогоном.

### Особенности отдельных семейств

**7 — массовые операции.** `_move` проверяется переносом задач прогона в одноразовую очередь
(правило C после правки 5.1 допускает `sandboxQueue` и `disposableQueue`). Следствие, которое надо
держать в голове: **при переносе ключ задачи меняется**, а журнал знает старый — дальнейшие
операции над перенесённой задачей рубеж отклонит. Поэтому `_move` идёт последним по этим задачам, и
перенесённые задачи уходят вместе с одноразовой очередью, когда пользователь её удалит. Порядок
семейств 7 и 14 из-за этого связан: очередь создаётся до массовых операций.

**10 — спринты.** Уборка спринта — явная операция `manage_sprint_lifecycle` с `action: 'delete'`
(`manage-sprint-lifecycle.operation.ts:43`), а не наблюдение после удаления доски. Гипотеза
«спринт уйдёт вместе с доской» не нужна и не проверяется. Второй спринт остаётся пользователю.

**13 — фильтры.** Независимое чтение здесь под вопросом, и это надо назвать до прогона:
`get_filters` ходит в `GET /v3/myself/favorites/filters`
(`src/tracker_api/api_operations/filter/get-filters.operation.ts:8-13`), то есть читает **избранное**
текущего пользователя, а не список фильтров; `/v3/filters` на GET отвечает 405. Созданный фильтр в
избранном может не появиться — тогда эффект `create_filter` независимым чтением не подтверждается
вовсе, и это идёт в отчёт как незакрытая позиция, а не как успех. Удаление фильтра изнутри прогона
недоступно; остаток убирает пользователь в интерфейсе.

**14 — одноразовая очередь.** Ключ `TESTTEST` (схема `^[A-Z]{2,10}$`, `create-queue.schema.ts:15`
пропускает). Переиспользуем ли ключ удалённой очереди — неизвестно; если повторный прогон упрётся в
занятый ключ, следующий берётся по схеме `TESTTESTB`, `TESTTESTC`. Инструмента удаления очереди у
нас нет вовсе — очередь убирает пользователь в интерфейсе.

## Отдельно проверить

- **Версия по факту ответа, а не по коду.** После миграции 4.1 весь код на v3; прогон обязан
  подтвердить это наблюдением каждой мутации.
- **`get_filters` читает избранное, а не фильтры** — путь установлен живой пробой, гипотезой
  остаётся эквивалентность «избранное = список фильтров». Проверяется в семействе 13.
- **`warnings` в бою** — введён 3.0.0, живьём проверен одним сценарием.
- **Классификация `get_thumbnail` и `download_attachment`.** Помечены пишущими, потому что пишут
  файл на диск, и без `--dangerously-allow-write` не вызываются, хотя данных Трекера не меняют.
  Решение по классификации принять по итогу прогона.
- **Ветки, которых не видел энумератор:** `manage_sprint_lifecycle` `archive` и `delete`.
  `manage_queue_access` в этот список не входит — оба его `action` бьют в один и тот же `PATCH`
  (`manage-queue-access.operation.ts:49`); проверить `remove` живьём полезно, но по другой причине.
- **Форма ответа Entity API** — какие поля идентификатора приходят (`id`, `shortId`); от неё
  зависит строка таблицы регистрации в 5.1.

## DoD

- отчёт файлом `5.2_LIVE_RUN_REPORT_2026-08-25.md`: по каждому инструменту — вызван/нет, версия по
  факту ответа, расхождение с контрактом или его отсутствие;
- каждое расхождение либо исправлено с регрессионным тестом, либо заведено отдельной задачей;
- **перечень созданного**: имя, идентификатор, чем создано, статус — «удалено прогоном при проверке
  удаления» либо «оставлено пользователю»; оставленное пользователь убирает сам;
- перечень созданного совпадает с журналом рубежа построчно; число отказов рубежа за прогон названо,
  каждый разобран в отчёте. Журнал доказывает, что создано, но не доказывает, куда прогон не ходил, —
  формулировка «не вышли за границы» этим не проверяется и потому не используется;
- каждый инструмент раздела D/E артефакта (26 штук) и каждый маршрут из таблицы, дописанной первым
  шагом этапа, либо закрыт наблюдением, либо назван с причиной, по которой остался незакрытым.

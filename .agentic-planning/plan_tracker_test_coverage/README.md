# План: доказательное покрытие инструментов Трекера

Преемник `plan_functional_testing_tracker_tools`, закрытого 2026-08-20. Тот план ответил на
вопрос «что проверить, чтобы утверждать, что инструменты работают», и его этап живого прогона
вскрыл семь расхождений контракта. Расхождения закрыты релизом 3.0.0
([отчёт до](3.1_LIVE_RUN_REPORT_2026-08-20.md), [отчёт после](3.2_LIVE_REVERIFY_REPORT_2026-08-20.md),
[принятые решения](CONTRACT_UNIFICATION_DECISIONS.md)).

**Что осталось:** сам вопрос покрытия. Контракт теперь единый, но утверждение «все 92 инструмента
работают» по-прежнему держится на выборочных проверках, а не на матрице.

Канон — [packages/servers/TESTING_STRATEGY.md](../../packages/servers/TESTING_STRATEGY.md)
(свойства С-1..С-7, канон предупреждений, два процессных урока) и
[tests/TESTING_STRATEGY.md](../../packages/servers/yandex-tracker/tests/TESTING_STRATEGY.md).

## Инвентарь (снят заново 2026-08-20, после релиза 3.0.0)

**Чем получено:** обход `src/tools/**/*.tool.ts`, сопоставление с `tests/**` по имени файла;
флаги из `*.metadata.ts` (`readOnlyHint`, `destructiveHint`).
**Чего способ не видит:** тесты, покрывающие инструмент под другим именем файла или списком внутри
одного файла; покрытие через workflow-сценарии. Числа ниже — нижняя граница покрытия.

| Показатель | Значение |
|---|---|
| Инструментов | 92 |
| Мутирующих (`readOnlyHint` не выставлен) | 52 |
| Деструктивных (`destructiveHint: true`) | 14 |
| Без unit-теста | 5 |
| Без интеграционного теста | 59 |

Пять без unit-теста — все про вложения и worklog: `upload-attachment`, `download-attachment`,
`delete-attachment`, `get-thumbnail`, `delete-worklog`. Первые четыре работают с бинарными
данными, то есть ровно тот класс, где мок дешевле всего расходится с реальностью.

## Приоритеты

1. **P0 — оснастка области действия.** Отдельной тестовой организации нет, песочница — очередь
   `TEST` боевой. Сейчас единственная защита от выхода за её пределы — аккуратность того, кто
   ведёт прогон. Это обязано стать машинным: программный белый список, отклоняющий любой не-GET
   запрос за пределы сущностей `TEST`, созданных текущим прогоном. Пока его нет, остальные этапы
   живого уровня запускать нельзя.
2. **P0 — 26 мутирующих инструментов без интеграционного теста**, из них 9 деструктивных
   (`delete_board`, `delete_board_column`, `delete_component`, `delete_entity`,
   `delete_global_field`, `delete_project`, `delete_worklog`, `clear_goal_key_results`,
   `set_goal_key_results`, `manage_sprint_lifecycle`). Ошибка здесь необратимо портит данные.
3. **P1 — целые непокрытые категории**: boards, sprints, entities/goals, projects, fields, filters.
4. **P1 — бинарные инструменты** (5 без unit-теста).
5. **P2 — С-7**: discoverability и размер ответов. Здесь же проверить на практике, помогает ли
   новый канал `warnings` — он введён 3.0.0 и живьём проверен лишь одним сценарием.

## DoD

- ни один инструмент не остался без строки в матрице со значением «покрыт тестом X» либо
  «сознательно не покрывается, причина»;
- белый список области действия покрыт тестом, который доказывает, что запрос за пределы `TEST`
  отклоняется — проверяется попыткой, а не декларацией;
- `npm run validate` зелёный.

## Хвосты, не относящиеся к покрытию

- **Мусор в песочнице:** `TEST-19`, `TEST-20`, `TEST-21` (прогон 2026-08-20, помечены
  `[live-2026-08-20]`), на `TEST-19` комментарий, пункт чек-листа, связь и worklog.
  Инструмента удаления задачи в сервере нет — убирать вручную. Отдельный вопрос: нужен ли он вообще.
- **Вики:** `yw_ping` даёт 503, причина транспортная (VPN split-tunnelling), не дефект кода.
  Проверить из другой сети. Разведение двух механизмов `fields` вынесено отдельной задачей.
- **Защита `main`:** сейчас её нет, поэтому `gh pr merge --auto` вырождается в немедленный мерж —
  PR #403 влился при бегущем CI. Рабочая связка (не проверена): `required_status_checks` плюс
  bypass для релизного токена, иначе semantic-release не сможет пушить тег.

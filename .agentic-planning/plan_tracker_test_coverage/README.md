## Целевая версия API — v3 (решено 2026-08-23)

v2 у Трекера живёт на совместимости, документация описывает только v3. Стабилизировать
поведение на v2 значит делать работу дважды, поэтому **цель — v3 всюду, где v3 существует**;
план миграции — [4.1](4.1_v3_migration_parallel.md).

Следствие для порядка: миграция идёт **до** волны 2 этапа 2.1.2, иначе волна напишет тесты,
прибивающие v2 у worklog, вложений и чек-листов, и их придётся переделывать. Рабочий порядок:
**4.1 → 2.1.3 → волна 2 → 3.1**.

## Приоритеты

1. **P0 — оснастка области действия.** Отдельной тестовой организации нет, песочница — очередь
   `TEST` боевой. Сейчас единственная защита от выхода за её пределы — аккуратность того, кто
   ведёт прогон. Это обязано стать машинным: программный белый список, отклоняющий любой не-GET
   запрос за пределы сущностей `TEST`, созданных текущим прогоном. Пока его нет, остальные этапы
   живого уровня запускать нельзя.
2. **P0 — 31 мутирующий инструмент без интеграционного теста**, из них 9 деструктивных
   (`delete_board`, `delete_board_column`, `delete_component`, `delete_entity`,
   `delete_global_field`, `delete_project`, `delete_worklog`, `clear_goal_key_results`,
   `set_goal_key_results`, `manage_sprint_lifecycle`). Ошибка здесь необратимо портит данные.
3. **P1 — целые непокрытые категории**: boards, sprints, entities/goals, projects, fields, filters.
4. **P1 — бинарные инструменты** (5 без unit-теста).
5. **P2 — С-7**: discoverability и размер ответов. Здесь же проверить на практике, помогает ли
   новый канал `warnings` — он введён 3.0.0 и живьём проверен лишь одним сценарием.

## Установлено волной 1 этапа 2.1.2 (2026-08-23)

**Разрыв версий API системен, но не аварийный.** Документация называет v3 для проектов, досок,
спринтов и глобальных полей, код ходит в v2. Боевой опыт
([отчёт](inventory/live-version-probe-2026-08-23.md)) показал: **v2 отвечает, число элементов и
набор ключей совпадают с v3** — это работающий алиас, инструменты не сломаны. Миграция плановая.

**Настоящий дефект оказался в типах, а не в версиях.** Тот же опыт: `options` у глобального поля
— `boolean`, а не массив опций, как объявлено в `field.entity.ts`; `id` у досок, колонок досок и
спринтов — число, а объявлено `string`. Мок этого не поймал бы никогда, потому что отдаёт
предписанное. Это же и есть довод в пользу этапа 3.1.

**`yandex_tracker_client/` источником истины по версии не является** — там версия параметр
соединения, поэтому submodule подтверждает нашу v2 тавтологически. Путь и метод им проверять
можно, версию нельзя.

**Рубеж области действия делает часть вопросов непроверяемой нашими инструментами.** Проекты,
доски, спринты, глобальные поля лежат вне очереди `TEST`, поэтому мутации по ним fail-closed
отклоняются — вопросы «`PUT` или `PATCH`» и «потерянный `version`» этап 3.1 закрыть не сможет без
отдельного механизма для сущностей уровня организации.

  «сознательно не покрывается, причина»;

## Возможный этап: миграция 33 тестов на фабрику

Вскрыто исполнением 2.1.1. Тридцать три интеграционных теста написаны до фабрики, на
`mock-server.ts`; они что-то проверяют, но обязательного состава кейсов в них не гарантирует
ничто. В матрице они получают отдельную оценку `мок (устаревшая оснастка)` и отдельное число
долга. Отдельным этапом не планируется, пока не закрыты 58 инструментов без тестов вовсе:
мигрировать оснастку под тестами, которые есть, дешевле, чем писать отсутствующие.

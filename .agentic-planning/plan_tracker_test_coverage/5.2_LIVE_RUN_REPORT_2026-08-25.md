# Отчёт живого прогона 5.2 — 2026-08-25

Метка прогона `live-2026-08-25`, префикс имён `[live-2026-08-25]`, очередь `TEST`,
одноразовая очередь `TESTTEST`, владелец `vr`. Канал — `mcp-dev` по пересобранному бандлу.
Эффект каждой мутации проверялся независимым чтением.

## Дефекты

### D1. `create_component` бьёт в маршрут, которого нет (BLOCKER)

`POST /v3/queues/TEST/components` → `405 POST is not allowed ([GET])`. До миграции 4.1 путь был
`POST /v2/queues/{q}/components` — тот же по форме, то есть **создание компонента не работало
никогда**, и моки это скрывали. Референсный клиент (`collections.py:366`) адресует коллекцию как
`/{version}/components/{id}` — создавать надо `POST /v3/components` с очередью в теле.
Чинится вместе с правилом рубежа: `POST /v3/components` сейчас падает в fail-closed.

### D2. Имя идентификатора расходится у соседних инструментов (подтверждение дефекта 3.1 №2)

- `add_checklist_item` возвращает `itemId`, `delete_checklist_item` принимает `itemId`,
  а `update_checklist_item` требует `checklistItemId`;
- `get_issue_transitions` принимает `issueId`, соседние `get_issue_links`, `get_checklist`,
  `get_attachments` — `issueIds`.

Цена измерена: на этом потеряно 2 вызова из первых 30. Отчёт 3.1 называл дефект системным —
он не закрыт.

### D3. Число против строки в одном ответе

`add_worklog`: `worklogId: "70"` и `worklog.id: 70`. `create_link`: `linkId: "66069"` и
`link.id: 66069`. Тот же разнобой, что миграция 4.1 чинила у досок и спринтов.

### D4. `get_thumbnail` отдаёт размер оригинала, а не превью

Ответ `size: 121747` при фактически сохранённом файле 40 503 байта (PNG 140×140). Поле описывает
не то, что инструмент сделал.

### D5. `update_worklog` заворачивает ответ дважды

`data.data` вместо `data`. У соседних инструментов семейства такого нет.

### D6. Отказ рубежа неотличим от частичной неудачи

Нарушение области действия приезжает как `success: true` с записью в `failed[]` — тем же кодом,
что «одна задача из трёх не найдена».

## Наблюдения, не являющиеся дефектами

- **Форма записи worklog на v3 наблюдалась впервые**: `id` числовой, длительность нормализуется
  (`1h 30m` → `PT1H30M`), `createdBy.self` указывает на `/v3/users/...`.
- **`get_thumbnail` → 404 на картинке 1×1** — свойство API (превью для такого файла не создаётся),
  не дефект инструмента: на картинке 240×240 тот же вызов отдал PNG 140×140. Проверено
  изолированным повтором.
- **Канал `warnings` работает в бою**: `FIELDS_WITHOUT_VALUE` назвал поле `thumbnail`,
  которого нет в ответе загрузки.
- **Рубеж работает в боевом канале**, а не только в тестах: `POST /v3/queues/TEST/components`
  с чужим лидом отклонён с причиной «lead назначает человека someone-else, а не владельца
  прогона vr»; `POST /v3/issues/TEST-999999/comments` отклонён как задача не этого прогона.
  Multipart-загрузка вложения прошла через рубеж — перехват на axios-интерцепторе оправдал себя.

### D7. `create_queue` невозможно вызвать успешно (BLOCKER)

API требует `issueTypesConfig` (`422 Требуется параметр`), в схеме инструмента такого поля нет,
неизвестные параметры схема отклоняет. Очередь этим инструментом создать нельзя в принципе.
Попутно: имя очереди ограничено 40 символами, о чём схема не предупреждает.

### D8. `create_project` невозможно вызвать успешно (BLOCKER)

`key` обязателен в нашей схеме и отвергается API в любой форме (`400 key: Incorrect data format`):
пробовались латиница `LIVEPROBE`, смешанный `LIVE20260825B`, кириллица `ЖивойПрогон`. У
существующих проектов `key` совпадает с названием (`Сделка`, `Ипотека`), то есть, судя по всему,
назначается сервером. Без `key` инструмент не проходит собственную валидацию.

### D9. `create_board` молча игнорирует переданные параметры (BLOCKER)

`POST /v3/boards` с `name` и `queue` создал доску `id 103` с именем **«Новая доска»** и пустым
фильтром; в сообщении инструмент при этом отрапортовал успех с переданным именем. Подтверждено
независимым чтением. `update_board` то же имя применяет корректно — дефект только в создании.

Два следствия. Первое: доска остаётся в организации без префикса прогона, то есть **свойство
«остаток находится поиском по имени» ломается**. Второе: доска создаётся не того типа, и на ней
нельзя завести спринт (`422 У доски этого типа не может быть спринтов`) — семейство спринтов
закрыть нечем.

### D10. `create_global_field` шлёт форму, которую API не принимает (BLOCKER)

`{name, schema:{type:'string'}}` → `400 schema: Incorrect data format`. Для сравнения, создание
**локального** поля очереди тем же прогоном прошло на форме `{id, nameEn, nameRu, category,
type:'ru.yandex.startrek.core.fields.StringFieldType'}`. Гипотеза (не проверена, `raw_api_request`
только на чтение): глобальное поле ждёт такую же форму, а не `schema`.

### D11. Идентификатор колонки доски не уникален внутри доски

`create_board_column` на доске с колонками `1,2,3` создал четвёртую колонку, тоже с `id: 1`.
Дальше: `update_board_column` по `columnId: 1` изменил **первую** колонку (чужую, «Открыт»), а
`delete_board_column` по тому же id удалил **обе** колонки с `id: 1` (было 4, стало 2). На боевой
доске это молча портит чужие колонки. Задним числом это оправдывает решение рубежа не вести
колонки в журнале: составной ключ `{доска}/{колонка}` ничего бы не гарантировал.

### D12. Созданный фильтр не виден ни одному нашему инструменту чтения

`create_filter` и `update_filter` работают (фильтр `id 6` создан и переименован), но `get_filters`
ходит в `GET /v3/myself/favorites/filters` и возвращает пустой список. Эффект нечем подтвердить
независимым чтением, а удалить фильтр нечем вовсе — инструмента нет. Предсказано ревью плана,
подтверждено живьём.

### D13. `bulk_move_issues` называет очередь по-разному на входе и в выходе

Вход — `queue`, ответ того же вызова — `targetQueue`.

## Рубеж области действия: что доказано боем

- Отклонён комментарий к чужой задаче (`TEST-999999` не в журнале) — запрос до API не дошёл.
- Отклонено создание компонента с чужим руководителем: «lead назначает человека someone-else,
  а не владельца прогона vr» — HIGH-находка Codex закрыта не тестом, а реальным отказом.
- Multipart-загрузка вложения прошла через рубеж: перехват на axios-интерцепторе, а не поверх
  `IHttpClient`, оправдал себя.
- Журнал прогона сошёлся с перечнем созданного построчно, включая обе формы адресации
  (`TEST-22` и 24-hex, `goal/<id>` и `goal/71`, ключ и составной id локального поля).
- Отказов рубежа за прогон: 2, оба намеренные (предполётная проверка и проба чужого лида).

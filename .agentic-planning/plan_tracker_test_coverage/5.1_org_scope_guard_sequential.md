# 5.1 Рубеж для сущностей уровня организации (последовательно)

Предусловие этапа 5.2. Сейчас `src/live_scope/scope-rules.ts:280-319` отклоняет мутации проектов,
досок, колонок, спринтов, глобальных полей, сущностей Entity API, фильтров и очередей
**безусловно** — восемью правилами вида «видно за пределами очереди» (очереди, доступы очереди,
проекты, поля, entities, доски, спринты, фильтры). Пока так, живая приёмка этих семейств
невозможна в принципе: рубеж отклонит собственный законный запрос прогона.

Перечисление, на котором стоит этап, снято заново по коду 2026-08-25 —
[inventory/mutating-tools-2026-08-25.md](inventory/mutating-tools-2026-08-25.md), таблицы 1 (раздел
D/E — 26 инструментов) и 2 (удаляемость восьми родов сущностей). Строка «чем получено и чего способ
не видит» — в артефакте; здесь важны два её следствия: энумератор не видит вторую ветку
`z.enum('action')` (поймано на `manage_sprint_lifecycle`), и наличие файла теста не означает
покрытия конкретной ветки.

Ревью плана 2026-08-25 дало 4 HIGH и 10 MEDIUM; все подтверждены чтением кода и учтены ниже.
Три из них меняли замысел, а не формулировку: родитель, названный в теле (проекты, доски),
обязательность префикса и способ учёта колонок.

## Решение

Безусловный отказ заменяется на **допуск по владению прогоном** — тот же принцип, что уже работает
у компонентов и локальных полей очереди, распространённый на организацию:

- **создание** (`POST`) допускается только если в теле есть имя, содержащее **префикс прогона**,
  и ни одна ссылка в теле не выводит сущность за пределы прогона;
- **правка и удаление** (`PATCH`, `DELETE`, подпути `_start`/`_archive`) — только если
  идентификатор сущности есть в журнале прогона в соответствующем роде;
- тело, из которого имя или родитель не распознаны, — отказ (fail-closed сохраняется).

Префикс обязателен не ради красоты: журнал теряется вместе с процессом (известное ограничение,
`src/live_scope/README.md`), и единственный способ найти остаток — поиск по имени. Сущность без
префикса нельзя ни отличить от чужой, ни убрать по следам.

**Ссылки в теле — отдельный класс дефекта, уже известный рубежу.** Связь задач проверяется по
обоим концам (`scope-rules.ts:133-140`, `decideLinkCounterpart`), потому что запрос, законный по
пути, может менять чужую сущность через тело. У организации то же самое: `POST /v3/projects`
принимает `queueIds` и `teamUserIds` (`src/tools/api/projects/base-project.schema.ts:53-63`), и
проект прогона с законным именем привязал бы к себе боевые очереди и живых людей.

**Что этап НЕ делает:** не ослабляет ни одного действующего правила очереди `TEST`, не отменяет
`refuseEverything` для необъявленного пишущего прогона, не добавляет инструментов Трекера
(в частности, `delete_queue` — пробел, найденный перечислением, — остаётся за границей этапа).

### Риск, принимаемый осознанно

Расширение снимает единственную машинную защиту организации от порчи. Компенсации, каждая
проверяется тестом: обязательный префикс в имени; правка и удаление только по журналу; проверка
ссылок в теле; неузнанное тело — отказ; отдельная переменная для одноразовой очереди, которую
нельзя выставить машинально.

## Контракты

### Журнал (`run-journal.ts`)

`EntityKind` дополняется: `project`, `board`, `sprint`, `globalField`, `entity`, `filter`, `queue`.

Рода `boardColumn` **нет** осознанно. Колонка не адресуется вне своей доски
(`DELETE /v3/boards/{b}/columns/{col}`), а доска целиком принадлежит прогону и убирается одним
`delete_board`; поэтому правом на колонку служит запись о **доске**. Отдельный род потребовал бы
составного ключа `{b}/{col}` и всё равно не покрыл бы колонки, созданные вместе с доской: они
приходят в теле `POST /v3/boards` (`src/tools/api/boards/create-board.schema.ts:34`) и в ответе
детектору как отдельные сущности не видны.

Составной идентификатор остаётся у одного рода: `entity` → `{entityType}/{entityId}`. Один и тот же
id у другого типа (`goal` против `portfolio`) — чужая сущность.

Публичная поверхность (`register`, `has`, `list`, `breakage`) не меняется.

### Детектор созданного (`live-scope.guard.ts`)

Контракт `createdEntityOf` расширяется, потому что составной идентификатор без контекста пути не
собрать:

```
createdEntityOf(request) -> { kind: EntityKind, idPrefix?: string } | undefined
// idPrefix — то, что стоит перед id в составном роде: тип у сущности Entity API
// ... implementation details
```

**Какие поля ответа регистрируются — по каждому роду, а не «обычно `id`».** Сейчас оба поля
(`key` и `id`) берутся только у задачи (`live-scope.guard.ts:85-90`); при регистрации одной формы
рубеж отклонит собственный законный запрос прогона, стоит инструменту адресовать сущность второй.

| Род | Регистрируется | Почему |
|---|---|---|
| `project` | `id` и `key` | `update_project` принимает «ID или ключ» (`update-project.schema.ts:20`) |
| `queue` | `id` и `key` | `manage_queue_access` принимает «идентификатор или ключ» (`manage-queue-access.schema.ts:15`) |
| `board`, `sprint` | `id` (числовой → строка) | второй формы адресации у них нет |
| `globalField`, `filter` | `id` | то же |
| `entity` | `{type}/{id}`; если ответ несёт `shortId` — дополнительно `{type}/{shortId}` | форма ответа проходит через `assertEntityRecordShape`; **фактический набор полей сверить первой же живой пробой этапа 5.2 и, если `shortId` отсутствует, убрать строку** |

`asIdentifier` (`live-scope.guard.ts:73-76`) уже приводит число к строке — менять его не требуется;
что новые рода кладут id именно в поле `id` верхнего уровня, проверяется пробой, а не принимается.

### Контекст правил (`scope-rules.ts`) — шов между пакетами B и C

`ScopeContext` объявлен в `scope-rules.ts:32-42` (пакет B), а заполняется в
`live-scope.config.ts:101` (пакет C). Контракт фиксируется планом, как и `EntityKind`:

| Поле | Тип | Смысл |
|---|---|---|
| `runPrefix` | `string \| undefined` | подстрока, обязательная в имени создаваемой сущности организации; не задана — мутации организации отклоняются с named-причиной |
| `disposableQueue` | `string \| undefined` | ключ одноразовой очереди; не задан — мутации очередей отклоняются, как сейчас |

Оба поля необязательные. Это не мягкость, а условие совместимости: прогон уровня 3.1 (только
очередь `TEST`) организации не касается вовсе, и требовать от него префикс — значит ломать
работающий сценарий. Отказ приходит там, где префикс действительно нужен, — в правиле создания
org-сущности, с текстом «задайте `YANDEX_TRACKER_LIVE_SCOPE_RUN_PREFIX`».

### Конфигурация (`live-scope.config.ts`)

| Переменная | Смысл | Обязательность |
|---|---|---|
| `YANDEX_TRACKER_LIVE_SCOPE_RUN_PREFIX` | значение `runPrefix` | необязательна; без неё организация недоступна |
| `YANDEX_TRACKER_LIVE_SCOPE_DISPOSABLE_QUEUE` | значение `disposableQueue` | необязательна; без неё очереди недоступны |

Ошибкой старта отсутствие любой из них **не является** — в отличие от журнала. Довод про журнал
(`live-scope.config.ts:87-91`) здесь не работает: без журнала теряется единственное основание
разрешать правку непрозрачных id, то есть половина защиты; без префикса теряется лишь находимость
остатка, и только для семейств, которых прогон может вовсе не касаться.

### Правила (`scope-rules.ts`)

Восемь безусловных отказов заменяются таблицей ниже; строка «доступы очереди» сохраняется как
отдельная, иначе она теряется при переписывании. Порядок: частное правило выше общего, первое
совпавшее решает.

| Семейство | Создание допускается, если | Правка/удаление допускается, если |
|---|---|---|
| `POST /v3/projects` | `name` несёт префикс **и** `queueIds ⊆ {sandboxQueue, disposableQueue}` **и** `teamUserIds` пуст | `id`/`key` из пути в журнале как `project`; те же ограничения на `queueIds`/`teamUserIds` в теле `PATCH` |
| `POST /v3/boards` | `name` несёт префикс **и** `queue` (если задан) ∈ `{sandboxQueue, disposableQueue}` | `id` в журнале как `board` |
| `POST /v3/boards/{b}/columns` | `b` в журнале как `board` | `b` в журнале как `board` (колонка права не имеет — их даёт доска) |
| `POST /v3/sprints` | `name` несёт префикс **и** `board` в теле в журнале как `board` (распознавать строку и объект `{id}`, как это делают `queueKeyOf`/`issueKeyOf`) | `id` в журнале как `sprint`, включая подпути `_start` и `_archive` |
| `POST /v3/fields` | `name` несёт префикс; распознаются обе формы — строка и объект локализации | `id` в журнале как `globalField` |
| `POST /v3/entities/{type}` | `fields.summary` несёт префикс. `name` в теле Entity API **не существует** (`create-entity.operation.ts:30-33`, `create-entity.schema.ts:17-19`: `name`/`description` дают 422) — иная форма означает отказ | `{type}/{id}` в журнале как `entity` |
| `POST /v3/filters` | `name` несёт префикс | `id` в журнале как `filter` |
| `POST /v3/queues` | `key` в теле равен `disposableQueue` **и** имя несёт префикс | `id`/`key` из пути в журнале как `queue` |
| `PATCH /v3/queues/{q}/permissions` | — | `q` в журнале как `queue` |

**Одно действующее правило меняется:** матчер массовых операций (`scope-rules.ts:217-223`)
допускает `_move` только в песочную очередь. Целевой очередью дополнительно становится
`disposableQueue` — иначе `bulk_move_issues` проверить нечем (единственный возможный вызов
TEST→TEST маршрута не подтверждает). Перенос в чужую очередь по-прежнему отказ.

**Якорение.** Действующие правила-родители не заякорены: `/^\/v[23]\/boards/`
(`scope-rules.ts:306`) матчит и `/v3/boards/{b}/columns/{col}`, `/^\/v[23]\/sprints/` — и
`/v3/sprints/{id}/_start`. Если новые строки сохранят эту форму и встанут выше частных,
подпути решатся правилом родителя, а частные правила не выполнятся никогда — при зелёных тестах,
потому что доска и спринт прогона в журнале есть. Правила-родители обязаны быть заякорены
(`$` либо `(?=\/|$)`), порядок закрепляется тестом. То же касается уже существующего порядка:
частные правила компонентов и локальных полей очереди стоят выше общего правила очередей и
должны там остаться.

**Версия в пути.** Новые правила пишутся под `/v3/` — после миграции 4.1 путей v2 в коде не
осталось. Ветка v2 упала бы в fail-closed, а его текст запрещён проверкой
`scope-rules.test.ts:59` для перечисленных запросов; поэтому строки v2 в
`tests/live_scope/known-mutating-requests.ts` вычищаются синхронно, а не оставляются «на всякий».

## Граничные условия (каждое — тест)

1. Создание проекта/доски/поля/фильтра с именем **без** префикса — отказ.
2. `PATCH`/`DELETE` сущности, которой нет в журнале, — отказ, даже если имя несёт префикс.
3. Колонка на доске, которой нет в журнале, — отказ.
4. Спринт с `board`, которого нет в журнале, — отказ; форма ссылки — строка и объект.
5. `_start`/`_archive` спринта не из журнала — отказ (ветки, которых не видел энумератор).
6. Сущность Entity API того же `id`, но другого `type`, — отказ.
7. Проект с `queueIds`, содержащим постороннюю очередь, — отказ; с непустым `teamUserIds` — отказ.
8. Доска с `queue` вне песочницы — отказ.
9. `POST /v3/queues` с ключом, отличным от `disposableQueue`, — отказ; при незаданной переменной —
   отказ на любой ключ.
10. Тело без распознанного имени (пустое, строка, FormData) — отказ.
11. Создание org-сущности при незаданном `runPrefix` — отказ с named-причиной, а не fail-closed.
12. Своя сущность, адресованная **второй формой** (проект по `key` при создании, отдавшем `id`), —
    допуск.
13. `bulk _move` в `disposableQueue` — допуск; в постороннюю очередь — отказ.
14. Действующие сценарии очереди `TEST` не изменились: все негативные кейсы существующих тестов
    рубежа остаются зелёными.

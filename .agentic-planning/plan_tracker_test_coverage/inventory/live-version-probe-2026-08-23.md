# Опыт: версии API и форма ответа у категорий вне очереди `TEST`

Снято 2026-08-23 боевыми `GET`-запросами через `raw_api_request` (`npm run tools:call`),
токен MCP-клиента, мутаций не делалось. Закрывает вопрос, поставленный волной 1 этапа 2.1.2:
документация называет v3 там, где код ходит в v2 — сломано ли это.

## Вопрос 1: отвечает ли v2

**Отвечает.** Обе версии дают одинаковое число элементов и одинаковый набор ключей.

| Путь | v2 | v3 | Различие ключей |
|---|---|---|---|
| `/{v}/boards` | 73 элемента | 73 элемента | нет |
| `/{v}/fields` | 72 | 72 | нет |
| `/{v}/projects` | 43 | 43 | нет |
| `/{v}/boards/3/sprints` | 95 | 95 | нет |

**Вывод: инцидента нет, срочная миграция не требуется.** v2 у этих категорий — работающий
алиас с идентичной формой ответа. Гипотеза «v2 не отвечает, инструменты сломаны» **опровергнута
наблюдением**. Миграция на v3 остаётся плановой работой (документация описывает только v3),
но не аварийной.

## Вопрос 2: совпадает ли форма с нашими типами

Здесь расхождения нашлись, и они реальные — их не поймал бы ни один мок, потому что мок
отдаёт то, что ему велели.

| Сущность | Поле | Наш тип | Боевой ответ |
|---|---|---|---|
| глобальное поле | `options` | `readonly FieldOption[]` (`field.entity.ts:134`) | **`boolean`** (`true`) |
| доска | `id` | `string` (`board.entity.ts:14`) | **`number`** (`1`) |
| колонка доски | `id` | `string` | **`number`** (найдено волной 1) |
| спринт | `id` | `string` (`sprint.entity.ts:43`) | **`number`** (`207`) |
| проект | `id` | `string` | `string` (`"2"`) — совпадает |
| глобальное поле | `id` | `string` | `string` (`"queue"`) — совпадает |

`version` (токен оптимистичной блокировки) присутствует в теле ответа у досок, проектов,
полей и спринтов — то есть значение для него взять откуда есть. У `Project` в наших entity
поле `version` не объявлено вовсе.

## Чего опыт не смог проверить и почему

Документация называет `PUT /v3/projects/{id}?version=<version>` против нашего
`PATCH /v2/projects/{id}` без `version`. **Проверить это нашими инструментами невозможно по
построению:** рубеж области действия живых прогонов (`src/live_scope/`) fail-closed отклоняет
любую мутацию по пути, не описанному правилом, а проекты, доски, спринты и глобальные поля
по природе лежат вне очереди `TEST` (§1 канона). Пишущий прогон без объявленной очереди
отклоняет мутации целиком.

Это не дефект рубежа — он ведёт себя как задумано. Но следствие требует решения: либо этап 3.1
получает отдельный механизм «сущность организации, созданная прогоном и удаляемая им же»,
либо вопросы `PUT` vs `PATCH` и потерянного `version` закрываются вручную, вне сервера.

## Что из этого следует

1. Приоритет не «сменить v2 на v3», а **починить типы**: `options: boolean` и числовые `id`
   у досок, колонок и спринтов. Сейчас код заявляет форму, которой у API нет.
2. Отсутствие `version` в мутациях проектов и глобальных полей — риск потерянного обновления
   при конкурентной правке, независимый от версии пути.
3. Оба пункта — свидетельство в пользу того, что мок не наблюдает С-4: расхождение прожило
   до первого боевого запроса.

## Контракты (без реализации)

### CursorCodec (новый util, домен Трекера)
- `encode(relativePath, endpointTag): string` — base64url payload `{v:1, t:tag, p:path}`
  (версия + тег семейства эндпоинта + путь). Версионный префикс/поле для forward-compat.
- `decode(cursor, expectedTag): string` — возвращает путь ИЛИ **бросает**
  `InvalidCursorError` при: битом base64/JSON, неизвестной версии, mismatch тега
  (R13), пути не прошедшем guard `/^\/v[23]\//` (reuse `stripHost`). НИКОГДА не
  возвращает undefined (R3) — вызывающий получает либо валидный путь, либо ошибку.
- Тег семейства (R13): короткий код на инструмент (chlog/cmnt/links/wlog/chk/q/proj/find).
- Инвариант: `decode(encode(p,t), t) === p` для валидных путей Трекера.
- **Где живёт:** статический util в `#tracker_api/utils` (без DI-регистрации).

### PaginationMeta (entity) — изменения
- ДОБАВИТЬ: `nextCursor?: string` (присутствует ⟺ `hasNextPage` от `Link next`).
- `page?` — пока ОСТАВИТЬ `@deprecated` (удаление в 3.1, см. R5); новый код не пишет.
- ОСТАВИТЬ: `perPage?`, `total?`, `totalPages?`, `hasNextPage`, `fetchedAll`,
  `truncated`, `pagesFetched`, `hasError`.
- Уточнить doc: `total`/`totalPages` заполняются ТОЛЬКО при `rel="seek"`.

### PaginationParams (entity) — изменения
- ДОБАВИТЬ `cursor?: string`; `page?` — `@deprecated` (удаление в 3.1).
  Оставить `perPage?`, `fetchAll?`, `maxItems?`, `maxTotalItems?`.

### TrackerPaginator — изменения
- `buildMeta(input)` (R4, R6):
  - Нормализовать сначала: `const path = stripHost(nextUrl)`.
  - `hasNextPage = Boolean(path) || truncated` (УБРАТЬ `hasMoreByTotal`).
  - `nextCursor = path !== undefined ? CursorCodec.encode(path, tag) : undefined`
    (`tag` приходит от операции/singlePage). `path===undefined` при валидном
    `nextUrl` = конец списка (НЕ ошибка — это выходной путь сервера).
  - `total`/`totalPages` — ТОЛЬКО при `hasSeek=true`.
  - УБРАТЬ из meta запись поля `page`.
- `hasSeek` вычисляет САМ paginator (R6): `singlePage`/`fetchAllPages` берут
  `parseLinkHeader(headers.link).seek !== undefined` из заголовков ответа и
  передают в `buildMeta`. Вызывающие операции про `hasSeek` НЕ знают.
- `singlePage(response, opts)`: `opts` = `{ perPage?, tag }` (без `page`).
- `fetchAllPages(...)`: `nextCursor` в финальную meta (если остался `next`/
  `truncated`); seek-gating по заголовкам финальной страницы (seek там присутствует —
  эмпирически подтверждено на queues, см. X1). Семантика обхода без изменений.

### Common schema (`pagination.schema.ts`) — изменения
- `PageSchema`/`noPageFetchAllConflict` — оставить `@deprecated` (удаление в 3.1, R5).
- ДОБАВИТЬ `CursorSchema` — `z.string().optional().describe(...)`: «Непрозрачный
  курсор следующей страницы из `pagination.nextCursor`. Использовать ТОЛЬКО с тем же

- ДОБАВИТЬ единый refine `noCursorWithBulkParams` (R9): `cursor` исключает

  выборки/bulk-обхода). Любой из них вместе с `cursor` → ошибка валидации.
  + `PAGINATION_CURSOR_CONFLICT_MESSAGE`.
- Сохранить `PerPageSchema`/`makePerPageSchema`/`FetchAllSchema`/`MaxItemsSchema`/
  `MaxTotalItemsSchema`/потолки.
- Обновить `index.ts`: добавить `CursorSchema`/`noCursorWithBulkParams`; deprecated
  экспорты пока сохранить.

### Batch-правило курсора (R1, КРИТИЧНО)
- В batch-эндпоинтах (changelog/comments/links/worklog/checklist) курсор валиден
  ТОЛЬКО при `issueIds.length === 1`. Refine `cursorRequiresSingleIssue`:
  `cursor` задан ⇒ ровно один issueId. Иначе ошибка «листайте задачи по одной».
  Подключается в схемах всех batch-эндпоинтов. fetchAll остаётся multi-issue.

### Контракт непагинируемых (R11, решение)
- `components`, `attachments` (и `worklog`/`checklist` — по результату верификации
  R7): убрать пагин-параметры; в ответе НЕТ блока `pagination`. Tools этих
  эндпоинтов не обращаются к `result.pagination`. Единый стиль во всех группах.

- Хелпер фильтрует `items`, пробрасывает `pagination` как есть → `nextCursor`

## Edge cases
- next-URL с чужим хостом/без `/v[23]/` → `decode`/`stripHost` = undefined →
  трактуем как конец списка (`hasNextPage=false`, без `nextCursor`).
- Заголовок `X-Total-*` без `seek` (случай comments) → `total`/`totalPages` НЕ
  попадают в meta.
- Пустой ответ (0 элементов) → нет `Link next` → `hasNextPage=false`,
  `fetchedAll=true`.
- `cursor` + `fetchAll=true` → ошибка валидации (refine).

## Тест-план (что проверяем, без кода)
- `CursorCodec`: round-trip с тегом; `decode` БРОСАЕТ при битом base64/JSON,
  неизвестной версии, mismatch тега (R13), чужом хосте, не-/v2,v3 пути (R3).
- `buildMeta`: nextCursor при наличии next; отсутствие при его отсутствии;
  `total` ТОЛЬКО при seek; отсутствие `total` при X-Total БЕЗ seek (регрессия comments);
  **позитив (R8): при `rel="seek"`+X-Total → `total`/`totalPages` присутствуют**.
- `singlePage`: корректный nextCursor из `Link rel="next"` c `id=`; hasSeek
  вычисляется самим paginator (R6).
- `fetchAllPages`: существующие тесты зелёные; nextCursor при truncated; total
  сохраняется на финальной seekable-странице (X1).

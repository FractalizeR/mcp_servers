# План: единообразная opaque-cursor пагинация для всех list-инструментов

## Цель

Заменить ручной параметр `page` единым непрозрачным курсором (`cursor`) во всех
10 list-инструментах MCP-сервера Яндекс.Трекера. Снаружи — один механизм листания
независимо от того, как пагинирует конкретный эндпоинт API (page+seek или id-cursor
или вовсе без пагинации).

## Контекст и обоснование (проверено на живом API 2026-06-19)

Сырые заголовки ответов API (curl) показали:

| Эндпоинт | `Link rel="next"` | `rel="seek"` | `X-Total-*` | Тип API |
|---|---|---|---|---|
| queues (v3), projects (v2), find_issues/_search (v3) | `?page=N` | да | да | page/seekable |
| changelog (v3), comments (v3), links (v3) | `?id=<cursor>` | нет | только comments | id-cursor |
| components (v2), attachments (v2) | нет (всё разом) | — | нет | не пагинируется |
| worklog (v2), checklist (v2) | нет данных в орг. | — | — | покрыты инвариантом |

**Проблема текущей реализации:** `page` рекламируется в схеме всех 10 инструментов,
но реально работает только у seekable (queues/projects/_search). У id-cursor
эндпоинтов API игнорирует `page` → возвращается первая страница. Хуже всего
`comments`: отдаёт `X-Total-Count`/`Pages` без seek → инструмент рисует ложные
`totalPages`, агент листает page=2..N и N раз получает первую страницу (дубли).

**Ключевой инвариант (фундамент решения):**
1. ВСЕ пагинируемые эндпоинты отдают `Link rel="next"`, и next-URL сам описывает
   свой механизм (`page=` либо `id=`). Непагинируемые — не отдают next.
   Сервер уже умеет повторять next-URL (`fetchAll` через `stripHost`).
2. `parseLinkHeader` (infra) уже возвращает и `next`, и `seek` — seek-gating
   реализуем без правок инфраструктуры.

## Архитектурное решение

**Opaque cursor.** Курсор — непрозрачная строка (base64url относительного
next-пути, напр. `/v3/issues/X/changelog?id=...&perPage=3`). Сервер:
- ПРОИЗВОДИТ курсор из `Link rel="next"` ответа (reuse `stripHost` + guard `/v[23]/`);
- ПРИНИМАЕТ курсор на вход → декодирует → валидирует префикс `/v[23]/` →
  использует как путь запроса (GET) либо endpoint для POST-replay (find_issues).

**Два правила метаданных (единые для всех):**
- `hasNextPage`/`nextCursor` выводятся ИСКЛЮЧИТЕЛЬНО из `Link rel="next"`
  (убрать эвристику `page*perPage < total`).
- `total`/`totalPages` показывать ТОЛЬКО при наличии `rel="seek"` в ответе
  (seek-gating чинит comments и любой непроверенный эндпоинт по построению).

## Согласованные решения

- **Единообразие важнее обратной совместимости.** Параметр `page` удаляется из
  публичного контракта всех 10 инструментов — это намеренный breaking change
  (одобрено пользователем 2026-06-19).
- Унификация возможна ТОЛЬКО на cursor: эмулировать `page` для id-cursor
  эндпоинтов нельзя без последовательного обхода от начала (дорого/хрупко).
- `fetchAll` сохраняется без изменения семантики (он уже единообразен).
- `components`/`attachments` (и, по инварианту, потенциально worklog/checklist)
  не пагинируются на уровне API → всегда `hasNextPage=false`, `nextCursor`
  отсутствует. Параметры пагинации у них становятся no-op (перестают вводить
  в заблуждение).

## Решения (закрыто пользователем 2026-06-19)

1. **find_issues (POST `_search`)**: курсор кодирует ТОЛЬКО next-путь; критерии
   поиска (query/filter/...) агент передаёт повторно вместе с `cursor` (как было
   с `page`). Тело replay-запроса пересобирается из повторно переданных критериев.
2. **cursor + perPage = ОШИБКА валидации.** Размер страницы зафиксирован внутри
   курсор-пути; одновременная передача `perPage` запрещена (refine `noCursorPerPageConflict`).
   Аналогично `cursor` + `fetchAll` = ошибка.
3. **Непагинируемые эндпоинты** (отдают всё разом):
   - **`components`, `attachments`** — ПОДТВЕРЖДЕНО сырыми заголовками (нет `Link`).
     У них УБРАТЬ пагинационные параметры полностью (`cursor`/`perPage`/`fetchAll`/
     `maxItems`/`maxTotalItems`); контракт ответа без `pagination` ИЛИ с
     минимальным маркером (решить в 2.x — см. ниже). Документировать как
     «возвращает все элементы за один ответ».
   - **`worklog`, `checklist`** — НЕ подтверждено (в орг. нет данных). РИСК тихой
     потери данных при ошибочном удалении пагинации. Действие: в этапе 2 СНАЧАЛА
     верифицировать на реальных данных (создать тестовую задачу с >perPage
     worklog/checklist-записями ИЛИ найти существующую ИЛИ свериться с офиц. докой
     API). ТОЛЬКО при подтверждении «не пагинируется» — убрать параметры; иначе
     оставить cursor-механизм (безопасный no-op, если API не пагинирует).
4. **Версионирование курсора**: короткий префикс-версия в токене (напр. `c1:`)
   для forward-compat.

## Definition of Done (весь план)

- Ни в одной tool-схеме нет `page`; везде `cursor` (opaque).
- `pagination.nextCursor` присутствует ⟺ есть следующая страница (по `Link next`).
- `total`/`totalPages` отдаются только при `rel="seek"`.
- comments более не отдаёт ложные `totalPages`; ручное листание comments/changelog
  курсором даёт реально следующие записи (регрессионные тесты на живой механике
  через MockHttpClient с заголовком `Link: ...; rel="next"`).
- `fetchAll` поведение не изменилось (существующие тесты зелёные).
- `npm run validate:quiet` = 0; knip/depcruise/cpd чисто.
- Документация (README пагинации + package CLAUDE.md) обновлена под cursor.

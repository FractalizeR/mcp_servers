# Live Scope — область действия живых прогонов

Рубеж, ограничивающий живые прогоны песочной очередью. Живые прогоны идут в **боевой**
Яндекс.Трекер под реальным токеном; отдельной организации нет, песочница — очередь `TEST`
боевой организации. Изоляция правами недостижима, поэтому этот рубеж — единственная защита.

Канон и реестр исключений — [tests/TESTING_STRATEGY.md](../../tests/TESTING_STRATEGY.md) §1.

## Публичная поверхность

`index.ts` — единственный вход:

- `createLiveScopeGuardFromEnv(env?)` — рубеж по переменным окружения либо `undefined`,
  если прогон не объявлен живым. Потребитель в продовом пути один: `composition-root`.
- `decideRequest(request, context)`, `LiveScopeGuard`, `RunJournal` — для тестов рубежа.

## Включение

| Переменная | Смысл |
|---|---|
| `YANDEX_TRACKER_LIVE_SCOPE_QUEUE` | ключ песочной очереди; задана — рубеж включён |
| `YANDEX_TRACKER_LIVE_SCOPE_JOURNAL` | файл журнала прогона |
| `YANDEX_TRACKER_LIVE_SCOPE_RUN_ID` | метка прогона, которой подписан журнал |
| `YANDEX_TRACKER_LIVE_SCOPE_RUN_PREFIX` | префикс имени для сущностей организации, см. ниже |
| `YANDEX_TRACKER_LIVE_SCOPE_DISPOSABLE_QUEUE` | ключ одноразовой очереди, см. ниже |
| `YANDEX_TRACKER_LIVE_SCOPE_RUN_OWNER` | владелец прогона: единственный человек, на которого вправе ссылаться тело, см. ниже |

Задана только первая — старт падает: половина рубежа опаснее его отсутствия, потому что
прогон считает себя защищённым. Не задана ни одна — сервер работает как обычно. Три последние
переменные необязательны и не влияют на старт: их отсутствие не ошибка, а отказ достаётся
конкретному правилу допуска (ниже), с текстом, что задать.

## Допуск по владению прогоном: сущности организации

Проекты, доски и их колонки, спринты, глобальные поля, сущности Entity API, сохранённые
фильтры и очереди видны всей организации, а не одной очереди — принадлежности очереди для них
недостаточно. Правило допуска то же, что уже действует у компонентов и локальных полей очереди,
распространённое на организацию:

- **создание** допускается, только если имя (или, у Entity API, `fields.summary`) несёт
  `YANDEX_TRACKER_LIVE_SCOPE_RUN_PREFIX` во **всех** непустых языках локализованного имени
  (остаток ищут поиском по отображаемому имени — префикс в одном языке из двух не находится);
- **правка и удаление** — только если идентификатор сущности есть в журнале прогона;
- **ссылки в теле** проверяются у всего семейства — и на создании, и на правке: право «сущность
  моя» не даёт права перевесить её на чужого родителя или назначить ей чужого человека;
- **правка не снимает префикс** с имени своей сущности: тело с именем обязано нести префикс,
  тело без имени правку имени не затрагивает;
- **состав тела ограничен белым списком ключей** (`organization-rules.ts`): у каждого семейства
  перечислены допустимые ключи верхнего уровня, у записи Entity API — ещё и ключи внутри
  `fields`, у доступов очереди — роли и действия. Неизвестный ключ — отказ с его именем;
- тело, из которого имя или ссылка не распознаны, — отказ.

## Ссылки в теле

Ссылки на очередь и на доску адресны — их проверяет правило своего семейства:

| Ссылка | Поля | Законна, если |
|---|---|---|
| на очередь | `queue` компонента, `queues` проекта на создании и `queueIds` на правке, `autoFilters.addFilter.liveFilter.fieldValues.queue` доски на создании и `queue` на правке, целевая очередь `bulk _move` | это песочная очередь либо одноразовая очередь, **созданная** этим прогоном |
| на доску | `board` спринта | доска есть в журнале прогона |

**Создание и правка адресуются по-разному, поэтому перечни ключей и проверки ссылок
парные** (`createAllowedKeys`/`allowedKeys`, `createViolation`/`editViolation`). Компонент
создаётся на `POST /v3/components` и называет очередь телом (`queue`), а не путём. Доска
создаётся на `POST /v3/liveBoards`, читается и правится по `/v3/boards/{id}`; устаревший
`POST /v3/boards` молча игнорирует тело и заводит доску по умолчанию — правилом он не
покрыт и уходит в fail-closed. Проект знает очередь как `queues` на создании и как
`queueIds` на правке. Общий перечень на два маршрута снял бы проверку очереди с одного
из них молча — это дыра, а не неудобство.

**Ссылка на человека ищется иначе — по всему телу и на любой глубине** (`people-in-body.ts`).
Перечислять «поля, где бывает человек» пробовали трижды, и трижды перечень оказывался неполон:
подряд были пропущены `lead`, `subjects`, `assignee` ключевого результата. Полнота чёрного списка
равна догадливости ревьюера, поэтому его тут нет: тело обходится рекурсивно, и КАЖДЫЙ ключ из
набора имён, несущих человека (`assignee`, `lead`, `followers`, `summonees`, `subjects`,
`teamUserIds`, `createdBy`, `author` и прочие — набор в `people-in-body.ts`), обязан указывать на
владельца прогона, где бы этот ключ ни лежал. Проверка применяется ко всем мутирующим запросам:
к задачам, компонентам, локальным полям и массовым операциям тоже, а не только к организации.
Исключение — поисковые POST: там тело фильтр, а не назначение.

**Пользовательское поле задачи допускается, только если его создал этот прогон**
(`custom-fields-in-body.ts`). Гейт людей узнаёт человека по ИМЕНИ поля, а в Трекере семантику
поля задаёт его ТИП: поле типа `user` с произвольным именем назначает живого сотрудника и мимо
перечня имён проходит незамеченным, а расширять перечень бессмысленно — имя произвольно по
построению. Поэтому ключ тела задачи (`customFields`) и ключ `values` массовой операции
допускается, если он **системный** (перечни сняты по DTO тел и Zod-схемам инструментов, свой на
каждую форму запроса) либо адресует поле, **созданное этим прогоном** (журнал, рода `globalField`
и `queueLocalField`). Неизвестный ключ — отказ с его именем. Системное поле Трекера, которого наши
схемы не объявляют, отклоняется осознанно: перечень пополняется вместе со схемой.

Поля обоих родов кладутся в журнал и по идентификатору, и по ключу: ключом поле стоит в теле
задачи, и им же (`myField`, а не `<hex>--myField`) адресуется `PATCH` локального поля очереди.

`YANDEX_TRACKER_LIVE_SCOPE_RUN_OWNER` не задана — любое тело, несущее поле-человека,
отклоняется с названием переменной в тексте отказа. Значение сравнивается со ссылкой буквально:
рубеж не разрешает логин в идентификатор и наоборот, поэтому задавать надо ровно ту форму,
которую шлют инструменты. Ложный отказ здесь безопаснее ложного допуска — прогон встанет,
а не испортит данные организации.

Без `RUN_PREFIX` создание любой сущности организации отклоняется: без известного префикса
допуск давать не по чему. Правка и удаление уже созданного прогоном от `RUN_PREFIX` не зависят
— журнала достаточно.

`YANDEX_TRACKER_LIVE_SCOPE_DISPOSABLE_QUEUE` — отдельный допуск для ровно одной очереди,
которую прогону разрешено завести и убрать (`POST /v3/queues` с этим ключом, массовый перенос
задач `_move` в неё, компоненты и локальные поля внутри неё). Без переменной создание любой
очереди отклоняется. Значение нельзя получить машинально — только явным заданием переменной.

**Ссылка на одноразовую очередь дополнительно требует записи в журнале.** Совпадения строки с
переменной мало: создание могло не состояться или состояться в прошлом прогоне, и тогда ключ
адресует чужую очередь либо не существует вовсе. Ссылка на песочную очередь журналом не
проверяется — она задана самой областью прогона.

Полная таблица правил по каждому семейству — `scope-rules.ts`.

**Пишущий прогон обязан объявить область.** `mcp-dev`, запущенный с
`--dangerously-allow-write`, выставляет дочернему процессу `MCP_DEV_WRITE_ALLOWED=1`;
увидев маркер без объявленной очереди, сервер отклоняет любую мутацию и объясняет, что
задать. Иначе рубеж остался бы тем, что легко забыть включить, — то есть снова
аккуратностью ведущего прогон. Осознанная правка боевых данных возможна:
`YANDEX_TRACKER_LIVE_SCOPE_OFF=i-am-writing-to-production`.

Отказ приходит на вызове инструмента, а не падением на старте: stdio-транспорт не доносит
stderr дочернего процесса, и упавший сервер виден клиенту как «Connection closed» —
транспортный сбой вместо названной причины.

## Устройство

| Файл | Ответственность |
|---|---|
| `scope-rules.ts` | порядок правил: сначала песочная очередь, потом организация; первое совпавшее решает, не совпало ни одно — отказ |
| `sandbox-queue-rules.ts` | правила сущностей, локализованных в очереди: задачи песочницы, компоненты и локальные поля любой очереди области прогона (очередь компонента читается из тела) |
| `organization-rules.ts` | правила сущностей, видных всей организации, и белые списки ключей их тел |
| `rule-matching.ts` | из чего состоит правило, как из тела достаются имя и ссылки, фабрики семейства |
| `people-in-body.ts` | ссылка на живого человека в теле — поиск по всему телу на любой глубине |
| `custom-fields-in-body.ts` | пользовательское поле задачи и `values` — системное либо созданное прогоном |
| `request-path.ts` | приведение пути к сопоставимому виду; неоднозначный путь и любое процентное кодирование в сегменте отвергаются |
| `run-journal.ts` | что создано этим прогоном — основание правки, удаления и уборки |
| `live-scope.guard.ts` | связывает правила и журнал с перехватом HTTP |
| `live-scope.config.ts` | включение по окружению |

Перехват стоит на request-интерцепторе axios (`HttpTrafficGuard` в infrastructure), а не
поверх `IHttpClient`: `upload_attachment` отправляет multipart через `getAxiosInstance()`
в обход интерфейса.

## Известное ограничение

Идентификатор созданной сущности приходит в ответе, то есть **после** мутации. Если процесс
погибнет между ответом сервера и записью в журнал, сущность останется в очереди без учёта,
и уборка по журналу её не найдёт. Сбой самой записи рубеж замечает и переводит себя в отказ,
но смерть процесса — нет. Закрывается снаружи: все создаваемые сущности организации носят
`YANDEX_TRACKER_LIVE_SCOPE_RUN_PREFIX`, по нему остатки находятся поиском.

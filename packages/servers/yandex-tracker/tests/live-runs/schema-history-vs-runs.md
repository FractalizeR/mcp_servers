# Схемы против прогонов: что менялось после отчёта

Снято 2026-08-26 по находке `claude-r2-01` (раунд 2). Предыдущее допущение реестра
(«последний коммит у каждой из 21 схемы принадлежит одной из этих починок; с тех пор их
схемы не менялись») — обобщение по множеству, множеству не соответствующее. Здесь оно
заменено сплошной сверкой: **каждый** из 21 инструмента с записями `LiveObservation`,
а не выборка.

## Чем получено

Скрипт (сохранён в `schema-history-vs-runs.py` рядом с этим файлом) для каждого
инструмента:

1. берёт записи из `tests/coverage-exceptions/live-observations.ts` (имя, свойства,
   `report`, `schemaFingerprint`);
2. находит `src/tools/**/{имя-через-дефис}.schema.ts` и строит **транзитивное замыкание
   его импортов** внутри пакета (относительные пути и `#`-префиксы, `index.ts` у
   каталогов) — так в сверку попадают общие подсхемы `#common/schemas/**`, через которые
   схема могла измениться без правки собственного файла;
3. добавляет к замыканию `*.tool.ts` инструмента — там стоит вызов
   `generateDefinitionFromSchema`, от аргументов которого `inputSchema` тоже зависит;
4. сверяет по git: `git diff --name-only <коммит отчёта> HEAD -- <файлы>` плюс тот же
   diff против рабочего дерева (незакоммиченные правки).

Коммиты отчётов (дата добавления файла в git, до переезда в `tests/live-runs/`):

| Отчёт | Коммит | Дата |
|---|---|---|
| `2_LIVE_RUN_REPORT_2026-08-25c.md` | `8e223af3` | 2026-08-25 21:38:28 +0300 |
| `0_LIVE_RUN_REPORT_2026-08-26.md` | `4da90142` | 2026-08-26 08:34:54 +0300 |

## Чего этот способ НЕ видит

- **Дрейф генератора.** `inputSchema` рождается из zod-схемы адаптером
  `zodToMcpInputSchema` (`@fractalizer/mcp-core`) и версией `zod`. Их смена меняет
  отпечатки всех записей разом, а по файлам инструмента выглядит как «чисто». Проверено
  отдельно, разово: между `8e223af3` и HEAD в `packages/framework/core/src/definition/**`
  и `packages/framework/core/src/tools/base/**` изменён единственный файл
  `tool-warning.ts` (+3 строки, перечисление кодов предупреждений), генератора он не
  касается; версия `zod` в `packages/framework/core/package.json` — `^4.3.6`, диапазон не
  менялся. Диапазон — не пин: та же строка `^4.3.6` допускает другую минорную версию
  после переустановки зависимостей, и этого сверка по git не увидит по построению. Это
  названный риск, см. `claude-r2-06`.
- **Переименование файла схемы.** Замыкание строится по текущему дереву; если файл
  переехал, `git log`/`git diff` без `--follow` истории до переезда не покажет.
- **Дата коммита ≠ дата наблюдения.** Сверка ведётся по коммиту, которым отчёт попал в
  git, а не по времени самих вызовов. Правка схемы между последним вызовом прогона и
  коммитом отчёта попала бы в графу «чисто». Для `update_queue` этот зазор как раз
  содержателен: живая проба `issueTypes`, названная в теле коммита `b1198193`, в самом
  отчёте не зафиксирована — см. ниже.
- **Огрубление по `*.tool.ts`.** Файл берётся целиком, хотя на `inputSchema` влияет
  только вызов `generateDefinitionFromSchema`. Отсюда ложное срабатывание у
  `update_component` (разобрано ниже). Направление огрубления безопасное: лишний красный,
  не молчаливый зелёный.
- **Межпакетные вкладчики схемы вне двух проверенных каталогов core.** Замыкание
  строится только внутри пакета: `resolve()` отдаёт `None` на любом bare-спецификаторе
  (`unresolved specs: ['@fractalizer/mcp-core', 'zod']`), а дрейф генератора закрыт
  разовой ручной сверкой ДВУХ каталогов — `core/src/definition/**` и
  `core/src/tools/base/**`. Zod-фрагменты, которые ядро экспортирует вне этих двух
  каталогов, способ не видит вовсе, и они реальны уже сегодня:
  `collectionResponseModeParamSchema` (`core/src/tools/common/collection-result/`)
  импортирует `find-issues.schema.ts`, `createRawApiRequestSchema` —
  `raw-api-request.schema.ts`. Ни одного из этих двух инструментов в реестре наблюдений
  пока нет, поэтому сегодняшняя сверка верна; с первой же их записью способ даст
  «чисто» на изменившейся схеме молча. При следующем использовании: резолвить
  `@fractalizer/mcp-core` в `packages/framework/core/src` и продолжать замыкание там же,
  вместо ручного выбора двух каталогов.
- **`*.tool.ts` добавляется БЕЗ замыкания своих импортов** (`set(schema_closure) |
  {one(tool, '.tool.ts')}`), хотя текст выше описывает его как «добавляет к замыканию».
  Для сегодняшних 21 инструмента безвредно — у всех `getParamsSchema()` возвращает
  символ из одноимённого `*.schema.ts` (проверено по всем 21), — но метод этого не
  гарантирует: инструмент, собирающий схему из чужого файла, вкладчика потеряет.
- **Отпечаток и без того слеп к маршруту и к форме ответа** — это свойство самого
  механизма, а не этой сверки; названо в `tool-schema-fingerprint.ts` и
  `tests/TESTING_STRATEGY.md` §1.

## Разбор двух срабатываний

**`update_component`** (отчёт `8e223af3`, 2026-08-25 21:38):

### `update_queue` — расхождение настоящее

Коммит `b1198193` (2026-08-25 23:29:19, то есть **после** коммита отчёта `8e223af3` в
21:38:28) удалил из схемы параметр `issueTypes` с пометкой BREAKING CHANGE. Значит
записанный `c7a9d1e0debb` снят с контракта, которого прогон 25 августа не наблюдал.

**Наблюдение правку пережило, и это проверяемо, а не принято на веру:**

- содержание наблюдения — правка описания очереди `TESTSWEEP` с обратным чтением (версия
  2, описание «описание правленое», отчёт `2_LIVE_RUN_REPORT_2026-08-25c.md`, абзац
  «Состояние на конец прогона»);
  параметра `issueTypes` в этой пробе не было;
- удалённый параметр в момент прогона **не работал вовсе**: тело коммита `b1198193`
  фиксирует живую пробу — `400 issueTypes: Incorrect data format`, тот же ответ, что у
  создания очереди, который отчёт называет прямо строкой таблицы «`create_queue` с
  `issueTypes` | `400` | параметра больше нет» (ссылка цитатой, а не номером строки:
  номера в редактируемом документе не переживают правок выше по тексту);
- то есть правка схемы сузила контракт ровно на ту часть, которая наблюдением не
  свидетельствовалась и свидетельствоваться не могла.

Исход: записи `update_queue` **пере-штампованы** — отпечаток текущий, а факт
пере-штамповки вынесен в отдельное поле `fingerprintRestamp` (видно в диффе и в матрице),
где названы коммит правки и обоснование. Удаление записи не потребовалось.

### `update_component` — ложное срабатывание сверки

Изменён только `update-component.tool.ts`, коммитом `fe4ddcea`, и изменение целиком лежит
в `execute()` (добавлено предупреждение `VERSION_NOT_PROVIDED`). `getDefinition()` и
аргументы `generateDefinitionFromSchema` не тронуты, схема не тронута — `inputSchema`
прежний. Срабатывание — следствие огрубления «берём файл целиком», названного выше.

## Что из этого следует для реестра

1. Формулировку «последний коммит принадлежит одной из этих починок» из JSDoc
   `LIVE_OBSERVATIONS` убрать: она неверна у 10 инструментов (последний коммит `1ac8b514`
   или `4f49aa0f`, к починкам прогонов отношения не имеющие) — безвредно, но это
   обобщение, а не факт.
2. Заменить на проверяемое утверждение: сверка даты коммита схемы с датой коммита отчёта,
   с ссылкой на этот файл и на способ повторить.
3. Единственное содержательное нарушение — `update_queue`; оно закрыто пере-штамповкой с
   обоснованием, а не смягчением барьера.

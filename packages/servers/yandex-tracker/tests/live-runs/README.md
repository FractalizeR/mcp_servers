# Отчёты живых прогонов

Доказательная база реестра `tests/coverage-exceptions/live-observations.ts`: каждая запись
`LiveObservation`/`LiveUnreachable` ссылается полем `report` на файл из этого каталога, и
ссылка на несуществующий путь роняет `npm run coverage:check`.

**Отчёт узнаётся по имени: `{N}_LIVE_RUN_REPORT_{ГГГГ-ММ-ДД}[буква].md`.** Конвенция
нормативна, а не косметична: её проверяет `requireReportSupportsRecord`. Без неё
доказательством проходил любой файл каталога, называющий инструмент и метку прогона, —
включая этот README (он содержит и то и другое). Прочие файлы каталога — документы о
каталоге, а не доказательства.

**Почему не в `.agentic-planning/`.** Каталог плана предписано удалять после исполнения
(корневой `CLAUDE.md`), а `inputs` задач `coverage:matrix`/`coverage:check` (`turbo.json`)
его не перечисляют — уборка дала бы кэш-хит и зелёный гейт при исчезнувшем доказательстве.
Здесь путь входит в `inputs`: правка или пропажа отчёта пересчитывает матрицу.

**Отчёт не редактируется задним числом.** Он фиксирует, что наблюдалось в конкретном
прогоне под конкретной меткой (`YANDEX_TRACKER_LIVE_SCOPE_RUN_ID`); новое наблюдение — новый
файл и новая метка, а не правка старого.

**Единственная разрешённая правка старого отчёта — назвать инструмент, чей эффект отчёт уже
описал, И ТОЛЬКО когда этот эффект не мог принадлежать никакому другому вызову прогона.**
Валидация реестра требует, чтобы отчёт содержал имя инструмента записи и метку
прогона (`live-observations.ts`, `requireReportSupportsRecord`). Засчитываются обе формы
имени — базовая (`update_board`) и с префиксом сервера
(`fr_yandex_tracker_update_board`, форма корневого `CLAUDE.md`), — а отчёты 25 и 26 августа
писались в терминах сущностей («Задача `TEST-25` создана»), а не инструментов. Проставить
рядом `create_issue` — не новое наблюдение, а имя того, что уже зафиксировано.

Граница проходит здесь, и она узкая:

- **можно** — эффект по построению производит ровно один инструмент сервера: задачу создаёт
  только `create_issue`, описание очереди правит только `update_queue`. Атрибуция выводима
  однозначно, и в записи реестра честно сказано, что она выведена, а не зафиксирована вызовом;
- **нельзя** — сущность могла возникнуть побочно, как следствие другого вызова. Колонки доски
  могла принести сама доска, и в отчёте 25 августа стоит «не установлено», а не
  `create_board_column`. Правило, не различающее эти случаи, разрешает называть инструмент
  шире, чем позволяет доказательство, — так и появилась та строка.

Сомневаешься между «однозначно» и «могло возникнуть побочно» — пиши «не установлено»:
неназванный инструмент стоит одной клетки матрицы, названный неверно — доверия ко всему
реестру. Менять сам факт, идентификаторы или исход — нельзя ни в каком случае. Правила самих
прогонов — `packages/servers/TESTING_STRATEGY.md` §4, песочница и допуск по владению прогоном
— `../TESTING_STRATEGY.md` §1.

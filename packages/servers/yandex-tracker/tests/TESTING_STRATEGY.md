# Стратегия тестирования: специфика Яндекс.Трекера

Общий канон (свойства С-1..С-7, уровни проверки, инвариант проверки эффекта, правила живых прогонов,
чек-лист нового инструмента) — в [packages/servers/TESTING_STRATEGY.md](../../TESTING_STRATEGY.md).
Здесь только то, что верно для Трекера и неверно для остальных серверов.
Устройство тестов — в [README.md](./README.md).

## 1. Песочница: очередь `TEST` в боевой организации

Отдельной тестовой организации нет, поэтому изоляция правами недостижима — токен живых прогонов
видит всю организацию. Правило 1 общего канона (белый список области действия) здесь не второй
рубеж, а единственный: он обязан отклонять любой не-GET запрос за пределами сущностей очереди `TEST`,
созданных текущим прогоном.

Рубеж реализован (`src/live_scope/`, см. [README](../src/live_scope/README.md)) и включается
переменными `YANDEX_TRACKER_LIVE_SCOPE_QUEUE`, `_JOURNAL` и `_RUN_ID`; без них сервер работает
как прежде. Перехват стоит на
request-интерцепторе axios, а не поверх `IHttpClient`: `upload_attachment` отправляет multipart
через `getAxiosInstance()` в обход интерфейса, и рубеж на уровне методов пропустил бы именно
мутирующий запрос. Отказ — `ScopeViolationError`: он не отображается в сетевую ошибку и не
повторяется retry (иначе один отказ давал четыре попытки и выглядел сбоем сети).

Живые прогоны идут через собранный бандл (`mcp-dev`), поэтому рубеж живёт в `src/`, а не в
тестовой оснастке: оснастка тот путь не покрывает.

### Что разрешено живьём

Критерий один: **сущность локализована в очереди `TEST` и не видна за её пределами.** Отсюда
разрешены задачи прогона и всё вложенное в них (комментарии, чек-листы, вложения, worklog, связи,
переходы), создание задач в `TEST`, массовые операции по явному списку ключей прогона, компоненты
и локальные поля очереди `TEST`.

Принадлежности очереди мало — требуется и запись в журнале прогона: очередь `TEST` общая, в ней
лежат чужие задачи и задачи прошлых прогонов. Задача адресуется двояко (ключ либо 24-hex id),
и журнал хранит обе формы: иначе защита обходится сменой формы записи.

### Реестр исключений: что живьём не проверяется

| Сущность | Почему | Замещающая проверка |
|---|---|---|
| очереди (создание, правка, доступы) | меняют организацию, а не песочницу | интеграционные тесты на моках |
| проекты | принадлежат организации целиком | интеграционные тесты на моках |
| глобальные поля | действуют во всех очередях | интеграционные тесты на моках |
| цели и сущности Entity API | видны организации, а не очереди | интеграционные тесты на моках |
| доски и колонки | видны за пределами очереди | интеграционные тесты на моках |
| спринты | принадлежат доске | интеграционные тесты на моках |
| сохранённые фильтры | видны за пределами очереди | интеграционные тесты на моках |

Путь, не описанный ни одним правилом, отклоняется (fail-closed): новый инструмент, про область
действия которого не подумали, обязан быть замечен отказом, а не по испорченным данным. По той же
причине отвергается путь, который адресует не то, что показывает: `..`, `%2F`, `//` — axios
канонизирует путь уже после рубежа, и `/v3/issues/TEST-1/../../v2/projects/11` уходил бы в чужой
проект, будучи разрешённым как запрос к задаче песочницы (найдено ревью 2026-08-20).

Журнал подписан меткой прогона и чужой не принимает: файл, забытый от прошлого запуска, иначе
выдавал бы права на его сущности. Повреждение журнала или сбой записи переводят рубеж в отказ —
неизвестный учёт не является основанием разрешать.

Если появится отдельная организация — этот раздел заменяется изоляцией правами, а реестр исключений
сокращается.

## 2. Источник истины про API

1. Официальная документация Яндекс.Трекера.
2. Референсный Python-клиент `yandex_tracker_client/` (git submodule) — **не** собственный код:
   сверка операции с нашим же кодом доказывает лишь его самосогласованность.

**Версии API.** Категория обязана ходить в версию из таблицы в
[CLAUDE.md](../CLAUDE.md) (issues/queues/comments/links/transitions/changelog — v3;
attachments/checklists/components/projects/worklogs — v2). Проверка версии входит в интеграционный
тест каждой операции: v2 вместо v3 обычно отвечает 200 и молча отдаёт другую форму данных.

**Эндпоинты по аналогии.** Часть путей взята из общей механики референсного клиента
(`Collection.get_all()`, базовый `Collection.delete()`), а не из документации — например
`GET /v3/filters` (см. комментарий в `get-filters.operation.ts`). Каждый такой случай — гипотеза,
подлежащая проверке живым прогоном; открытый пример: существует ли `DELETE /v3/filters/{id}`
(инструмента `delete_filter` у нас нет, асимметрия CRUD не подтверждена ответом API).

## 3. Классы дефектов, уже реализовавшиеся в этом сервере

Каждый прошёл мимо зелёных моков — это и есть обоснование живого уровня и регрессионных тестов:

| Дефект | Класс | Регрессия проверяет |
|---|---|---|
| `find_issues` терял ключи при фильтрации полей | С-3 | идентификаторы переживают `fields` и режим `links` |
| `transition_issue` возвращал описание перехода вместо задачи | С-3/С-4 | тип возвращаемой сущности |
| Ложный `hasNextPage` на курсорных эндпоинтах | С-6 | неполная страница ⇒ `false`; `nextCursor` ⊇ `hasNextPage` |

## 4. Пагинация: типы постранички в одном сервере различаются

`TrackerPaginator` обслуживает несколько механик сразу — offset (`page`/`perPage`), курсор,
`Link rel="next"`, флаг `truncated`. Тест пагинации, написанный на одном эндпоинте, **не переносится**
на другой: для каждого пагинируемого эндпоинта тип постранички фиксируется явно, а обрыв по
защитному лимиту страниц отличается в ответе от «есть ещё данные» — это разные смыслы.

## 5. Batch: единый формат обязателен

Все batch-операции возвращают `{ total, successful[], failed[] }` с `issueId` в каждом элементе обеих
групп — в том числе когда всё упало и когда всё прошло. Конвенция и `ParallelExecutor` описаны в
[CLAUDE.md](../CLAUDE.md); тест обязан покрывать смешанный исход, а не только happy path.
Соблюдение `MAX_CONCURRENT_REQUESTS` проверяется барьером, а не таймингами — тайминговый вариант
уже давал флак.

**Соблюдение проверяется машинно, не только декларируется.** До плана `plan_tool_contract_unification`
этот раздел был декларацией, которую код не соблюдал: 10 инструментов отдавали `successful` числом
вместо массива (счётчик, а не форма из первого абзаца) — расхождение прошло мимо ревью и держалось до
живого прогона 2026-08-20. Два независимых машинных барьера закрывают этот класс регрессии:

- контрактный тест `tool-output-schema-representatives.test.ts` — форма `successful`/`failed` и общее
  имя ключа идентификатора зафиксированы через `makeBatchResultSchema`
  (`#common/schemas/output.schema.js`), единственное место, откуда её берёт каждый `*.schema.ts`;
- `npm run check:tool-contract-ratchet` (корень монорепо, `scripts/check-tool-contract-ratchet.ts`,
  шаг `validate`) — падает, если в `*.schema.ts` появится `successful: z.number(...)`. Слепое пятно
  описано в самом скрипте: `successful`, собранный на стороне `*.tool.ts` рантайм-объектом (а не
  Zod-полем), этому шагу не виден — форму там держит только контрактный тест выше.

Декларация в этом файле без одного из этих двух барьеров не значит ничего — история этого самого
расхождения тому доказательство.

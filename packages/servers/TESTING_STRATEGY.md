# Стратегия тестирования MCP-серверов

Общий канон для всех серверов монорепо (`yandex-tracker`, `yandex-wiki`): **что должно
быть проверено, чтобы утверждать, что инструмент работает**. Устройство тестов конкретного сервера —
в его `tests/README.md`; специфика домена — в его `tests/TESTING_STRATEGY.md` (если заведён).

---

## 1. Семь свойств исправного инструмента

| # | Свойство | Формулировка |
|---|---|---|
| С-1 | Достижимость | виден в `tools/list`, вызывается по протоколу, `inputSchema` генерируется из Zod без расхождений; `DISABLED_TOOL_GROUPS` реально убирает категорию |
| С-2 | Контракт входа | валидное принимается, невалидное отвергается **до** HTTP-вызова, все объявленные параметры реально доходят до запроса |
| С-3 | Контракт выхода | ответ соответствует `outputSchema`; идентификаторы не теряются при фильтрации полей; форма ответа одна и та же на полном и частичном успехе |
| С-4 | Верность API | правильный endpoint правильной версии правильным методом с правильным телом |
| С-5 | Правдивость эффекта | заявленное изменение действительно произошло, и это подтверждено **независимым чтением** |
| С-6 | Поведение на краях | пагинация, batch с частичными отказами, коды ошибок, лимиты, юникод, таймауты и ретраи |
| С-7 | Пригодность для LLM | находится по запросу пользователя, описание не врёт, ответ не взрывает контекст, аннотации соответствуют поведению |

## 2. Уровни проверки: что каждый ловит и чего не ловит

| Уровень | Ловит | НЕ ловит |
|---|---|---|
| Контрактные smoke (`tests/smoke`) | регистрацию, схемы, редакцию секретов, единый формат ошибок | любое расхождение с реальным API |
| Unit (`tests/unit`) | логику трансформации и ветвления | сетевой контракт |
| Integration на моках (`tests/integration`) | путь tool → operation → HTTP, форму запроса | правдивость самого мока |
| Raw-wire (`scripts/raw-wire-test.ts`) | JSON-RPC поверх собранного бандла, сбои транспорта | доменное поведение |
| Живой прогон (`tests/live`) | С-4, С-5, С-6 на реальных данных | — |

**Почему живой уровень обязателен.** Мок подтверждает лишь то, что автор кода и автор мока поняли
API одинаково — включая случай, когда оба поняли неверно. Уровни выше живого не наблюдают С-4 и С-5
в принципе; отсутствие живого уровня означает, что эти два свойства не проверяются ничем.

**Строчное покрытие не является критерием исправности** — оно не наблюдает ни С-4, ни С-5.

## 3. Инвариант проверки эффекта (С-5)

> Результат мутирующего инструмента никогда не принимается как доказательство того, что мутация
> произошла.

После каждой мутации — независимое чтение (raw-API-инструмент сервера) и сравнение с ожидаемым
состоянием. Читать тем же инструментом, чей эффект проверяется, запрещено: инструмент, который
отчитался об успехе, ничего не изменив, невидим для проверки «ответ выглядит правильно».

По той же причине **уборка после живого теста идёт через raw API, а не через тестируемые `delete_*`**:
иначе сломанный `delete_*` оставляет мусор и одновременно прячет собственный дефект.

## 4. Правила живых прогонов

Применимы независимо от домена; конкретная песочница описывается в доке сервера.

1. **Белый список области действия.** Harness перехватывает исходящий HTTP и отклоняет любой не-GET
   запрос за пределами песочницы, созданной текущим прогоном, — на клиенте, до сети. Обязателен
   негативный тест самой оснастки: без него белый список выглядит работающим ровно до первого
   нарушения.
2. **Уборка только по журналу прогона.** Удаляется лишь созданное этим прогоном. «Удалить всё, что
   нашлось в песочнице» запрещено, если песочница делит пространство с чужими данными.
3. **Массовые операции — только по явному списку идентификаторов** этого прогона.
4. **Префикс прогона** в именах всех создаваемых сущностей: без него повторный запуск отравляет
   выборки предыдущего, и тесты флакают по причине, неотличимой от дефекта продукта.
5. **Реестр исключений.** Всё, что по природе выходит за пределы песочницы, живьём не проверяется —
   с явной записью, какой моковый уровень его замещает. Непокрытая зона должна быть названной.

*Ограничение метода:* белый список в клиенте слабее прав на сервере — он защищает от дефекта в
тестируемом коде, но не от дефекта в самом белом списке. Где доступна изоляция правами (отдельная
организация, отдельный аккаунт), она предпочтительнее и правило 1 становится вторым рубежом.

## 5. Эндпоинты, выведенные из механики SDK или из соседних эндпоинтов

Endpoint, взятый не из документации, а по аналогии (общий механизм референсного клиента, «у соседней
сущности так же»), — **гипотеза, а не факт**, и помечается комментарием в операции. Проверяется
живым прогоном. Утверждение «такого метода в API нет» требует того же доказательства — кода ответа
на реальный запрос, а не отсутствия строчки в документации.

## 6. Канон предупреждений (`warnings`)

Контракт уровня `@fractalizer/mcp-core` (`src/definition/tool-warning.ts`), обязателен для всех
серверов монорепо. Основание и разбор альтернатив — план `plan_tool_contract_unification`, README
§2–3.

**Что это.** `warnings?: ToolWarning[]` — необязательное поле success envelope
(`{ success: true, data, warnings? }`), `ToolWarning = { code, message, details? }`. Предупреждение
не меняет `success: true` и не делает ответ `isError` — это не отказ, а честная оговорка к
успешному результату.

**Инвариант «только когда непусто».** Поле `warnings` присутствует в ответе, только если массив
непуст; пустого массива или `warnings: []` быть не должно — иначе предупреждения превращаются в
фон, который агент перестаёт замечать. Проверяется на **обеих** проекциях ответа
(`content[0].text` и `structuredContent` — MCP дублирует payload для клиентов без поддержки
структурированного контента).

**Перечень кодов замкнутый.** Расширяется только правкой `tool-warning.ts`, не добавлением кода
inline в инструменте. На момент записи: `FIELDS_WITHOUT_VALUE` (путь из параметра `fields` не дал
значения ни у одного элемента ответа), `UNKNOWN_PARAMETER` (во входных параметрах есть имя, которого
нет в схеме инструмента, а запрос в остальном валиден), `AMBIGUOUS_ENTITY_ID` (операция создала
сущность, чей id совпал с id другой существующей сущности в той же области видимости).

**Предупреждение называет наблюдаемый факт, а не гипотезу о причине.** По ответу API невозможно
отличить опечатку в имени поля от легитимно пустого значения — `assignee.display` у задачи без
исполнителя отсутствует ровно так же, как `totallyBogusFieldName`. Поэтому формулировка честная:
«поля не вернули значения ни у одного элемента ответа», а не «неизвестное поле» или иная гипотеза,
которую код не может подтвердить.

## 7. Чек-лист для нового инструмента

- [ ] unit-тест на логику трансформации;
- [ ] интеграционный тест: верный метод/путь/версия API (сверено с внешним источником истины, а не
      с собственным кодом), happy path против `outputSchema`, отказ валидации без HTTP-вызова,
      отображение 403/404 в контрактную ошибку;
- [ ] batch (если применим): смешанный исход даёт обе группы, идентификатор в каждом элементе;
- [ ] пагинация (если применима): полная страница ⇒ `hasNextPage=true`, неполная ⇒ `false`;
- [ ] аннотации правдивы: `readOnlyHint=true` ⇒ ни одного не-GET запроса за весь тест;
      `destructiveHint` ⇔ `requiresExplicitUserConsent`;
- [ ] описание содержит английские ключевые слова — поиск инструментов на стороне MCP-клиента
      кириллицу не матчит;
- [ ] живой сценарий с read-back — либо строка в реестре исключений с указанием причины.

## 8. Уроки процесса

### 8.1 Устаревший `dist` отравляет тесты и маскируется под флак

Пойман 2026-08-20 (план `plan_tool_contract_unification`, 3.1). `dist/` пакета, собранный до
правки исходников, привёл к тому, что `TOOL_CLASSES` в `composition-root/types.ts` оказывался
массивом из `undefined`, и падало 242 файла из 246. Симптом выглядел как гонка параллельных
агентов: три исполнителя независимо доложили «транзиентное падение, прошло само». Оно не проходило
— просто каждый гонял только свою категорию тестов.

1. **Вывод «флак» требует изолированного повтора на тихом дереве.** Несколько независимых
   наблюдений одного симптома не делают объяснение верным: здесь три отчёта сошлись на «гонке», а
   детерминированный повтор 3 из 3 показал жёсткую поломку.
2. **Тесты зависят от собранного артефакта** (`turbo.json`: `test` → `dependsOn: build`), поэтому
   `dist`, собранный из несогласованного состояния исходников, даёт отказ, который не объясняется
   ни одним изменением в `src`. Первое действие при необъяснимом массовом падении — пересобрать
   `dist` и повторить, до анализа графа импортов.

### 8.2 Фундаментный этап обязан отдавать точку употребления, не только механику

Пойман тем же планом. Этап 1.1 поднял механику предупреждений (детектор, схему `ToolWarning`,
контракт формата) без готового хелпера подключения к конкретному инструменту. Результат — 24
независимо написанные копии одной и той же интеграции в 11 категориях инструментов, и как следствие
— расхождение самого контракта: две несовместимые формы поля `details` внутри одного и того же
проекта. Свести это пришлось отдельным этапом (2.8).

Правило: механика без готовой точки употребления не считается завершённым фундаментом. Этап,
вводящий общий контракт для нескольких последующих потребителей, обязан поставить вместе с
контрактом рабочий пример или хелпер его подключения — иначе каждый потребитель придумывает
подключение заново, и разнобой возвращается в новой форме на следующем уровне.
